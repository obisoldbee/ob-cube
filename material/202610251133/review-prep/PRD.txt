## 0. 结论先行

1. **产品的真正卖点不是"网页魔方"，而是"同一题面的可复现人机同台"**。速拧计时器已经解决了打乱与手感，AI 评测平台已经解决了复现与对比，但两者从未合并在一个页面里。本产品的差异化就压在这条缝合线上。
2. **MVP 必须闭环 12 项 P0 功能**，其中 4 项是"没有它整个产品定义就不成立"的地基：统一引擎、seed 可复现题面、API 层蒙尘门控、操作记录与回放。
3. **两个必须先说清楚的诚实边界**：纯前端不能真正防作弊，蒙尘只能做到"不主动泄露 + 抬高作弊成本"；不接求解器时难度分级只能是启发式估计，必须标注为估计值。
4. **最大的产品风险是键盘记忆成本**，不是技术风险。4 阶的可操作层组合有 10 种以上，键位设计失败会让人类玩家在第一分钟流失。

## 1. 产品定义

### 1.1 一句话描述

> 一个网页，人和 AI Agent 用**同一套魔方引擎、同一份计步规则、同一条回放记录**，在**同一个可复现题面**上比谁还原得更好。

### 1.2 核心问题

| 谁 | 什么场景 | 现在怎么解决 | 为什么不行 |
|---|---|---|---|
| 普通玩家 | 想在浏览器里不装 App 就转两把 2/3/4 阶，并且能复盘自己的操作 | 用速拧计时器（csTimer / CubeDesk / Twisty Timer） | 这些工具的核心是"计时 + 成绩统计"，虚拟魔方要么没有、要么是附属功能；键位是给熟练速拧者设计的，没有引导；没有"这一把我转了什么"的逐帧复盘 |
| AI Agent 开发者 | 想验证自己的 Agent 是否真能"看懂魔方状态并规划转动"，而不是靠模拟点击碰运气 | 自己写脚本 + 自己造魔方状态 | 没有标准化题面、没有统一计步、没有可对比的历史运行，每次实验结论都无法复现；自己造的题面别人无法重跑 |
| 模型评测人员 | 想用同一批题面横向比较多个模型/多个 prompt 版本 | 用通用 Agent benchmark（AgentBench / SWE-bench 类） | 这些平台没有"带观察权限限制的几何状态推理"场景；想加一个魔方维度就得自己搭全套环境 |

**一句话**：缺的不是魔方，缺的是**"同题面 + 同引擎 + 同计步 + 可回放"的横向可比性**。

### 1.3 目标用户画像

| 画像 | 特征 | 关键诉求 | 会因为什么放弃 |
|---|---|---|---|
| **A. 普通玩家**（主） | 18–35 岁，会还原 3 阶但非竞速选手，愿意在浏览器里消磨 5–15 分钟 | 打开就能转；不用背键位；能看回放知道自己哪一步走错了 | 前 60 秒内搞不清怎么转某一层；键位提示要看说明书 |
| **B. AI Agent 开发者**（主） | 熟悉 JS，能在控制台里调 `window.cubeAgent`，关心确定性与可调试性 | 题目 seed 固定；每步有明确返回值；能导出 trace；失败原因明确 | API 返回值模糊、错误码缺失、同 seed 出不同题面 |
| **C. 模型评测人员**（次） | 需要跑批量对比但这次不想搭后端 | 同一题面能跑 N 次；结果有表格对比；知道每次跑用的什么配置 | 记录里分不清"哪次是哪个 prompt 版本"；没有运行元信息 |

次要用户：教程作者（需要可分享的固定题面链接）。

### 1.4 产品设计原则（继承并修订原文）

| 原则 | 状态 | 说明 |
|---|---|---|
| 人类与 Agent 使用同一套引擎方法 | 保留 | Agent 调用的是引擎方法本身，不是模拟点击 |
| 视觉展示、真实状态、观察权限三者独立 | 保留 | 三者分层，互不耦合 |
| 每次转动可验证、可记录、可复现 | 保留 | 事件级记录 |
| 默认不向 Agent 暴露隐藏状态 | **修订** | 原文为"由服务端强制执行"。本产品无服务端，改为"由 API 层门控强制执行，并明确其不可强保证的边界"（见 §8） |
| 时间/步数/难度/观察限制由挑战配置决定 | 保留 | 配置即契约 |

## 2. 用户流程

### 2.1 状态机总览

```
idle ──▶ configuring ──▶ ready(蒙尘) ──▶ running ⇄ paused ──▶ finished ──▶ review
              ▲                          │                              │
              └──────────── 新建挑战 ◀─────┴──────────────────────────────┘
```

> `paused` 是 `running` 的子状态（仅人类模式可进入），**计时不停止**。详见 §7.2.1。

| 状态 | 含义 | 魔方是否可见 | 计时 | API 可写 | API 可读颜色 |
|---|---|---|---|---|---|
| `idle` | 未创建挑战 | 不渲染或渲染已还原态演示体 | 未启动 | 否 | 否 |
| `configuring` | 配置中 | 不渲染真实题面 | 未启动 | 否 | 否 |
| `ready` | 题面已生成、等待开始（**蒙尘点**） | 仅遮蔽材质，无颜色 | 未启动 | 否 | **否** |
| `running` | 挑战进行中 | 按观察规则开放 | 运行 | 是 | 按观察规则 |
| `paused` | 暂停中（仅人类，屏蔽输入与观察） | 冻结在暂停前最后一帧 | **继续运行** | 否 | 否 |
| `finished` | 已结束（成功/失败） | 全开 | 停止 | 否 | 是（含答案） |
| `review` | 回放中 | 全开 | 停止 | 否 | 是 |

### 2.2 逐步流程

#### 步骤 1：创建挑战（`configuring`）

**界面状态**：单页三栏布局。左栏为配置表单，中栏为空态引导（说明"选好配置后点创建"），右栏为最近 5 条历史运行摘要。

**可配置项与默认值**：

| 字段 | 选项 | 默认 | 备注 |
|---|---|---|---|
| 阶数 | 2×2 / 3×3 / 4×4 | 3×3 | 切换阶数时重置层选择器 |
| 参与者 | 人类 / AI Agent | 人类 | 仅影响 UI 文案与是否默认聚焦 API 面板，不影响引擎 |
| 题目来源 | 随机打乱 / 固定题目 / 指定 seed / 导入 | 随机打乱 | 见 §2.2 步骤 2。**v1 的"随机"= 随机操作打乱（`random_moves`），不提供均匀随机状态生成**（§6.5）。UI 上不得出现"随机状态 / 均匀随机 / 标准化题面"一类措辞 |
| 时间限制 | 不限时 / 预设（60s / 3min / 5min / 20min）/ 自定义 | 20 分钟 | 下限 10s，上限 180 分钟 |
| 步数限制 | 不限步 / 预设（20 / 50 / 100 / 200）/ 自定义 | 不限步 | 下限 1 |
| 蒙尘模式 | 开 / 关 | 关 | 开启后 `ready` 态强制遮蔽 |
| 观察模式 | 完整观察 / 三面观察 / 单面观察 / 操作后观察 / 受限观察 | 完整观察 | 见 §7.2 观察规则 |
| 键盘 180° 双击归并 | 开 / 关 | 开 | 关闭后 180° 只能通过界面按钮提交，键盘不提供替代键（`Alt` 因会触发浏览器菜单栏聚焦，已禁用，见 §5.3.5） |

**系统行为**：
- 表单校验不通过（如时间填 0、步数填负数）时，"创建挑战"按钮禁用并就地显示原因文案，不使用弹窗。
- 点击"创建挑战"后进入 `ready`。

#### 步骤 2：生成题面（`configuring` → `ready`）

**系统行为**（顺序执行，任一失败则回退到 `configuring` 并显示原因）：

1. 按题目来源生成题面：
   - **随机**：内部生成一个高熵 seed（32 位），用该 seed 生成题面，并把 seed 写进题面元信息。
   - **指定 seed**：用户输入 1–32 位字符串，用规范化后的 seed 生成题面。
   - **固定题目**：从本地题库选一条 `题目 ID`，直接读其快照，不使用 seed。
   - **导入**：解析用户粘贴的 Singmaster 打乱序列或状态快照，校验合法性。
2. 校验题面合法性（配色方案合法、可还原、非已还原态、最短解距离满足下限，见 §6.4）。
3. 保存题面元信息（§13.1）。
4. 视角复位到默认（默认展示前、上、右三面）。
5. 进入 `ready`：3D 场景切遮蔽材质（单色哑光，不显示任何贴纸色差），API 侧状态置为 `ready`。

**关键约束（蒙尘点）**：`ready` 状态下
- `observe()` **不返回任何颜色、状态字符串或可推导颜色的字段**；
- 页面 DOM 中不渲染任何带颜色的贴纸元素；
- 打乱序列、seed、初始快照不写入 `localStorage`，不由 `window` 可达对象持有（见 §8）。

#### 步骤 3：开始挑战（`ready` → `running`）

**界面状态**：遮蔽材质在 200ms 内溶解为真实贴纸；计时器开始跳字；左栏按钮由"开始挑战"变为"暂停"（次要样式）+ "结束挑战"（次要危险样式）+ "放弃"；右栏操作日志开始接收事件。Agent 模式下不渲染"暂停"按钮（§7.2.1 P5）。

**系统行为**：
1. 记录 `started_at`（单调时钟）。
2. 状态置 `running`。
3. 开放观察权限：`observe()` 首次返回该观察模式允许的数据。
4. 启动限时倒计时（若配置了时间）。
5. 键盘/按钮/API 输入通道同时开放。

#### 步骤 4：操作（`running`）

**人类玩家**：
1. 鼠标拖拽空白区域 → 轨道旋转视角（不计步、不计时事件）。
2. 键盘按 §5 键位 → 立即提交一次转动。
3. 或：在层选择器中勾选层组合 → 点击轴向箭头按钮。
4. 每次操作后：播放转动动画（时长可在 60–300ms 间由用户设定，默认 150ms），更新步数，追加一条操作事件，刷新右栏日志。
5. 或：点击"暂停"进入 `paused`——输入与观察被屏蔽，但**计时与超时判定继续**（§7.2.1）。再点"继续"回到 `running`。

**Agent**：
1. `observe()` → 拿到观察数据（含 `observation_id`）。
2. 基于观察决定下一步。
3. `applyMove('R')` → 拿到 `{ok, move, cube_state_hash_after, move_count, remaining_ms, observation_id}`。
4. 循环 1–3，直到 `submitSolution()` 或触发终止条件。

**统一约束**：人类与 Agent 的转动**走同一个引擎入口**。人类按键后产生的指令字符串，与 Agent 提交的指令字符串，进入同一条校验与执行路径、产出同构事件。

#### 步骤 5：结束（`running` / `paused` → `finished`）

触发条件（见 §7.3）：还原成功 / 超时（**含发生于 `paused` 期间**）/ 步数耗尽 / 主动放弃 / 提交校验连续失败 3 次。

> 注意：`paused` 可**直接**转入 `finished`。用户在暂停状态下被判定超时是合法路径，此时 `result_detail` 为"超时发生于暂停中"（§7.2.1 P3 / AC-56）。

**系统行为**：
1. 停止计时，记录 `ended_at`。
2. 状态置 `finished`，关闭写通道（`applyMove` 返回 `409`）。
3. 3D 场景全开颜色。
4. 计算并落盘结果对象（§13.3）。
5. 写入 `localStorage` 历史（含题面元信息、事件流、结果）。
6. 右栏切换为结果面板。

#### 步骤 6：结果与回放（`finished` → `review`）

见 §9 与 §10。

## 3. 功能清单与 RICE 排序

### 3.1 RICE 说明

`Score = (Reach × Impact × Confidence) / Effort`

| 维度 | 取值 | 本产品口径 |
|---|---|---|
| Reach | 1–10 | 每季度会用到该功能的用户比例（10 = 几乎所有用户） |
| Impact | 0.25 / 0.5 / 1 / 2 / 3 | 对单个用户完成核心任务的影响 |
| Confidence | 50% / 80% / 100% | 100% = 有明确需求原文或竞品实证；80% = 有间接证据；50% = 判断 |
| Effort | 1–10 | 人月（1 ≈ 半天；10 ≈ 3 个月以上） |

> **重要**：RICE 只用于**排序**，不用于决定 P0。P0 由"MVP 闭环依赖门"决定——任何一项缺失都会让"人机同台可比"这个产品定义不成立，即使它的 RICE 分不高（例如 Agent API 的 Reach 只有 5）。这条规则写在这里，避免后续用分数砍地基。

### 3.4 4 阶操作面板的 tab 组数（锁定）

## 4. 明确不做（Out-of-Scope）

| 不做的事 | 原因 | 何时考虑 |
|---|---|---|
| **后端账号体系**（注册/登录/用户档案） | 产品定位是"打开即用、可离线、可静态部署"。账号体系会引入服务端、隐私合规、密码安全三项非核心负担，且与"无后端"的交付约束直接冲突。历史数据用 localStorage 已能满足单人纵向对比。 | 当出现"跨设备同步成绩"或"多人榜单"的真实需求，且已确认愿意承担服务端成本时。触发信号：≥30% 用户在反馈里提到换设备丢记录。 |
| **云端题库共享**（公开题库市场、他人题面订阅） | 题库共享需要内容审核、版本兼容、题面合法性服务端校验。MVP 阶段用"导出 JSON / 粘贴 seed"已能完成题面流转，成本几乎为零。 | 当固定题库的本地运营量超过约 200 条、或出现"希望别人跑我的题面"的重复请求时。 |
| **自动难度分级**（按最优解长度自动标级） | 真难度需要求解器（2 阶可做，3 阶需两阶段算法，4 阶需降阶 + parity 处理），是数人月量级的独立工程；且 4 阶求解在浏览器里耗时不可控。MVP 用启发式估计（§6）覆盖 90% 的运营标注需求。 | 当难度标签引发争议（同一题被判为不同等级）、或需要对外发布"标准化能力测试集"时。 |
| **批量多步提交**（Agent 一次提交整段算法） | 会绕过"逐步观察"这一核心评测维度：如果允许一次交 60 步，模型就可以不做状态推理只做模式匹配，评测结论失真。且会让计步与人机对比失去可比性。 | 作为**独立模式**（`batch` 标记）与逐步模式并存时考虑；必须单独标注、单独排行榜，不得与逐步模式混算。触发信号：开发者明确反馈逐步调用的网络/调用开销成为主要成本。 |
| **移动端深度适配**（触屏手势转层、竖屏三栏改版、性能调优） | 4 阶有 96 个贴纸 + 层选择器 + 三栏信息，竖屏下触控目标密度不足；手势转层需要独立设计一套交互（本项目 UX 预算只够桌面键盘一套）。第一版优先保证桌面效率（沿用原文"第一版优先保证桌面端操作效率"）。 | 当移动端访问占比 > 25%，或明确出现"想在手机上做 Agent 评测"的需求时。最小让步方案：移动端只读回放 + 只做 2×2。 |
| **求解器提示 / 分步教学** | 与评测平台的核心价值**直接冲突**：任何内置提示都可能被 Agent 通过 API 触达，一旦存在就等于提供答案通道，会污染全部评测结论。另需承担求解器体积与耗时。 | 上线后作为**独立"学习模式"**，与挑战模式硬隔离（不同构建产物或不同页面，学习模式的任何模块在挑战页不加载）。不得出现在挑战页。 |
| **多人比赛房间**（实时对战、观战） | 需要服务端房间、实时同步、断线重连、裁判逻辑；与"纯前端静态部署"约束冲突。竞品 CubeDesk 的 1v1 之所以存在，是因为它本来就有云端基础设施。 | 当产品已有后端（例如因账号体系引入），且"人机同台"已被验证有留存时。 |
| **纯前端防作弊强制** | 详见 §8。做不到就是做不到，不列功能，只列边界。 | 当评测结论需要对外背书（论文、榜单、采购决策）时，必须引入服务端持有状态。 |
| **成绩排行榜 / 反作弊评分** | 没有服务端就无法验证成绩真实性，公开榜单会立刻被污染，反而伤害可信度。 | 与服务端方案同期。 |
| **魔方类型扩展**（金字塔、五魔方、SQ1） | 状态模型与记法体系完全不同，是独立产品线。 | 当 2/3/4 阶的留存与评测使用率已稳定。 |

## 5. 键盘映射方案

### 5.1 设计目标与硬约束

| 约束 | 本方案的处理 |
|---|---|
| 覆盖 2/3/4 阶全部外层转动（6 面 × 顺/逆/180°）= 18 种 | 面键 6 个 × 三种转动量 |
| 覆盖 3 阶中层 M / E / S | `Z` 前缀 + 面键（统一语法，不为中层开特例） |
| 覆盖 4 阶内层（`2R` / `2L` 两族）与宽转（`Rw` / `3Rw` / `Lw` / `3Lw`） | `Z` 前缀（单内层，配本侧面键或对面面键）+ `2` / `3` 前缀（宽转） |
| **不与浏览器快捷键冲突** | 全部使用裸键 + 仅 `Shift` 一个修饰键；**不注册任何 `Ctrl`/`Cmd` 组合**，因此 `Ctrl+W`、`Ctrl+T`、`Ctrl+N`、`Cmd+W` 等保持浏览器原生行为，既不拦截也不依赖；不使用 `/`（Firefox 快速查找）、不使用 `Tab`（焦点切换）、不使用 `F1`/`F5`/`F12` |
| **单手可操作** | 全部面键、全部前缀键、`Shift` 均在**左手可达区**（`Q W E R T / A S D F G / Z X C V` + 数字行 `1 2 3`）。右手全程留给鼠标拖拽视角。这是硬性取舍：不为右手设计任何操作键 |
| **有记忆规律** | 见 §5.2 的"展开图投影"原则：面键的空间位置 = 魔方六个面在展开图上的相对位置 |

### 5.2 核心记忆规律：把魔方展开图投影到左手九宫格

标准魔方展开图（正对屏幕观察）：

```
            ┌───┐
            │ U │            上
    ┌───┬───┼───┼───┐
    │ L │ F │ R │ B │   左 / 前 / 右 / 后
    └───┴───┼───┼───┘
            │ D │            下
            └───┘
```

把这张图的 5 个位置映射到 `W A S D X` 这个"十字"上：

```
        Q(W 左上)   W(上)
   A(左)      S(中心)     D(右)
              X(下)
```

| 面 | 键 | 位置理由 |
|---|---|---|
| **U 上** | `W` | `W` 正在 `S` 正上方，对应展开图的上格 |
| **D 下** | `X` | `X` 正在 `S` 正下方，对应展开图的下格 |
| **L 左** | `A` | `A` 正在 `S` 左侧 |
| **R 右** | `D` | `D` 正在 `S` 右侧 |
| **F 前** | `S` | 十字中心 = 正对着你的那个面 |
| **B 后** | `Q` | 展开图第 4 列本应是 `B`，但那个位置对应键 `F`/`G` 会与"Front"字面冲突。改取 `Q`：`Q` 是整个十字团外围唯一的斜角键，对应"唯一看不见的面"。且 `Q` 与任何面字母（U/D/L/R/F/B）都不重名，零歧义 |

> **为什么不用"字母 = 面名"（按 `R` 键转 R 面）？**
> 因为 `U`、`L`、`B` 三个字母键都在键盘右手区或边缘，强行使用会让右手离开鼠标，违反"单手可操作"与"右手留给视角"两条约束。相比之下空间映射的学习成本是一次性的（约 60 秒，配合常驻键位图），而"按键名转面"的失败成本是每次都要伸手。这是本方案最核心的取舍。`R` 和 `F` 虽然恰好在左手区，但**故意不使用**——半个面用字母、半个面用位置，会破坏规律的一致性，比全用位置更难记。

### 5.3 完整映射表

#### 5.3.1 转动量（三种状态）

| 转动量 | 按键方式 | 助记 |
|---|---|---|
| 顺时针 90°（`X`） | 面键（无修饰） | 默认动作 |
| 逆时针 90°（`X'`） | `Shift` 按住 + 面键 | `Shift` = 反向，与"撤销由 Shift 触发"的通用直觉一致 |
| 180°（`X2`） | 同面键在 **300ms 内连按两次** | 转两下就是 180°，物理直觉 |
| 180°（无键盘替代） | 界面按钮（每个面卡上的 `X2` 按钮） | **不提供 `Alt`/`Ctrl` 类替代通道**：`Alt` 会触发浏览器菜单栏聚焦，`Ctrl` 会撞保留键。关闭双击归并后，180° 只能走鼠标 |

> **`Shift` 与所有前缀正交**：`2`+`Shift`+`R` = `Rw'`，`Z`+`Shift`+`R` = `2R'`，逻辑一致。

#### 5.3.2 层深前缀（决定"转哪几层"）

| 前缀 | 含义 | 2 阶 | 3 阶 | 4 阶 |
|---|---|---|---|---|
| 无 / `1` | 只转外层 1 层 | `R` | `R` | `R` |
| `2` | 从该面起连续转 2 层（宽转） | 忽略（无内层） | `Rw` | `Rw` |
| `3` | 从该面起连续转 3 层（宽转） | 忽略 | 忽略（3 阶三层 = 整体转） | `3Rw` |
| `Z` | **只转该面那一侧的内层**（不含外层） | 忽略 | `2R`（= `M'`） | `2R`（靠近该面） |
| `4` / `C` | **不使用**。见下方"为什么没有 `C` 前缀" | — | — | — |

**为什么没有 `C` 前缀（v1.4 修正，重要）**

4 阶每个轴的 4 个层，按"离哪个外层更近"命名即可完整覆盖两个内层：

| 轴 | 层 1 | 层 2 | 层 3 | 层 4 |
|---|---|---|---|---|
| R/L 轴 | `R` | `2R`（近 R） | `2L`（近 L） | `L` |
| U/D 轴 | `U` | `2U`（近 U） | `2D`（近 D） | `D` |
| F/B 轴 | `F` | `2F`（近 F） | `2B`（近 B） | `B` |

而 `Z` 前缀的定义是"只转该面那一侧的内层"，因此：

- `Z` + `R` = `2R`（R 侧内层）
- `Z` + **`A`（L 面键）** = `2L`（L 侧内层）

**两个内层全部由 `Z` + 六个面键覆盖，不需要第三个前缀。** 原本设想的 `C`+`R`=`3R` 是错的：按"用更近的外层命名"这一唯一规则，R 轴第 3 层应记作 `2L`，而非 `3R`；而 `2L` 恰好由 `Z`+`A` 表达。保留 `C` 会产生"按 `C`+R 却得到 `2L`"的错位映射，是纯负担。

**因此键盘物理键从 12 个降为 11 个**（6 面键 + `1` `2` `3` `Z` + `Shift` + 双击）。G6 这个 tab 仍然存在（见 §3.4），只是它的键盘入口是 `Z` + 对面面键。

#### 5.3.2.1 4 阶按键复用的处理方式（明确回答）

同一个面键 `R` 在 4 阶上承担 3 种含义，**由前缀唯一区分**：

| 用户输入 | 规范化指令 | 转动层（从 R 面数起） |
|---|---|---|
| `R` | `R` | 第 1 层 |
| `2` `R` | `Rw` | 第 1–2 层 |
| `3` `R` | `3Rw` | 第 1–3 层 |
| `Z` `R` | `2R` | 第 2 层 |
| `Z` `A`（L 面键） | `2L` | 第 3 层 |

复用不产生歧义的三个保障：
1. **前缀是"待生效状态"，不是"组合键"**：按下 `2` 后，状态栏立即高亮显示"层深：2 层"，下一次面键按下即消费该状态并复位。状态栏同时预览"将提交：`Rw`"。用户在按下前就能看到结果，不需要记忆。
2. **前缀不跨帧残留**：按前缀后 3 秒内无面键输入，前缀自动取消并在状态栏淡出提示。避免"以为在转外层，实际转了宽转"。
3. **鼠标兜底**：界面上有"层选择器"（2/3/4 阶分别显示 1–4 个层槽位）+ 轴向箭头按钮。**任意连续层区间都能用鼠标精确表达**（非连续子集如 `{1,3}` 既无标准记法也无实际用途，见 §5.7），键盘只覆盖高频子集。因此"覆盖全部层操作"这一要求由"键盘 + 层选择器"共同满足，不存在遗漏。

#### 5.3.3 3 阶中层 M / E / S 的等价表

统一语法 `Z` + 面键，不为中层开特例：

| 用户输入 | 4 阶规范指令 | 3 阶规范指令 | 说明 |
|---|---|---|---|
| `Z` `R` | `2R` | `M'` | 中层，按 R 方向转 |
| `Z` `A`（L） | `2L` | `M` | 同一层，按 L 方向转（与上行互逆） |
| `Z` `W`（U） | `2U` | `E'` | |
| `Z` `X`（D） | `2D` | `E` | |
| `Z` `S`（F） | `2F` | `S` | |
| `Z` `Q`（B） | `2B` | `S'` | |

**为什么 3 阶与 4 阶的规范字符串不同**：
- **3 阶**的中层有公认的单字母 Singmaster 记法（`M`/`E`/`S`），直接用它作为规范字符串，日志列最短且与全球教程一致。
- **4 阶**没有公认的中层单字母记法，只能按"离哪个外层更近"命名（`2R`/`2L`）。同一题面内不会混用两种阶数，所以不存在歧义。

**显示规则**：日志指令列用 `describeMove` 返回值（3 阶 `M'`、4 阶 `2R`）；状态栏额外用括号给出另一族别名（3 阶 `M'（2R）`、4 阶 `2R（M'）`），供熟悉另一套记法的人过渡。

#### 5.3.4 视角与流程控制（右手区，不与魔方操作冲突）

| 键 | 行为 | 备注 |
|---|---|---|
| 鼠标拖拽空白区 | 轨道旋转视角 | 主力方式 |
| `←` `→` `↑` `↓` | 视角按 90° 步进绕竖直/水平轴旋转 | `preventDefault()` 阻止页面滚动 |
| `Home` | 复位默认视角（前/上/右） | `preventDefault()` |
| 界面 6 个面视角按钮 | 直接跳到 U/D/L/R/F/B 正视 | 按钮为文字标签"上视 / 下视 / 左视 / 右视 / 前视 / 后视" |
| `Space` | 仅 `ready` 态 = 开始挑战；仅 `finished` 态 = 返回配置 | `running` 态下 `Space` **不绑定任何操作**，且 `preventDefault()` 阻止滚动。此举避免还原中误触 |
| `Enter` | **仅 `configuring` 态**：创建并开始挑战（与"创建挑战"主按钮等价） | `running` 态下 `Enter` **不绑定任何操作**。理由：提交解答改由界面按钮触发，避免还原中误按 `Enter` 造成一次 `NOT_SOLVED` 失败（累计 3 次会终止挑战） |
| `?`（`Shift` + `/`） | 打开/关闭快捷键说明浮层 | 浮层内 `Esc` 关闭。`Shift+/` 不触发 Firefox 快速查找（裸 `/` 才触发，故裸 `/` 仍禁用） |
| `Esc` | 弹"放弃挑战"确认层 | 确认层内 `Esc` = 取消 |
| `F2` | 聚焦记法输入框（P1 功能 F16） | 不使用 `/`（Firefox 快速查找冲突） |

##### 整体旋转 `x` / `y` / `z` 的口径（已由架构师裁决，三方必须一致）

> **结论：`x` / `y` / `z` 只转相机，不是可提交的转动指令。**

| 面 | 口径 |
|---|---|
| 定义 | 整体旋转 = 改变观察方向，**不改变魔方内部状态**，不计步（§7.1） |
| 人类玩家 | 只能通过鼠标拖拽、方向键、`Home`、界面 6 个面视角按钮实现；**键盘不提供 `x`/`y`/`z` 按键**（附录 A 已注明"不占用键盘"） |
| Agent | 只能通过 `rotateView({axis, direction, steps})` 实现。**调用 `applyMove('x')` 必须被拒绝** |
| 引擎 | `apply_move` 对 `x` / `y` / `z` / `x'` / `y2` 等一切整体旋转记法**直接返回错误**，错误码 `E_NOTATION_ORIENTATION_NOT_MOVABLE`（本文档内简称 `ORIENTATION_NOT_MOVABLE`），**且状态指纹必须不变、`move_count` 必须不增** |
| 为什么这样定 | ① 若 `applyMove` 接受整体旋转，它就能被用来"免费"改变状态而不计步，破坏计步公平性；② 人类与 Agent 必须走同一条权限路径——人类不能用键盘做，Agent 也不能用 `applyMove` 做；③ 把"观察"与"操作"两个通道彻底分开，是 §1.4"视觉展示 / 真实状态 / 观察权限三者独立"原则的直接落地 |
| 连带影响 | `getProgress()` 与 `MoveEvent` 里**不得**出现整体旋转；回放的"视角变化"只作为 `ViewEvent` 记录，不进 `MoveEvent` 流 |

#### 5.3.5 明确禁用的键

| 键 | 禁用原因 |
|---|---|
| 任何 `Ctrl` / `Cmd` 组合 | 与浏览器/系统快捷键冲突，且 `Ctrl+W`/`Ctrl+T`/`Ctrl+N` 无法可靠拦截。本方案**不注册、不 `preventDefault`**，交还浏览器 |
| `Alt` + 任意键 | 会触发浏览器菜单栏聚焦（Windows/Linux）或输入特殊字符（macOS），`preventDefault()` 在各浏览器表现不一致。**完全禁用，不作为任何操作的修饰键** |
| `Tab` | 焦点切换是重要的可访问性通道，不得占用 |
| `F1` `F5` `F11` `F12` | 系统/浏览器功能键 |
| `/` | Firefox 快速查找 |
| 长按重复（key repeat）作为输入 | 长按会连发，导致误转。所有面键在 `keydown` 时若 `event.repeat === true` 直接忽略 |

### 5.4 180° 双击归并的机制与代价（必须写清）

**机制（已按团队主理人裁决修正，禁止按旧版实现）**：

按下 `R` → 立即执行 `R`（状态前进一次，计 1 步，入日志一条）。若 300ms 内再次按下同一面键（其间无其他输入插入）→

1. **状态层：再执行一次 `R`**。`R` 接 `R` 在物理与视觉上本就等于 `R2`，**不需要回退、不需要逆操作、不需要重放**。
2. **计步层：把第二次的 `+1` 抹掉**。`move_count` 净增量 = 1，不是 2。
3. **日志层：把两条事件合并为一条**，`move` 字段为 `R2`，元信息保留 `merged_from: ["R","R"]`。
4. `state_fingerprint_after` 取第二次执行后的真实指纹（与执行 `R2` 的结果一致）。

**明确禁止的实现方式**：不得采用"执行逆操作 `R'` 抵消 + 再以 `R2` 重新提交"。原因：动画会呈现 `R → R' → R2` 三段，观感是一次**闪回抖动**（转过去、转回来、再转半圈），用户会以为程序出错。旧版本 PRD 的字面表述会导致这个错误实现，本节为纠正后的唯一口径。

#### 5.4.1 唯一可行的实现结构：开放事件（open event）

要让 AC-61 / AC-62 / AC-63 三条**同时**成立（1 条事件、净增 1 步、不得出现逆向事件、角度单调 0→90→180、且与显式 `X2` 事件五字段一致），实现结构只有一种：

> **事件在 300ms 窗口关闭时才定稿；引擎立即推进状态、立即起动画；事件流延后写。**

| 时刻 | 引擎状态 | 动画 | 事件流 |
|---|---|---|---|
| 第一次 `keydown` | 立即执行 `R` | 立即从 0° 起转 | 写入一条**开放事件**（未定稿，`move` 暂为 `R`） |
| 300ms 内第二次 `keydown` | 再执行 `R` | 从当前角度继续转，不回 0° | 就地改写该开放事件：`move=R2`、`turn_amount=180`、`merged_from=["R","R"]` |
| 窗口关闭且有第二击 | 停在 `R2` 终态 | 停在 180° | 事件**定稿**，`move_count` +1 |
| 窗口关闭且无第二击 | 停在 `R` 终态 | 停在 90° | 事件**定稿**为 `R`，`move_count` +1 |

四条硬约束：

1. **零输入延迟**：不得为了"确认是单击还是双击"而延后第一下的状态推进或动画（那会引入 300ms 卡手）。
2. **`move_count` 只在事件定稿时 +1**，不在 `keydown` 时 +1。这样"1 条事件 = 1 步"永远成立（AC-21 / AC-61）。
3. **不得产生逆向事件**：合并靠"改写开放事件"，不靠"撤销再重放"（AC-62）。
4. **第一步就已还原时不进入合并窗口**：若第一下 `R` 执行后已满足还原条件，该事件**立即定稿**，不再等待双击。否则"还原判定"与"合并窗口"会互相等待，产生一个 300ms 的判定空窗。

**为什么必须这样**：若不允许"延后写事件"，就只能靠"先写一条再撤一条"，那必然产生可被观测到的撤销痕迹，也就无法满足"不得出现逆向事件"。

**为什么这样设计**：
- 零输入延迟（第一下立刻响应，不像"等 300ms 判断是否双击"那样卡手）；
- 视觉连续（两次 90° 连做，没有任何回退帧）；
- HTM 语义正确（`R2` 记 1 步）；
- 人机一致（Agent 直接发 `R2` 也是 1 步 1 条事件、状态指纹相同）；
- 无状态回退，引擎只需一个"改写开放事件"的日志操作，实现风险最低。

> **归并的性质（口径裁决）**：**归并是输入整形，不是计步规则。** 它把"两次同面击键"整形为"一次 `R2` 意图"，之后一切照 `R2` 处理。因此它与计步规则无关，也不构成对人或 Agent 的差异化对待——见 §7.1.1。

**代价与缓解**：
- 代价：若玩家真的想在 300ms 内连做两次同面 90°（实际还原中几乎只可能是 `R2` 意图），会被归并。
- 缓解：① 可在配置里关闭（关闭后 180° 只能走界面按钮）；② 归并发生时状态栏显示"已合并为 `R2`"并伴随一次轻微高亮；③ 事件元信息保留 `merged_from: ["R","R"]`，回放与审计可查。

### 5.6 键盘映射交付表（供 UI 角标、日志列宽、辅助说明浮层直接使用）

**结构结论（先说清，避免按"每族 2–3 个独立键"去设计）**

在"单手可操作 + 不撞浏览器键 + 有记忆规律"三条硬约束下，**不可能**为每个动作分配独立单键：
- 全量动作数 = 外层 18 + 中层 9（3 阶）+ 宽转 18 + 三层宽转 18（4 阶）+ 单内层 9（4 阶）+ 视角 6 + 会话 4 ≈ **82 个动作**；
- 单手舒适可达区约 15–20 键，全键盘也仅约 100 键但需双手且无规律；
- csTimer 把动作平铺到 3 行 × 10 列（30 键）仍漏掉大量动作，且已被社区视为"必须贴表操作"的失败设计。**平铺路线在 82 个动作上直接不可行。**

因此采用：**6 个面键（单键直达最常用动作）+ 4 个前缀键 + 1 个修饰键 + 1 个双击手势**，共 12 个物理键覆盖 82 个动作。

> **G5 与 G6 是同一机制的两半，不是两套键**：4 阶每个轴有 2 个内层，`Z`+本侧面键拿到近本侧的那个（G5），`Z`+对面面键拿到近对面的那个（G6）。G5(9) + G6(9) = 18 = 3 轴 × 2 内层 × 3 变体，刚好覆盖全部单内层动作。**没有 `C` 前缀**（见 §5.3.2）。

**峰值按钮数核算（供 UI 排布参考，证明不需要折叠）**

| 阶数 | tab 组 | 各组按钮数 | 峰值单 tab 控件数 |
|---|---|---|---|
| 2 阶 | G1、视角 | 18 / 6 | 18 + 1 层选择器 = **19** |
| 3 阶 | G1、G2、G3 | 18 / 9 / 18 | 18 + 1 = **19** |
| 4 阶 | G1、G3、G4、G5、G6 | 18 / 18 / 18 / 9 / 9 | 18 + 1 = **19** |

三阶数峰值一致（均为 19），未突破既有布局容量，**因此 G4 与 G6 无折叠需要**。折叠反而会延长 AC-40 要求验证的"可点击路径"，是负优化。

**面键对照（唯一权威）**：`W`=U（上）、`X`=D（下）、`A`=L（左）、`D`=R（右）、`S`=F（前）、`Q`=B（后）。

**角标（kbd chip）规格建议**

| 形态 | 显示 | 视觉宽度 | 用在哪 |
|---|---|---|---|
| 单键 | `W` | 1 字符 | 6 个"顺时针"按钮上 |
| 单修饰 | `⇧`（8px）+ `W` | **约 2 字符** | 6 个"逆时针"按钮上。用 `⇧` 小号前置而非写出 `Shift+`，就是为了压进 2ch |
| 双击 | `W×2` | 3 字符 | **建议 180° 按钮不挂角标**，只在 §5.5 的常驻键位图和 `?` 浮层里出现。180° 是低频动作，挂上去会让 18 个按钮的角标宽度不齐 |
| 前缀型 | `Z·W` / `2·D` / `3·D` | 3 字符 | 仅出现在键位图与浮层，不挂在按钮上。**无 `C` 前缀**（§5.3.2） |

**记法字符串长度上限**

| 最长实例 | 长度 | 结论 |
|---|---|---|
| `3Rw'` / `3Rw2` | **5 字符** | 高于你给的"4 字符"假设 1 格。你日志列已按 `6ch` 排（`4ch/6ch/5ch/auto` 的第 2 列），5 字符可容纳，**列宽不需要改** |
| `2-3R2` / `2-3R'` | **5 字符** | 中间两层的区间记法（本平台扩展），同样落在 6ch 内 |
| `2L2` / `2R2` | 4 字符 | 无问题 |

若你希望严格守住 4 字符，唯一办法是给宽转改用 `3r`（`3r'`=4 字符）这类小写记法——但这会破坏"日志 / API `move` 字段 / 角标三者同一字符串"的一致性。**建议不改，走 6ch 列宽**。

**禁用键最终清单（合并双方约束）**

`Tab`、`Space`（除开始/暂停外不分配转动语义）、`Enter`（仅配置页）、`Esc`（仅关闭浮层）、`F1`–`F12`、`Ctrl`/`Cmd`/`Alt` + 任意、裸 `/`、`?` 单独占用、`←→↑↓` 单独占用给视角。

**明确不做**：不为右手分配任何转动键（右手全程留给鼠标拖拽视角与按钮点击）。这是"单手可操作"的兑现方式。

### 5.7 记法规范化契约（`describeMove`）

> **唯一原则：UI 与日志不得自行拼接记法字符串。** 所有展示字符串由引擎导出，UI 只做渲染。

**契约**

```
describeMove(axis, layerSet, amount) -> string
```

- `axis`：`x` | `y` | `z`（转轴，x 对应 R/L，y 对应 U/D，z 对应 F/B）
- `layerSet`：层索引集合，1 起，**必须是连续区间 `[a,b]` 且 `b-a+1 < N`**（排除整轴全层 = 整体旋转）。非连续子集（如 `{1,3}`）不在范围内——物理魔方上不存在这种同时转动，也没有还原算法会用到，且记法与日志无法序列化（见 §14.5 AC-40）
- `amount`：`90cw` | `90ccw` | `180`
- 返回：规范化 Singmaster 字符串

**命名规则（唯一）**：每个轴上的层区间，**用离它更近的那个外层字母命名**；当区间两端都不含外层时（只有中间层），用区间记法 `2-3X`。

**4 阶全量映射表（R/L 轴示例，U/D 与 F/B 轴同构）**

| 层集合 | 90° 顺 | 90° 逆 | 180° | 说明 |
|---|---|---|---|---|
| {1} | `R` | `R'` | `R2` | |
| {2} | `2R` | `2R'` | `2R2` | 靠近 R |
| {3} | `2L` | `2L'` | `2L2` | **靠近 L，故用 `2L`，而非 `3R`** |
| {4} | `L` | `L'` | `L2` | 即 L 面 |
| {1,2} | `Rw` | `Rw'` | `Rw2` | |
| {3,4} | `Lw` | `Lw'` | `Lw2` | |
| {1,2,3} | `3Rw` | `3Rw'` | `3Rw2` | |
| {2,3,4} | `3Lw` | `3Lw'` | `3Lw2` | |
| **{2,3}** | `2-3R` | `2-3R'` | `2-3R2` | **本平台扩展**（中间两层等距，固定用 X 侧字母） |
| {1,2,3,4} | — | — | — | 整体旋转，`applyMove` 拒绝（AC-66） |

**3 阶特例**：3 阶每轴仅 3 层，内层只有一个，且该层有公认的单字母 Singmaster 记法。因此 **3 阶的规范字符串直接用 `M` / `E` / `S` 族**（`M`/`M'`/`M2`、`E`/`E'`/`E2`、`S`/`S'`/`S2`），而 4 阶用 `2X` 族（`2R`/`2L`/`2U`/`2D`/`2F`/`2B`）。两者不会在同一次运行内混用，故无歧义。等价关系见 §5.3.3。

**UI 层的三条硬约束**

1. 按钮角标、日志 `move` 列、`?` 浮层里的记法，三者必须取同一个 `describeMove` 返回值。
2. 状态栏"将提交"预览也调 `describeMove`，不得由 UI 用前缀规则自行推断（因为前缀规则与命名规则在 4 阶上不一致，这正是最容易出两种写法的地方）。
3. 另一族记法（3 阶的 `2R`、4 阶的 `M'`）**只允许出现在状态栏括号里作为别名**，不得进日志列、不得进 API `move` 字段、不得作为角标。

**往返恒等（硬要求，AC-71）**

> `describeMove` 的输出**必须**能被记法解析器解析回原三元组：`parse(describeMove(axis, L, t)) === (axis, L, t)`。

这条不是形式主义。若某条记法"能显示但解析不回来"，日志里就会出现一条无法重放的指令，回放会**静默失败**——用户看到的是"回放停在第 37 步"，没有任何报错。这类缺陷的排查成本远高于在契约层加一条恒等断言。

因此：
- `describeMove` 的输出域必须严格落在 §5.1 记法语法的覆盖范围内；
- 引擎侧对 144 个三元组做穷举往返测试（AC-71），作为发布门禁；
- 任何新增记法（例如未来支持更高阶）必须先扩语法再扩 `describeMove`，不得只扩一头。

## 6. 难度分级定义

### 6.1 设计前提：为什么不能只用打乱步数

打乱步数（scramble length）衡量的是**题面被扰动了几次**，不是**求解难度**：
- 20 步打乱可能因操作抵消而等效于 6 步（`R R'` 白打）；
- 4 阶的 60 步打乱可能全部是外层转动，实际等价于一个 3 阶题面加未配对中心（反而更容易）；
- 反过来，一个 8 步打乱的 3 阶若含大量 D 面/双层结构，人类还原难度显著高于 20 步全 R/U 打乱。

因此难度由**四个正交维度**共同判定，打乱相关因子只占其中一个子权重。

### 6.2 四个判定维度

| 维度 | 代号 | 量化方式 |
|---|---|---|
| **规模** | `S` | 2 阶 = 1.0；3 阶 = 2.5；4 阶 = 4.0 |
| **题面结构复杂度** | `K` | `K = 0.8·dF + 1.2·pW + 0.5·(nE/10)`，其中 `dF` = 打乱序列覆盖的不同面数（1–6）、`pW` = 宽转/内层步在序列中的占比（0–1）、`nE` = 抵消化简后的净有效步数（上限 40）。**打乱步数只通过 `nE` 这一项间接进入，且权重最低** |
| **观察约束** | `O` | 完整观察 = 0；三面观察 = 1.0；单面观察 = 2.0；"操作后观察"叠加 +1.0；"受限观察"叠加 +1.0 |
| **时间/蒙尘约束** | `C` | 蒙尘开 +1.5；限时压力 `T = clamp( (估算最低步数 × 2.0 秒) / 时间限制秒数 , 0 , 2.0 )`（2 秒/步是新手节奏假设，用于把"时间够不够"折算为压力值） |

`difficulty_score = S + K + O + C`

### 6.3 等级判定表

| 等级 | 判定条件（全部满足） | 附加说明 |
|---|---|---|
| **入门** | `difficulty_score < 3.0` **且** `O = 0` **且** `C < 0.5` | 典型：2 阶 4–6 步打乱；3 阶净有效步数 ≤ 6 且只涉及 2–3 个面 |
| **常规** | `3.0 ≤ difficulty_score < 5.5` **且** `O ≤ 1.0` | 典型：3 阶标准 20 步随机打乱、完整观察、不限时 |
| **高难度** | `difficulty_score ≥ 5.5` **且** `O ≤ 2.0` | 典型：4 阶随机态；3 阶高净有效步数 + 宽转密集 |
| **指定结构** | 题面带 `structure_tag`（正交标签，不参与 `difficulty_score`） | 预置标签：`仅对面双转`、`十字已完成`、`F2L 缺一组`、`仅 R/L 面`、`中心已聚`（4 阶）、`棱已配对`（4 阶）。标签由运营者手动指定 |
| **长序列** | 打乱序列原始长度 ≥ 阈值（2 阶 ≥ 30 / 3 阶 ≥ 25 / 4 阶 ≥ 45）**且** `nE ≥ 0.6 × 原始长度`（即未被大量抵消） | 这一条单独存在，专门用于测"长上下文跟随能力"。**若净有效步数不达标，不允许打"长序列"标签** |
| **专项观察** | `O ≥ 1.0` | 与主等级并集存在（一个题可同时是"常规 + 专项观察"） |
| **限时** | `T ≥ 1.0` | 同上 |
| **蒙尘** | 蒙尘模式开启 | 同上 |

主等级（入门/常规/高难度）互斥取一；四个专项标签（指定结构 / 长序列 / 专项观察 / 限时 / 蒙尘）为正交并集。

### 6.4 题面合法性下限（与难度无关的硬门槛）

| 阶数 | 门槛 | 依据 |
|---|---|---|
| 2×2 | 最短解 ≥ 4 步 | 对齐 WCA 规则 4b3b 的下限精神，防止出现 1–3 步白给题 |
| 3×3 | 最短解 ≥ 2 步 | WCA 4b3 默认下限 |
| 4×4 | 最短解 ≥ 2 步 | 继承立方体类下限 |

> 无求解器时，`最短解` 用"净有效步数 ≥ 下限"作为代理判定，并在题目元信息中标记 `distance_is_estimated: true`。**这是已知的近似，必须对用户可见**，不得宣称这是真最短解距离（对应 Out-of-Scope 中的"自动难度分级"）。

### 6.5 打乱生成方式必须区分（继承原文，强化）

| 方式 | 定义 | 用途 | 元信息标记 | MVP 是否实现 |
|---|---|---|---|---|
| **随机操作** | 从已还原态施加 N 次随机合法操作 | 娱乐、操作手感测试 | `gen_mode: "random_moves"` | **是（v1 唯一实现）** |
| **随机状态** | 从合法状态空间等概率采样 | 标准化能力测试 | `gen_mode: "random_state"` | **否（v2 候选）** |

**硬性约束**：随机操作生成的状态**不得**标记为随机状态。UI 上必须用不同措辞区分（"随机题面"vs"随机打乱"），并在结果页脚注标明本次运行用的是哪种。混用会让跨运行的评测结论不可比。

#### v1 范围收窄（已由架构师裁决，本 PRD 据此降级）

> **v1 只实现「随机操作打乱」，不做均匀随机状态生成。**

原因与影响：

| 项 | 说明 |
|---|---|
| 为什么不做的技术原因 | 均匀随机状态生成需要对每个阶数实现"随机状态采样 + 求解器校验距离下限"。2 阶可做（状态空间小），**3 阶需两阶段算法、4 阶需降阶 + parity 处理**，属于独立工程且浏览器内耗时不控。这与 §4 Out-of-Scope 中"自动难度分级（需求解器）"是同一块能力的依赖 |
| PRD 相应降级 | `gen_mode: "random_state"` 保留在数据模型枚举中作为**预留值**，但 v1 的任何代码路径都不得产出该值 |
| 对评测结论的影响（必须写进结果页） | v1 的题面分布**不是**状态空间上的均匀分布，因此**不能**宣称"标准化能力测试"或用于跨平台能力对比。结果页在 `random_moves` 时必须显示："本次题面由随机操作生成，非均匀随机状态，不构成标准化难度基准。" |
| 何时升级到 v2 | 当出现"需要对外发布标准化题集"或"同一题面难度争议"时，且求解器已可用（F19） |

**因此**：§4 Out-of-Scope 里"自动难度分级"的"何时考虑"与本节绑定——两者应同期或在求解器落地后一并评估。v1 的难度标签一律是启发式估计，`distance_is_estimated` 恒为 `true`。

## 7. 计分与判定规则

### 7.1 HTM 计步细则

**定义（本平台口径，记作"本平台 HTM"）**：

> **一次提交的、绕单一轴线的、刚性层组的转动 = 1 步**，不论该次转动包含几层、转角是 90° 还是 180°。

| 情况 | 步数 | 说明 |
|---|---|---|
| `R` | 1 | |
| `R'` | 1 | |
| `R2` | 1 | 半转 1 步，这是 HTM 与 QTM（单转计步）的核心区别 |
| `Rw`（宽转 2 层） | **1** | 见下方结论 |
| `3Rw`（宽转 3 层） | **1** | 同上 |
| `2R`（单内层） | **1** | 原文明确要求"内层也各计 1 步" |
| `M` / `E` / `S` | **1** | |
| 视角旋转 | **0** | 不改变魔方状态 |
| `observe()` 调用 | **0** | 观察不是转动 |
| `submitSolution()` | **0** | |
| 被拒绝的非法操作 | **0** | 未改变状态，不计步也不计尝试 |

#### 结论：一次操作转动多层，仍计 1 步

**理由**：

1. **人体工学事实**：`Rw` 在物理魔方上是一次手指动作，和 `R` 的肌肉成本同阶。按层计步会让 4 阶的同一套解法在数字上被系统性放大 2–3 倍，制造"4 阶比 3 阶难 3 倍"的假象。
2. **跨阶可比性**：本平台的核心场景是**跨阶数、跨模型对比**。若计步口径随层数变化，4 阶的 60 步和 3 阶的 60 步就不是同一个量，对比表失去意义。
3. **与主流速拧直觉一致**：速拧社区说"这把 55 步"时，`Rw` 算一步。
4. **不损失信息**：见下方辅助字段。

**辅助字段（必须同时记录，保证可后验重算）**：

| 字段 | 含义 |
|---|---|
| `layer_count` | 本次转动涉及的层数（1 / 2 / 3） |
| `turn_amount` | 90 / 180 |
| `axis` | `x` / `y` / `z`（转轴） |
| `layer_set` | 具体层索引集合，如 `[1,2]` |

由此可派生 `HTM-layer` 口径（每层各计 1 步）与 `QTM` 口径（180° 计 2 步），在结果页作为"其他计步口径"折叠展示。默认展示与对比排序一律用本平台 HTM。

#### 口径与"限步 / 判定"的关系（必须写清，UI 需要据此设计标签）

| 场景 | 采用口径 | 是否可切换 |
|---|---|---|
| 挑战进行中的实时步数计数 | 本平台 HTM | **不可切换**。中途换口径会让"还剩多少步"这件事失去意义 |
| `move_limit` 限步判定 | 本平台 HTM | **不可切换**。判定标准必须在开始前锁定，否则同一 run 内可被口头重解释 |
| 结果页主指标 | 本平台 HTM | 不可切换 |
| 结果页"其他计步口径"折叠区 | `HTM-layer` / `QTM` | 可切换，**只影响该折叠区的展示与跨 run 对比表的排序**，不回写记录、不影响判定与胜负 |

**结论给 UI**：挑战中的步数标签是**固定口径**，不需要做成可选控件；但标签旁**必须**标注口径名（因为有 `R2` 算 1 步这种反直觉点）。结果页需要一处可切换的三口径展示区，用分段控件（Segmented）而非下拉，因为只有 3 个选项且需要并排对比。

#### 7.1.1 计步的三条公理（AC-21 / AC-61 / AC-70 的相容性说明）

这三条曾被误认为互斥，实际不互斥。先把公理写死：

| 公理 | 内容 |
|---|---|
| **G1** | `move_count` **等于事件数**。既不按层数累加，也不按角度除以 90 |
| **G2** | **一条已定稿的转动事件恒计 1 步**，无论它是 `R`、`R2`、`Rw`、`3Rw`、`2R`、`M`、还是归并产生的 `R2` |
| **G3** | **归并是输入整形，不是计步规则**。归并发生在事件定稿之前（§5.4.1），定稿之后一切照 `R2` 处理 |

**表面矛盾与解答**：

| 场景 | 表达出来的 move 序列 | 事件数 | `move_count` |
|---|---|---|---|
| 人类 300ms 内双击 `R` 键两次 | `['R2']`（整形后） | 1 | **1** |
| 人类点 `R2` 按钮 | `['R2']` | 1 | **1** |
| Agent 调 `applyMove('R2')` | `['R2']` | 1 | **1** |
| Agent 连调两次 `applyMove('R')` | `['R','R']` | 2 | **2** |
| 人类按 `R` 键两次但间隔 > 300ms | `['R','R']` | 2 | **2** |

**关键**：前三行的表达序列相同 → 计步相同；后两行表达的是两次独立转动（`R` 再 `R` 与 `R2` 是**不同意图**，尽管终态相同）→ 计步相同。**人机之间不存在不公平，因为比较基准是"表达出来的 move 序列"，不是"按了几个键"或"调了几次接口"。**

**禁止的做法**（会破坏上述一致性）：
- 按 `input_channel` 差异化处理（例如"键盘才合并、api 不合并"或反之）——见 AC-70；
- 在 `keydown` 时就 `move_count + 1`，之后再"抹掉"——见 §5.4.1 约束 2；
- 把 `move_count` 定义为 `Σ layer_count` 或 `Σ (turn_amount/90)`——见公理 G1。

**为什么这条重要**：`move_count` 会进 `Run.metrics`、进结果页排序、进跨阶对比表。口径一旦漂移，所有历史记录就不可比，且**不可逆**。这是全篇最不能"随手实现"的一条。

### 7.2 计时口径

| 指标 | 定义 | 备注 |
|---|---|---|
| `elapsed_ms` | `running` 开始到结束的单调时钟差 | 用单调时钟，避免系统时间调整干扰 |
| `agent_think_ms` | 相邻两次交互之间的间隔（观察返回 → 下次操作提交） | 外部 Agent 的模型推理时间无法直接测量，此项即"端到端等待时间" |
| `api_call_ms` | 每次 API 调用的本地处理耗时 | 纯前端下通常 < 1ms，主要价值是排查卡顿 |
| `first_move_ms` | 开始 → 第一步操作 | 用于分析"读题"成本 |
| `submit_ms` | 开始 → `submitSolution()` | 无提交时为 `null` |

**诚实边界**：纯前端计时无法防篡改（用户可暂停调试器、改内存）。所有计时结果必须在结果页标注"本机测量，未经服务端校验"。**不得用于对外成绩背书**。

#### 7.2.1 暂停（`paused`）的计时细则 —— "计时不暂停"

> 已由团队主理人裁决：**保留暂停按钮，但暂停只屏蔽输入，不停止计时。** 这是本 PRD 唯一一种"用户以为停了、系统没停"的设计，必须写死，避免实现时被"顺手做成真暂停"。

| 规则 | 内容 |
|---|---|
| P1 | 暂停**只**屏蔽输入与观察。`elapsed_ms` 在 `paused` 期间**继续累加**，不使用"累计活跃时长" |
| P2 | 超时判定在 `paused` 期间**继续生效**。主循环 tick（每 200ms）与 `applyMove` 入口、`observe` 入口的检查在 `paused` 下同样执行 |
| P3 | 限时模式下，若超时发生在 `paused` 期间，判定为 `result: "timeout"`（同样判负），且 `result_detail` **必须**标注"超时发生于暂停中"，结果页结论区**必须**原样显示这句话 |
| P4 | `paused` 期间 `observe()`、`applyMove()`、`submitSolution()`、`rotateView()` 一律返回 `{ok:false, error_code:"PAUSED"}`，不改变状态、不计步 |
| P5 | 暂停**仅人类模式可用**。`window.cubeAgent` **不提供** pause/resume 方法；Agent 模式下界面上不渲染暂停按钮 |
| P6 | 暂停次数不设上限，但每次暂停/恢复都记入事件流（`pause` / `resume` 事件，含时间戳），供回放与审计 |
| P7 | 暂停期间 3D 场景冻结在暂停前最后一帧（不渲染新动画），但**倒计时数字继续跳动**，作为"时间在跑"的可见信号 |

**为什么不做真暂停（这段必须与 §8 一起读）**

真暂停等于给人类玩家**无限思考时间**：暂停 → 慢慢看题面 → 想好整条解法 → 恢复 → 快速执行。这会直接摧毁三样东西：

1. **人机可比性**：Agent 没有"暂停慢慢想"的等价能力（它的每一次 `observe` 都实时计费到 `agent_think_ms` 里）。若人类可停表，两边就不是同一场比赛。这是本平台唯一的核心价值，不能破。
2. **限时模式的意义**：限时的设计目的是"在时间压力下做决策"，可停表的限时等于不限时。
3. **跨运行对比**：`elapsed_ms` 若混入"活跃时长"语义，历史运行之间的时间就不可比，多轮实验对比表（F13）整张失效。

**与 §8 蒙尘边界的关系**：两者是同一类诚实性问题——蒙尘承认"用户能看源码"，暂停承认"用户能停表但时间照跑"。**都不假装解决了做不到的事**，而是把真实规则写清楚、并在 UI 上明示。结果页在发生过暂停的运行上，**必须**额外显示一行："本次运行包含 `N` 次暂停（共 `M` 秒），计时未暂停。"

### 7.3 终止判定

判定顺序固定为：**先判还原 → 再判超时 → 再判步数耗尽 → 再判放弃**。顺序不可改，因为它决定了"最后一步刚好还原且刚好超时"的归属。

| 判定 | 触发条件 | 结果状态 | 后续行为 |
|---|---|---|---|
| **还原成功** | 每次 `applyMove` 执行后、以及 `submitSolution` 时，检查 §7.4 的还原条件成立 | `finished` / `result: "solved"` | 立即终止，记录 `solved_at_move` |
| **超时** | `elapsed_ms > time_limit_ms`。检查点：每次 `applyMove` 入口、`observe` 入口、主循环每 200ms tick（**`paused` 期间同样检查**，见 §7.2.1 P2） | `finished` / `result: "timeout"` | 终止；进行中的动画播放完毕后定格；`applyMove` 此后返回 `409 TIMEOUT`。若超时发生在 `paused` 中，`result_detail` 必须为"超时发生于暂停中" |
| **步数耗尽** | 已提交步数 `= move_limit` 且提交后状态未还原 | `finished` / `result: "move_limit"` | 第 `move_limit` 步仍允许执行（可能正好还原，此时按"还原成功"结算）；第 `move_limit + 1` 步提交返回 `409 MOVE_LIMIT` |
| **主动放弃** | 人类点"放弃"并确认；或 Agent 调 `abandonChallenge(reason)` | `finished` / `result: "aborted"` | 终止，保留已有记录 |
| **提交校验连续失败** | `submitSolution()` 且未还原，累计 3 次 | `finished` / `result: "invalid_submission"` | 第 1、2 次失败**不终止**（防止误判终止一次有效尝试），返回 `{accepted:false, reason}` 让用户继续；第 3 次终止 |
| **页面关闭/刷新** | `beforeunload` 且状态为 `running` **或 `paused`** | 该运行标记 `result: "interrupted"` | 尽力写入 localStorage（含已知事件）；重进时提示"有一次未完成的运行" |

### 7.4 还原判定标准（2/3/4 阶差异）

#### 总原则

> **已还原 ⟺ 存在某个整体朝向 `o`，使 6 个面各自单色，且该朝向下"颜色 → 面"的映射属于标准配色方案的 24 个合法旋转之一。**

为什么需要朝向归一化：玩家/Agent 完全可能在还原后改变观察方向（通过视角操作，不是通过 `applyMove`，见 §5.3.4），4 阶还可能在还原过程中自然地换过握持方向。物理上已还原，但"哪一面朝上"不唯一。若判定绑定固定朝向，会把合法还原判为失败。

#### 各阶差异

| 阶数 | 判定实现 | 关键差异 | 为什么 |
|---|---|---|---|
| **2×2** | 24 种朝向归一化后检查 6 面各单色 | **无中心块、无棱块**，仅 8 个角块。单色 6 面 ⟺ 还原 | 2 阶没有任何"锚点"能固定朝向，只能靠归一化 |
| **3×3** | 同样 24 朝向归一化后检查 6 面各单色（实践中可简化为直接检查 6 面单色，见右） | **中心块相对彼此固定**，因此"6 面单色"本身已蕴含"配色正确"——中心块无法被单独移动，若 6 面单色则必然是合法配色 | 3 阶的 24 种整体旋转只是把"白上绿前"转成别的朝向，不改变"每面单色"这一事实。所以 3 阶可以跳过枚举，直接判 6 面单色 |
| **4×4** | **必须做 24 朝向枚举 + 配色合法性校验** | **中心块可动、无固定朝向**：① 4 个中心块同色时互相不可区分，不能用"中心块朝向"定义还原；② 6 面单色是**必要但不充分**条件——理论上可能存在"6 面单色但中心块排列为镜像配色"的非法陈列（由物理拆装造成，合法转动无法达成）；③ 存在 OLL/PLL parity，但若 6 面单色则 parity 必然已消解，无需单独检测 | 这是三阶中唯一需要显式枚举 24 种朝向 + 校验配色映射的阶数 |

#### 4 阶的实现要点（供架构师参考，非技术选型）

1. 提取每面 `N/2 × N/2` 中心区域的实际颜色（4 阶为 2×2 = 4 块，需 4 块同色才算该面"单色"）。
2. 若 6 面全单色 → 得到"面 → 颜色"映射 `M`。
3. 枚举标准配色 `S` 的 24 个整旋转，若任一旋转 `S_o` 满足 `M = S_o` → 已还原。
4. 若无匹配 → 未还原（**注意**：此时 UI 不应报"颜色错误"，因为在真实流程中不可能出现，只可能出现在"导入非法状态"路径，应报 `INVALID_STATE`）。

#### 判定时机

| 时机 | 是否判定 | 说明 |
|---|---|---|
| 每次 `applyMove` 成功后 | 是 | 用于即时反馈（3D 场景可播一次"已还原"高亮，但不自动结束——见下） |
| `submitSolution()` | 是 | 唯一正式结算点 |
| 达到步数上限时 | 是 | 先判还原，再判耗尽 |

**关于"自动结束"**：`applyMove` 后检测到已还原**不自动终止挑战**，只在 3D 上给出视觉提示，并把状态置为"可提交"。理由：人类玩家可能在还原后继续做整体旋转演示；Agent 可能想再确认一次观察。是否自动提交由用户在配置里选择（默认：人类模式自动提交，Agent 模式不自动，须显式 `submitSolution`）。

## 8. 蒙尘模式的诚实边界

> 这一章是本文档最重要的"不吹牛"章节。原文第 7.3 节写的"所有观察限制均由服务端强制执行。前端隐藏元素不构成权限控制"在本产品**不成立**，因为本产品没有服务端。必须改写为用户可见的诚实表述。

### 8.1 蒙尘模式想解决的问题

在"开始"之前，人和 Agent 都不应该看到题面。这不是纯技术问题——绝大多数场景下，它要防的是**无意的提前看见**（切标签页回来看到颜色、截图时泄露、Agent 在初始化阶段顺手套取状态），而不是**有意的逆向工程**。

### 8.2 能做到什么（有明确机制，可验证）

| # | 机制 | 可验证方式（对应 §14 的 AC 编号） |
|---|---|---|
| C1 | **API 层门控**：`ready` / `configuring` / `idle` 状态下，`observe()` 返回 `{ok:false, error_code:"NOT_STARTED", status}`，响应体中**不含** `face_colors`、`state_snapshot`、`state_fingerprint`、`move_count`、`scramble`、`seed` 等任何可推导颜色的字段 | **AC-14**：在 `ready` 态遍历 `observe()` 返回值 JSON，断言不含上述键名且序列化后不出现颜色字符串 |
| C2 | **视觉遮蔽**：`ready` 态 3D 场景使用统一遮蔽材质（单色平光 unlit、无贴纸色差、无光照差异），且**不渲染**任何带颜色的贴纸网格 | **AC-16**：确定性探针判定（见下方"为什么不用颜色种类数"） |
| C3 | **数据隔离**：题面快照、seed、打乱序列在挑战结束前**不写入 `localStorage`**，不由 `window` 直接可达的对象持有；`window.cubeAgent` 只暴露方法，不暴露引擎实例引用 | **AC-15**（`localStorage` 中不存在题面字段）+ **AC-41**（遍历 `window.cubeAgent` 自有属性，断言全为函数、无对象型属性可回溯到引擎状态） |
| C4 | **接口最小化**：不提供 `getDebugState()` / `getSolution()` / `getScramble()` 一类的诊断接口；`getChallengeInfo()` 在 `ready` 态对 `seed` / `scramble` 字段返回 `null` | **AC-64** |
| C5 | **UI 显式声明**：`ready` 态在遮蔽体下方常驻一行说明文案（非弹窗）："开始前不显示题面。本模式用于防止误看，不能阻止通过开发者工具读取内存。" | **AC-17**：断言该文案在 `ready` 态存在 |
| C6 | **观察模式执行**：`running` 态下按 `observation_mode` 裁剪返回字段（三面观察只返回当前朝向下的 3 个面；单面观察只返回 1 个面），裁剪发生在 API 层而非渲染层 | **AC-19**（单面观察恰好 1 个面）+ **AC-20**（三面观察在 `rotateView` 后返回新朝向的 3 个面）+ **AC-65**（裁剪发生在 API 层：直接序列化 `observe()` 返回值断言未授权面缺失） |

> **注**：本表曾误引 AC-21~AC-26（那是计步与还原判定的编号），已在 v1.2 修正。C1–C6 与 AC 的对应关系以本表为准。

#### 为什么蒙尘像素用"确定性探针"而不是"颜色种类数"（AC-16 的口径说明）

原写法是"画布中除背景色外的颜色种类数 ≤ 2"。这条**在开启抗锯齿后永远通不过**：MSAA 会在几何边缘生成过渡色，边缘像素数量与几何复杂度、像素比、相机角度都相关，必然超过 2 种。

考虑过的两种收窄方案，都不成立：

| 方案 | 为什么不成立 |
|---|---|
| 只统计中心 80% 区域 | 魔方轮廓的边缘仍然落在中心区内；而且"80%"是把判定绑在布局比例上，窗口尺寸一变就漂 |
| 允许颜色数 ≤ N（放宽 N） | N 取多少都是拍脑袋；6 面颜色本身就有 6 种，放宽到 6 就失去判定意义 |

**改为确定性探针判定（AC-16 正式口径）**：

1. 按相机矩阵在屏幕空间计算固定探针点：**每个可见面的中心 1 点 + 每面 4 个内缩点**（内缩比例取该面投影包围盒的 25%，落在面内部，避开边缘过渡带）。
2. 断言条件一：所有探针像素与遮蔽色 `--cube-masked` 的色差 **ΔE ≤ 2**（证明"全身都是遮蔽色"）。
3. 断言条件二：任一探针像素与 6 个贴纸色中任一个的色差 **ΔE ≥ 20**（证明"没有一丝贴纸色透出来"）。

**为什么这样更对**：我们真正在意的是"魔方表面有没有出现贴纸颜色"，而不是"整幅画面恰好只有两种 RGB"。探针法直接测前者，且结果与分辨率、抗锯齿等级、背景复杂度无关。

**该判定对 2D 降级视图同样适用**（§12.2 第 5 条）：2D 展开图模式改用 6 个网格的面中心点作为探针点，判定条件相同。这样"蒙尘"在两条渲染路径上有一致的、可自动化的验收标准。

**遮蔽态不加轮廓线（单色剪影）**：遮蔽材质必须是**不受光的纯色**，且**不得**添加轮廓线、倒角、贴纸缝隙、体积感或噪点。理由不是"省事"，而是：**轮廓线和贴纸缝隙会泄露"缝在哪"，而"缝在哪"就等于泄露块的大小**——这在 `ready` 态属于题面信息。**看不见就别暗示。** 若未来确需在遮蔽态保留轮廓暗示，则必须把第三种轮廓色的 ΔE 与全部 6 个贴纸色拉开 ≥20，并同步放宽 AC-16 判定；当前不做。

**遮蔽材质必须关闭色调映射（`NoToneMapping`）**：AC-16 断言的是"探针像素与 `--cube-masked` 的 ΔE ≤ 2"，这是**对最终像素值**的断言。若渲染管线启用了 ACES / Reinhard 等色调映射，`--cube-masked` 会被映射成另一个颜色，断言必然失败——而且失败原因极难归因（看起来是"遮蔽色不对"，实际是"管线把颜色改了"）。因此遮蔽态与 `running` 态的色彩管线必须**分别明确**：遮蔽态 `NoToneMapping`，`running` 态可按视觉需要选择。

**遮蔽色是被测指标，不是主观配色**：`--cube-masked` 的取值受 AC-16 条件二约束（与 6 个贴纸色的 ΔE 均 ≥20），因此它**不能**作为"配色微调"随意改动。改动前必须重跑 6 色 ΔE 实测。

> **实测提示（来自设计的真实数据，供后续调色参考）**：最危险的一对**不是**"冷灰遮蔽色 vs 白色贴纸"，而是"**蓝调遮蔽色 vs 蓝色贴纸**"——因为深色竞技风的遮蔽色天然会带一点冷蓝，而六色里正好有一个蓝。当前 `#2B323C` 与蓝贴纸的 ΔE 为 63.85（六色中最低，仍是阈值 20 的 3.2 倍）。若有人想把遮蔽色调成"更深更蓝"，**第一个要测的就是它和蓝色贴纸的距离**。

### 8.3 做不到什么（必须写明，不得含糊）

| # | 做不到的事 | 为什么 |
|---|---|---|
| N1 | 阻止用户阅读打包后的 JS 源码、搜索状态数组、在 DevTools 里设断点拦截引擎方法 | 代码在用户机器上执行，没有任何隔离边界 |
| N2 | 阻止用户覆盖 `window.cubeAgent` 的实现，或 hook `Object.defineProperty` / `JSON.stringify` / `Math.random` 后再调用 | 同上；所有"防护"本身也是可被覆盖的 JS |
| N3 | 阻止用户在启动前修改 `localStorage` 里上次运行的数据来伪造结果 | 同上 |
| N4 | 阻止用户暂停调试器来延长 `elapsed_ms`，或直接把状态数组改成已还原 | 计时与状态都在前端 |
| N5 | 保证"Agent 没有在 `ready` 态通过非常规手段拿到题面" | 只要 Agent 运行在同一个浏览器上下文里，它就有和用户同等的内存访问权限 |

### 8.4 边界结论（用于对外表述）

> **蒙尘模式是"防误看"，不是"防逆向"。**
> 它能保证：正常使用路径下，开始前不泄露题面；API 不会主动交出颜色；界面上看不到颜色。
> 它不能保证：有动机、有 JS 能力的人拿不到题面。
> 因此：**本平台任何一次运行的结果，在蒙尘场景下都不构成"模型能力"的强证据**，只能作为内部迭代的参考信号。需要可对外背书的评测结论时，必须把状态与判定搬到服务端。

这段结论应同时出现在：① 本 PRD；② 结果页脚注（蒙尘运行时）；③ 配置页蒙尘开关旁的说明文案。

### 8.5 同一类诚实性：暂停不做真暂停（与 §7.2.1 配套）

蒙尘与暂停是**同一类问题的两个面**，处理口径必须一致：

| 维度 | 蒙尘 | 暂停 |
|---|---|---|
| 用户直觉期待 | "开始前我什么都看不到" | "点了暂停时间就该停" |
| 实际能给的 | 不主动泄露 + 视觉遮蔽 + API 门控 | 只屏蔽输入，**时间照跑** |
| 为什么不给足 | 给了也守不住（代码在用户机器上） | 给了就摧毁人机可比性（Agent 没有等价能力） |
| UI 必须明示的 | "不能阻止通过开发者工具读取内存" | "计时未暂停"（`PAUSED` 错误文案 + 结果页暂停摘要） |
| 对外可宣称 | 只防误看 | 只防误触 |

**共同原则**：凡是"用户以为做到了、但系统做不到"的地方，**必须在 UI 上明说**，而不是让用户自己发现。这两处都不做假承诺。

### 8.6 受限观察下屏蔽状态指纹（有意设计，不是漏实现）

#### 问题

`applyMove` 的返回值里有一个 `state_fingerprint_after`（AC-42）。它原本用于回放对账与调试。但在**受限观察**下，它会变成一条**完整的**信息泄露通道：

| 阶数 | 状态空间规模 | 指纹反推成本 |
|---|---|---|
| 2×2 | 约 3.67 × 10⁶ | **秒级可枚举建表**，拿到指纹即可查出全部 6 面颜色 |
| 3×3 | 约 4.3 × 10¹⁹ | 不可枚举，指纹基本安全 |
| 4×4 | 约 7.4 × 10⁴⁵ | 不可枚举，指纹基本安全 |

也就是说：在 **2 阶 + 受限观察** 的组合下，Agent 只要走一步并读指纹，就能反推出全部隐藏面——**按规矩调用 API 就能拿到答案**。

这与 §8.3 的诚实边界是两件事：§8.3 说的是"用户能看源码"，那是需要动手逆向的；而这里是"照文档调用接口就行"，性质更重。

#### 裁决

> **`observation_mode !== 'full'` 时，`state_fingerprint_after` 必须返回 `null`。**

| 场景 | `state_fingerprint_after` |
|---|---|
| `observation_mode === 'full'` | 返回真实指纹（覆盖绝大多数场景，AC-42 在此模式下完整成立） |
| `observation_mode` ∈ {`three_face`, `one_face`, `after_move`, `restricted`} | **`null`** |
| 挑战结束后调 `getChallengeResult()` | 正常返回最终指纹——此时已无隐藏信息可泄露 |
| `Run.events[].state_fingerprint_after`（本地记录） | 正常记录——它是本机数据，不通过 API 交出 |

#### 为什么选"屏蔽"而不是"保留 + 加一句免责说明"

架构师曾建议保留并补一句"2 阶受限观察不构成有效信息约束"，我否决了。理由：

1. **受限观察的全部意义就是限制信息**。返回一个本地可枚举反推的哈希，与直接返回状态没有区别——只是把作弊成本从 0 秒抬到 10 秒。
2. **产品已经在 §8.4 明说"蒙尘不构成安全边界"**，就更不该在 API 里再造一个假的安全感。留一个"看起来是哈希、其实是明文"的字段，比没有这个字段更危险：它会让使用者**误以为**受限观察有效。
3. 屏蔽的成本很低：`full` 模式照常返回（覆盖绝大多数场景），回放对账改用一个数据源（挑战结束后的 `getChallengeResult`）。

#### 连带影响（必须一起实现）

| 影响 | 处理 |
|---|---|
| AC-42 在受限模式下 `state_fingerprint_after` 为 `null` | 已在 AC-42 写明；**键必须存在**，值为 `null`，不得省略键（省略会让调用方无法区分"不支持"与"为空"） |
| 回放对账 | 改用 `Run.events[].state_fingerprint_after`（本地记录）+ 结束时的 `getChallengeResult()` 最终指纹，两者结合足以对账 |
| 用户困惑 | 结果页不显示，只在 `?` 浮层与 API 文档中说明"受限观察下不返回指纹" |

**这是有意屏蔽，不是漏实现。** 后续若有人提"这里应该返回指纹"，请先读本节。

## 10. 过程回放（补全原文缺失章节）

### 10.1 回放的数据基础

回放不重跑逻辑，只重放事件流。每个运行记录保存：

- 题面快照（初始状态，或可重建初始状态的 seed + gen_mode + 算法版本）；
- 事件流（有序数组，每个转动事件含指令、层集合、转角、时间戳、操作后的状态指纹）；
- 观察事件（`observation_id`、观察模式、返回的面集合——**不保存完整颜色数据**，需要时由回放引擎在对应帧重建）。

### 10.2 回放界面

| 控件 | 行为 |
|---|---|
| 播放 / 暂停 | 按事件时间戳等比压缩播放（默认把总时长压到 20–40 秒，可调速度 0.5× / 1× / 2× / 4×） |
| 上一步 / 下一步 | 单步前进/后退，每步执行一次逆操作或正操作 |
| 进度条 | 可拖拽跳转到任意步；跳转通过从最近关键帧快进实现 |
| 时间轴刻度 | 显示每步的时间戳与累计步数 |
| 视角 | 回放期间可自由拖拽视角；视角变化不写入记录 |
| 操作日志联动 | 当前步在日志中高亮滚动到可视区 |
| 显示开关 | `显示步数`、`显示时间`、`显示观察发生点`（观察点用竖线标在时间轴上） |

### 10.3 回放的三种视角模式

| 模式 | 说明 |
|---|---|
| **上帝视角** | 全开颜色，看完整过程。默认 |
| **观察者视角** | 按该次运行的 `observation_mode` 重现"Agent 当时能看到什么"。这是回放最有价值的模式——能直观看出"Agent 在单面观察下做了多少盲猜" |
| **校验视角** | 每步显示操作前后 6 面颜色矩阵的差异高亮，用于人工核验引擎正确性 |

### 10.4 回放的边界

- 回放不修改任何原始记录；在回放中做操作只影响视图，不产生新事件。
- 若记录的 `engine_version` 与当前不一致，回放页顶部提示"本次运行由旧版引擎生成，回放结果可能与当时不完全一致"，并提供"仍要回放"确认。不静默播放。
- 单次运行事件数上限：默认 2000 条（2 阶/3 阶远超需求，4 阶也够）。超过时只保存前 2000 条 + 最终状态，并标注"记录已截断"。

### 11.1 数据埋点方案

MVP 必须埋点的事件（不埋等于上线后无法验证任何假设）。纯前端方案，事件先入内存队列，随运行记录一起落 localStorage；不发送到任何远端。

| 事件类别 | 事件名 | 触发时机 | 关键属性 |
|---|---|---|---|
| 获客 | `page_view` | 首次加载完成 | `referrer_type`（直接/外链/无）、`device`、`version` |
| 获客 | `challenge_config_submitted` | 点"创建挑战"且校验通过 | `cube_size`、`gen_mode`、`time_limit_ms`、`move_limit`、`dust_mode`、`observation_mode` |
| 激活 | `challenge_started` | 状态进入 `running` | `challenge_id`、`from_state`（配置停留时长） |
| 激活 | `first_move_made` | 首次有效操作 | `time_to_first_move_ms`、`input_channel`（keyboard/button/api） |
| 活跃 | `move_made` | 每次有效操作 | `move`、`layer_count`、`turn_amount`、`input_channel`、`step_index` |
| 活跃 | `view_rotated` | 视角变化（节流 500ms） | `axis`、`method`（drag/key/button） |
| 活跃 | `challenge_paused` / `challenge_resumed` | 暂停 / 继续（仅人类） | `pause_index`、`elapsed_ms_at_pause`、`paused_duration_ms`（resume 时回填） |
| 活跃 | `move_merged_to_half_turn` | 双击归并触发 | `face`、`merged_from`、`window_ms`（两次按键间隔） |
| 留存 | `session_start` / `session_end` | 页面可见性变化 | `duration_ms`、`challenges_in_session` |
| 留存 | `run_again_clicked` | 点"再挑战一次"或"同题面重跑" | `same_challenge`（bool） |
| 转化 | `replay_opened` | 打开回放 | `challenge_id`、`result` |
| 转化 | `export_clicked` | 点导出 JSON | `challenge_id` |
| 异常 | `illegal_move_rejected` | 引擎拒绝非法操作 | `raw_input`、`error_code` |
| 异常 | `api_error` | 任何 API 返回 `ok:false` | `method`、`error_code` |
| 异常 | `render_stall` | 帧间隔 > 100ms 连续 3 帧 | `cube_size`、`fps` |
| 异常 | `storage_unavailable` | localStorage 读写失败 | `reason`（quota/blocked） |

**埋点规范**：
- 命名：`{对象}_{动作}`，过去式（`move_made` 而非 `make_move`）。
- 公共属性：`session_id`、`client_time`、`version`、`device_class`、`cube_size`。
- **不采集**：IP、原始输入内容（只采集规范化后的指令）、任何可识别个人的信息。不做设备指纹。
- 埋点开关：配置页提供"本地使用统计（仅存本机，不外发）"开关，默认开；关闭后仍保留自用回放所需的最小事件，但不写埋点字段。

## 12. 错误处理（补全原文缺失章节）

### 12.1 错误码表

> **命名口径**：本表使用无前缀短名，便于在 PRD 与 AC 中引用。架构师的 API 规范中统一加 `E_` 前缀（如 `E_INVALID_MOVE`、`E_PAUSED`），**两者指同一码**，实现以架构师命名为准。唯一例外是 `ORIENTATION_NOT_MOVABLE`，其对外标识在架构师裁决中即为 `E_NOTATION_ORIENTATION_NOT_MOVABLE`，本表原样保留该全名作为别名。

| 码 | 语义 | 触发场景 | 用户/Agent 可见文案 |
|---|---|---|---|
| `NOT_STARTED` | 尚未开始 | `ready` 态调用 `observe` / `applyMove` | "挑战尚未开始，无法观察或操作。" |
| `ALREADY_FINISHED` | 已结束 | `finished` 态调用 `applyMove` | "挑战已结束。" |
| `TIMEOUT` | 已超时 | 超时后任何写操作 | "已超过时间限制。" |
| `MOVE_LIMIT` | 步数耗尽 | 超出步数上限 | "已达步数上限。" |
| `INVALID_MOVE` | 非法指令 | 记法解析失败（如 `R3`、`X`、空串） | "无法识别的操作：`{raw}`。" |
| `INVALID_LAYER` | 非法层 | 层索引超出该阶数范围（如 2 阶请求 3 层） | "当前阶数不支持该层操作。" |
| `ORIENTATION_NOT_MOVABLE` | 整体旋转不是转动 | `applyMove('x')` / `'y2'` 等任何整体旋转记法 | "整体旋转是观察操作，请使用视角旋转。"<br>架构师 API 规范中的对外标识：`E_NOTATION_ORIENTATION_NOT_MOVABLE` |
| `OBSERVATION_DENIED` | 观察被拒 | 请求的面不在当前观察规则允许范围内 | "当前观察模式不允许观察该面。" |
| `INVALID_STATE` | 状态非法 | 导入的题面不合法/不可还原 | "该题面无法还原，请检查配色与块位。" |
| `NOT_SOLVED` | 提交时未还原 | `submitSolution` | "魔方尚未还原。" |
| `PAUSED` | 挑战已暂停 | `paused` 态下调用 `observe` / `applyMove` / `rotateView` / `submitSolution` | "挑战已暂停。计时仍在进行。"（后半句必须出现，见 §7.2.1） |
| `RATE_LIMITED` | 调用过频 | 单帧内 API 调用 > 60 次 | "调用过于频繁，请降低频率。"（防 Agent 死循环打爆主线程） |
| `STORAGE_FULL` | 存储已满 | localStorage 配额不足 | "本机存储已满，本次结果未保存。" |
| `INTERNAL` | 内部错误 | 引擎抛出未预期异常 | "内部错误，本次运行已终止。"+ 允许导出诊断包 |

### 12.2 错误处理原则

1. **非法操作绝不改变状态**：所有校验在状态变更之前完成（对应 AC-08）。
2. **错误不静默**：任何 `ok:false` 都在右栏日志留痕，并计入 `api_error` 埋点。
3. **不因误判终止**：`NOT_SOLVED` 与 `INVALID_MOVE` 不终止挑战（连续 3 次 `NOT_SOLVED` 除外）。
4. **错误文案不指责用户**：不用"你的操作有误"，用"无法识别的操作：`X`"。
5. **渲染异常降级**：若 WebGL 初始化失败，进入"2D 展开图模式"——用 6 个网格展示状态，键盘与按钮操作照常可用，计时与判定不受影响。这是唯一的功能降级路径，必须实现，因为它是"无 WebGL 环境仍可完成评测"的兜底。

## 13. 数据模型（补全原文缺失章节）

### 13.1 题面（`Challenge`）

> **可复现四件套（缺一即不可逆降级）**：`scramble` + `gen_version`（算法版本）+ `notation_version`（记法版本）+ `state_fingerprint`（初始状态指纹）。这四样必须在**第一版就存全**——当时没存，历史记录就永久变成"无法验证的静态数字"，且无法事后补。

| 字段 | 类型 | 说明 |
|---|---|---|
| `challenge_id` | string | 唯一 ID |
| `cube_size` | 2 \| 3 \| 4 | 阶数 |
| `gen_mode` | `random_moves` \| `imported`（v1）；`random_state` 为 v2 预留值，v1 不得产出 | 生成方式（必须区分，见 §6.5） |
| `seed` | string \| null | 随机种子；`imported` 时为 `null` |
| `scramble` | string \| null | 打乱序列（Singmaster）；`imported` 时可为 `null`（改用 `facelet_string`） |
| `facelet_string` | string \| null | **v1 唯一的状态载体**：把每个面按行展开拼接的 facelet 串（`imported` 必填；`random_moves` 可由 `scramble` 重放推出，用于校验） |
| `state_fingerprint` | string | `facelet_string` 的 **FNV-1a** 哈希（不引入 crypto 依赖），前 8 位用于 UI 展示与"同题面"比对 |
| `state_snapshot` | — | **v1 不存**。已由架构师裁决（§16.2 Q2 关闭）：**不存打乱后的状态快照，改为"重放打乱序列 + 指纹校验"**。载入时重放 `scramble` 得到状态，再用 `state_fingerprint` 校验一致；不一致即报 `INVALID_STATE` 并拒绝进入 `ready` |
| `distance_is_estimated` | boolean | 最短解距离是否为估计值（本版恒为 `true`） |
| `estimated_distance` | number | 净有效步数作为代理值 |
| `difficulty_score` | number | §6.2 公式结果 |
| `difficulty_level` | `beginner` \| `standard` \| `hard` | 主等级 |
| `difficulty_tags` | string[] | `structure` / `long_sequence` / `observation` / `timed` / `dust` 等正交标签 |
| `structure_tag` | string \| null | 指定结构标签 |
| `gen_version` | string | 题目生成算法版本。**与 `notation_version`、`state_fingerprint`、`scramble` 四者共同构成可复现的最小信息集**，缺任一项历史记录即降级为不可验证的静态数字 |
| `notation_version` | string | **记法版本**。记法与 `describeMove` 的语义一旦变更（如新增阶数、调整命名规则），必须升版本号；载入旧题面时据此判断能否精确重放 |
| `created_at` | number | 时间戳 |

### 13.2 挑战配置（`RunConfig`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `participant` | `human` \| `agent` | |
| `time_limit_ms` | number \| null | `null` = 不限时 |
| `move_limit` | number \| null | `null` = 不限步 |
| `dust_mode` | boolean | |
| `observation_mode` | `full` \| `three_face` \| `one_face` \| `after_move` \| `restricted` | |
| `observation_limit` | number \| null | `restricted` 模式下的观察次数上限 |
| `double_tap_merge` | boolean | 180° 双击归并开关 |
| `auto_submit_on_solved` | boolean | 人类模式默认 `true`，Agent 模式默认 `false` |
| `animation_ms` | number | 转动动画时长，60–300 |

### 13.3 运行（`Run`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `run_id` | string | 唯一 ID |
| `challenge` | `Challenge` | 题面元信息（含快照） |
| `config` | `RunConfig` | |
| `agent_meta` | object \| null | `{name, version, prompt_version, tool_version, note}`，由 Agent 运行时的用户填写 |
| `started_at` / `ended_at` | number | 单调时钟基准 + 墙钟 |
| `result` | `solved` \| `timeout` \| `move_limit` \| `aborted` \| `invalid_submission` \| `interrupted` | |
| `result_detail` | string | 人可读原因。超时发生于暂停时必须为"超时发生于暂停中" |
| `metrics` | object | §7.2 全部计时指标 + `move_count` + `htm_layer_count` + `qtm_count` + `pause_count` + `paused_total_ms` |
| `events` | `(MoveEvent \| SessionEvent)[]` | 见 13.4；`SessionEvent` 为 `pause` / `resume` 事件，含 `at_ms` |
| `observations` | `ObservationEvent[]` | 见 13.5 |
| `truncated` | boolean | 事件是否被截断 |
| `engine_version` | string | 用于回放兼容性判断 |
| `device_class` | string | `desktop` / `tablet` / `mobile`（仅用于自用分析） |

### 13.4 转动事件（`MoveEvent`）

| 字段 | 说明 |
|---|---|
| `index` | 步序（0 起） |
| `raw_input` | 原始输入（`"R"` / `"2R"` / `"key:R"` 的来源标记） |
| `move` | 规范化指令（如 `"Rw'"`） |
| `axis` / `layer_set` / `layer_count` / `turn_amount` | §7.1 辅助字段 |
| `input_channel` | `keyboard` \| `button` \| `api` |
| `submitted_at_ms` | 相对开始的时间 |
| `state_fingerprint_after` | 操作后状态指纹 |
| `observation_id` | 本步基于哪次观察（人类为 `null`） |
| `merged_from` | 归并来源（如 `["R","R"]`），无归并时为 `null` |
| `ok` | 是否执行成功 |
| `error_code` | 失败时的错误码 |

**归并事件的字段取值（按 §5.4 纠正后的机制，实现时照此填）**

| 字段 | 归并后的取值 | 说明 |
|---|---|---|
| `move` | `"R2"` | 规范化记法，与 Agent 直接提交 `R2` 完全一致 |
| `turn_amount` | `180` | 不是 `90`；因为最终语义是半转 |
| `layer_count` / `layer_set` / `axis` | 与原单次 90° 相同 | 层与轴不变 |
| `raw_input` | 第一次按键的原始输入 | |
| `merged_from` | `["R","R"]` | 审计用；回放时按 `move` 播放，不按 `merged_from` 逐条重放 |
| `submitted_at_ms` | **第二次**按键的时间 | 用户视角"这一步完成了"的时刻 |
| `state_fingerprint_after` | 第二次执行 `R` 之后的真实指纹 | 与直接执行 `R2` 的指纹相同（AC-45 一致性） |

> 注意：`move_count` 是**由事件数派生**的，归并后事件数减 1，故 `move_count` 净增 1。**不得**出现"事件 1 条但 `move_count` 增 2"或反之的实现。

### 13.5 观察事件（`ObservationEvent`）

| 字段 | 说明 |
|---|---|
| `observation_id` | 唯一 ID |
| `at_ms` | 相对开始时间 |
| `mode` | 当次观察模式 |
| `view_orientation` | 视角（朝向 + 旋转） |
| `face_set` | 返回的面集合（**只存面名，不存颜色**，颜色由回放引擎重建） |
| `denied` | 是否被拒绝 |

> **设计意图**：不把颜色矩阵写进存储，一是省空间（4 阶单面 16 色 × 多次观察会迅速膨胀），二是让"回放时按 `state_fingerprint_after` 重建"成为唯一真相源，避免存储与状态不一致。

## 14. 验收标准（EARS 格式）

> 格式：`While <状态>` / `When <触发>` / `If <条件>` + **系统必须** + `<可观测行为>`。
> 每条都能被机器验证（自动化测试或脚本断言）。P0 功能全覆盖。

### 14.1 引擎与状态（F02）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-01 | Ubiquitous | 系统**必须**对 2、3、4 阶分别维护一个 N×N×N 状态模型，任一时刻 6 面贴纸总数分别恒为 24 / 54 / 96，且每种颜色出现次数恒为 4 / 9 / 16。 |
| AC-02 | Event | When 收到指令 `R`，系统**必须**在 5ms 内完成转动并返回 `{ok:true, move:"R", layer_count:1, turn_amount:90}`。 |
| AC-03 | Event | When 收到 `R`、`R'`、`R2` 依次执行，系统**必须**使最终状态指纹等于初始状态指纹（逆操作闭环）。 |
| AC-04 | Event | When 收到同一轴同一层的 `R` 与 `R'`，系统**必须**使执行后的状态回到执行前（单次逆操作正确）。 |
| AC-05 | Event | When 在 4 阶收到 `Rw`，系统**必须**使 `layer_set == [1,2]`；收到 `3Rw` 时 `layer_set == [1,2,3]`；收到 `2R` 时 `layer_set == [2]`。 |
| AC-06 | Event | When 在 3 阶收到 `Z`+`R`（即 `2R`），系统**必须**返回与 Singmaster `M'` 完全等价的状态变化。 |
| AC-07 | State-driven | While 阶数为 2，If 收到任何含层数 > 1 的前缀指令，系统**必须**返回 `{ok:false, error_code:"INVALID_LAYER"}` 且状态指纹不变。 |
| AC-08 | Unwanted | If 收到的指令无法解析（如 `"R3"`、`"Xq"`、`""`），系统**必须**返回 `{ok:false, error_code:"INVALID_MOVE"}` 且**状态指纹必须不变**、`move_count` 必须不增。 |

### 14.2 题面生成与复现（F04）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-09 | Event | When 用同一 seed 与同一 `cube_size` 连续生成 100 次题面，系统**必须**产出 100 个完全相同的 `state_fingerprint`。 |
| AC-10 | Event | When 连续生成 **1000** 个未指定 seed 的 2 阶题面，系统**必须**使**不同 `state_fingerprint` 的数量 ≥ 999**（碰撞率 ≤ 1‰）。断言方式：收集 1000 个指纹去重后计数。**原表述"比率 ≥ 99%"未给样本量——测试者取 3 次可得"100% 通过"，取 10 万次可得完全不同结论，随机性断言不给 N 即不可验收** |
| AC-11 | State-driven | While `gen_mode == "random_moves"`，系统**必须**使"随机操作打乱"这一字符串**同时存在于**题面元信息 DOM 文本与结果页 DOM 文本中（两处均需断言命中），且 `gen_mode` 字段值**不得**为 `"random_state"`。 |
| AC-12 | Unwanted | If 导入的题面快照非法（颜色计数不符、不可还原、已是还原态），系统**必须**返回 `{ok:false, error_code:"INVALID_STATE"}` 且**不进入** `ready` 态。 |
| AC-13 | Event | When 创建挑战成功，系统**必须**持久化 `Challenge` 对象的全部 13.1 字段，且 `state_fingerprint` 长度 ≥ 8。 |

### 14.3 蒙尘门控（F05）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-14 | State-driven | While 状态为 `ready` 或 `configuring`，When 调用 `window.cubeAgent.observe()`，系统**必须**返回 `{ok:false, error_code:"NOT_STARTED"}`，且返回值的 JSON 序列化中**必须不包含** `face_colors`、`state_snapshot`、`state_fingerprint`、`scramble`、`seed` 任一键名。 |
| AC-15 | State-driven | While 状态为 `ready`，系统**必须**不在 `localStorage` 中存储该题面的 `state_snapshot`、`scramble`、`seed` 任一字段。 |
| AC-16 | State-driven | While 状态为 `ready` 且 `dust_mode == true`，系统**必须**通过**确定性探针**证明魔方表面未出现任何贴纸颜色：在屏幕空间按相机矩阵计算固定探针点（每个可见面中心 1 点 + 每面 4 个内缩点），断言同时满足：① 所有探针像素与遮蔽色 `--cube-masked` 的色差 **ΔE ≤ 2**；② 任一探针像素与 6 个贴纸色中任一个的色差 **ΔE ≥ 20**。该判定对 2D 降级视图（§12.2 第 5 条）同样适用。**不得**使用"画布颜色种类数 ≤ N"这类统计式断言——MSAA/抗锯齿的边缘过渡色必然违反它，判定会恒假 |
| AC-17 | State-driven | While 状态为 `ready` 且 `dust_mode == true`，系统**必须**在遮蔽体相邻位置渲染文案，文案内容包含"不能阻止通过开发者工具读取内存"。 |
| AC-18 | Event | When 状态由 `ready` 转为 `running`，系统**必须**在 300ms 内使 `observe()` 返回成功且包含当前观察模式允许的全部字段。 |
| AC-19 | State-driven | While `observation_mode == "one_face"` 且状态为 `running`，系统**必须**使 `observe()` 返回的 `face_colors` 恰好包含 1 个面，且未请求的面以缺失键表达（不使用 `null` 占位）。 |
| AC-20 | State-driven | While `observation_mode == "three_face"`，When 调用 `rotateView()` 后再次 `observe()`，系统**必须**返回新朝向下可见的 3 个面（即"三面可见"而非"永久只能看三个面"）。 |

### 14.4 计步与判定（F06 / F07）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-21 | Ubiquitous | 系统**必须**使每条**已定稿**的转动事件使 `move_count` 增量恒为 1（`R`、`R'`、`R2`、`Rw`、`3Rw`、`2R`、`M/E/S`、以及归并产生的 `X2` 事件同样计 1）；视角旋转与观察调用的增量恒为 0。**`move_count` 必须等于事件数**，不得按层数累加、不得按角度除以 90 |
| AC-22 | Ubiquitous | 系统**必须**为每个 `MoveEvent` 记录 `layer_count`、`turn_amount`、`axis`、`layer_set` 四个字段，且可由其重算出 `HTM-layer` 计步结果。 |
| AC-23 | Event | When 2 阶 6 面各单色但处于任意整体朝向，系统**必须**判定为已还原。 |
| AC-24 | Event | When 3 阶 6 面各单色但处于任意整体朝向，系统**必须**判定为已还原。 |
| AC-25 | Event | When 4 阶 6 面各单色且"面→颜色"映射等于标准配色方案的任一 24 旋转，系统**必须**判定为已还原。 |
| AC-26 | Unwanted | If 4 阶 6 面各单色但"面→颜色"映射为镜像配色（不属于 24 个合法旋转），系统**必须**判定为未还原并返回 `INVALID_STATE`。 |
| AC-27 | Event | When `move_count == move_limit` 且该步执行后已还原，系统**必须**判定 `result == "solved"`（还原优先于步数耗尽）。 |
| AC-28 | Event | When `elapsed_ms` 首次超过 `time_limit_ms`，系统**必须**在 200ms 内将 `result` 置为 `"timeout"`，且此后 `applyMove` 必须返回 `{ok:false, error_code:"TIMEOUT"}`。 |
| AC-29 | Unwanted | If 调用 `submitSolution()` 时未还原，系统**必须**返回 `{accepted:false, error_code:"NOT_SOLVED"}` 且**不终止**挑战；累计第 3 次失败时**必须**将 `result` 置为 `"invalid_submission"` 并终止。 |
| AC-30 | Event | When 人类玩家点击"放弃"并确认，系统**必须**将 `result` 置为 `"aborted"` 并保留终止前全部事件。 |

### 14.5 键盘与操作（F03）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-31 | Event | When 在 `running` 态按下裸键 `W`/`A`/`S`/`D`/`X`/`Q`，系统**必须**分别提交 `U`/`L`/`F`/`R`/`D`/`B`，且 `input_channel == "keyboard"`。 |
| AC-32 | Event | When 按住 `Shift` 再按任一面键，系统**必须**提交对应的逆时针指令（`U'`/`L'`/…）。 |
| AC-33 | Event | When 在 300ms 内按下同一面键两次且其间无其他输入，系统**必须**使最终状态等于该面 `X2`、`move_count` 增量 = 1、且只产生 1 条 `MoveEvent`（`merged_from` 记录两次原始输入）。 |
| AC-34 | Event | When 按下前缀键 `2` 后按面键 `R`（3/4 阶），系统**必须**提交 `Rw`；按下 `3` 后按 `R`（仅 4 阶）**必须**提交 `3Rw`；按下 `Z` 后按 `R`，**4 阶必须**提交 `2R`、**3 阶必须**提交 `M'`；按下 `Z` 后按 `A`（L 面键），**4 阶必须**提交 `2L`、**3 阶必须**提交 `M`。**系统不得存在 `C` 前缀**（按下 `C` 不产生任何转动） |
| AC-35 | Unwanted | If 按下前缀键后 3 秒内无面键输入，系统**必须**取消该前缀状态，且状态栏不再显示"将提交"预览。 |
| AC-36 | Unwanted | If `event.repeat === true`（长按连发），系统**必须**忽略该 `keydown`，`move_count` 不增。 |
| AC-37 | Ubiquitous | 系统**必须**不注册任何 `Ctrl` 或 `Cmd` 组合键处理器，且对 `Ctrl+W`、`Ctrl+T`、`Ctrl+N`、`Cmd+W` **必须**不调用 `preventDefault()`。 |
| AC-38 | State-driven | While 状态为 `running`，When 按下 `Space`，系统**必须**不产生任何魔方操作、不改变 `move_count`，且**必须**调用 `preventDefault()` 阻止页面滚动。 |
| AC-39 | State-driven | While 状态为 `ready`，When 按下 `Space`，系统**必须**将状态转为 `running`。 |
| AC-40 | Ubiquitous | 系统**必须**按**轴口径**满足联合覆盖：对任意三元组 `(axis, L, t)`——`axis` ∈ {x, y, z}（3 个）；`L` 为 `1..N` 上的**连续非空区间** `[a,b]` 且满足 `b-a+1 < N`（**排除整轴全层**，那是整体旋转，按 AC-66 拒绝）；`t` ∈ {`90顺`,`90逆`,`180`}——界面上**必须**存在一条可点击路径完成该操作**。验证方法：程序枚举全部三元组，逐个驱动 UI（键盘序列，或"层选择器选定连续区间 `L` + 点击该轴转向 `t` 按钮"），断言 `applyMove` 收到的规范化指令满足 `parse(describe(axis,L,t)) === (axis,L,t)` 且 `ok == true`。**三元组总数：2 阶 18 / 3 阶 45 / 4 阶 81，合计 144**（3 轴 × 连续真子集数 × 3 转向；2 阶 2 区间、3 阶 5 区间、4 阶 9 区间）。**采用轴口径而非面口径**：面口径存在跨面冗余（2 阶 `2R` ≡ `L'`、3 阶 `3R` ≡ `L'`、4 阶 `4R` ≡ `L'` 都是同一物理层换个面命名），会对同一物理操作重复计数。**不要求每个三元组都有独立键盘按键**，键盘只需覆盖 §5.6 列出的高频子集 |

### 14.6 Agent API（F08）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-41 | Ubiquitous | 系统**必须**在页面内暴露 `window.cubeAgent`，其自有属性**必须**只包含方法（`getChallengeInfo`、`observe`、`rotateView`、`applyMove`、`getLastActionResult`、`getProgress`、`submitSolution`、`getChallengeResult`、`abandonChallenge`），**不得**包含可回溯到引擎实例的对象型属性。 |
| AC-42 | Event | When 在 `running` 态调用 `applyMove("R")`，系统**必须**返回 `{ok, move, layer_count, turn_amount, state_fingerprint_after, move_count, remaining_ms, observation_id}` 全部字段（**键必须存在**）。其中 `state_fingerprint_after` 的取值受观察模式约束：`observation_mode === "full"` 时返回真实指纹；**`observation_mode !== "full"` 时必须为 `null`**（理由见 §8.6）。挑战结束后由 `getChallengeResult` 正常返回最终指纹 |
| AC-43 | Event | When 调用 `observe()`，系统**必须**返回含 `observation_id` 的对象，且后续 `applyMove` 的返回值中 `observation_id` **必须**与该 `observation_id` 一致（用于关联"基于哪次观察做了决定"）。 |
| AC-44 | Unwanted | If 单帧内 `applyMove` 调用次数超过 60，系统**必须**返回 `{ok:false, error_code:"RATE_LIMITED"}` 且不改变状态。 |

### 14.12 输入完整性（不得静默丢弃）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-69 | Unwanted | 系统**必须**不静默丢弃任何合法的面键输入。具体：If 在 180° 归并窗口（300ms）内到达的是**不同**的面键，系统**必须**立即执行该面键对应的转动，并保留已执行的前一步（不得回退、不得改写、不得丢弃其中任何一个）。验证方式：注入 `W` 后 120ms 注入 `Q`，断言事件流中恰好新增 2 条 `MoveEvent`（`U` 与 `B`）、`move_count` 净增 2、`state_fingerprint` 等于按序执行 `U` 再 `B` 的结果。 |
| AC-70 | Ubiquitous | 系统**必须**按**表达出来的 move 序列**比较人机一致性，而非按输入来源比较：**同一个表达出来的 move 序列，无论来自键盘、按钮还是 `applyMove`，`move_count` 与事件序列必须一致**。例：`['R','R']` 经键盘输入（300ms 内双击）表达的是 `R2` 意图 → 1 条事件 1 步；而 `applyMove('R')` 调用两次表达的是两次独立转动 → 2 条事件 2 步；两者**不构成不一致**，因为表达出的 move 序列不同。**禁止**按输入通道做任何差异化处理（不得因来源是 `keyboard` 而合并、不得因来源是 `api` 而不合并） |

### 14.13 记法往返恒等（§5.7）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-71 | Ubiquitous | 系统**必须**保证 `describeMove` 与记法解析互为逆运算：**对全部 144 个 `(axis, L, t)` 三元组，必须满足 `parse(describeMove(axis, L, t)) === (axis, L, t)`（轴、层区间、转向三项全等）**。验证方式：程序遍历 144 个三元组，先 `describe` 再 `parse`，逐项断言相等；任一组不等即失败。**理由**：若某条记法的输出无法被解析回原三元组，日志里就会出现"能显示但重放不了"的字符串，回放会静默失败——这是最难排查的一类缺陷。同时该 AC 保证 `describeMove` 的输出域必然落在 §5.1 的记法正则内 |

### 14.14 界面呈现与唯一真源一致（§5.3.2.1 / AC-40 的补充）

| 编号 | 类型 | 验收标准 |
|---|---|---|
| AC-72 | Ubiquitous | 系统**必须**保证"层选择器显示"与"将提交的指令"由**同一个** `layerSet` 唯一真源派生，二者不得脱钩。具体：When 点击任一操作 tab 的按钮（如 G4 的 `3Rw`），层选择器**必须**同步显示该按钮对应的层区间（断言：选择器宿主元素的 `data-layer-set` 属性值等于该按钮的规范化层区间，如 `[1,3]`）；When 手动改动层选择器，tab 中与该区间不符的高亮**必须**全部取消。**禁止**出现"点了 `3Rw` 但层选择器显示 `层 1`"的错位——那会让用户以为自己在转单层，而实际提交的是三层宽转 |

#### AC-40 的覆盖性论证（为什么这条能过）

AC-40 不要求每个三元组配一个专用按钮，它要求"存在一条可点击路径"。这条路径只需**一条组合**就够：

> **G1 的 18 个按钮（6 面 × 3 转向）+ 层选择器的 9 个区间 = 162 个面组合。**

而 4 阶的轴三元组是 **3 轴 × 9 区间 × 3 转向 = 81 个**。162 恰好是 81 的两倍，因为**每个轴区间都正好有 2 个面表示**（x 轴区间可由 R 侧或 L 侧命名，两者等价）。因此：

- **G1 + 层选择器这一条路径就覆盖了 AC-40 的全部三元组**；
- 其余 4 个 tab（G3 / G4 / G5 / G6）是**纯捷径**，不是覆盖性所必需。

这个论证反过来约束了层选择器的能力边界：它**必须能表达全部 9 个区间**（4 阶）。少一个区间，对应三元组的可点击路径就断了。

| 阶数 | 连续区间数（排除整轴全层） | 轴三元组 | 面组合 |
|---|---:|---:|---:|
| 2 | 2（`[1]` `[2]`） | 18 | 36 |
| 3 | 5（`[1]` `[2]` `[3]` `[1-2]` `[2-3]`） | 45 | 90 |
| 4 | 9（4 个单层 + 3 个双层 + **2 个三层**：`[1-3]` `[2-4]`） | 81 | 162 |
| 合计 | — | **144** | 288 |

> **易漏点**：4 阶的 9 个区间里有 **2 个三层区间**（`[1-3]` = `3Rw`、`[2-4]` = `3Lw`）。若层选择器只做"单层 + 双层"，会漏掉 G4 那一整组，AC-40 随之失败。

#### AC-40 与 `move_catalog` 是两个不同维度（勿混用）

| 项 | AC-40 | `move_catalog`（架构契约） |
|---|---|---|
| 回答的问题 | **界面上有没有可点击路径**能完成这个物理转动 | **Agent 能下哪些合法指令串** |
| 计数维度 | **物理上不同的转动**（轴口径，别名去重） | **可提交的指令串**（含同物异名的别名 token） |
| 2 阶 | 18 | 18 |
| 3 阶 | 45 | 99 |
| 4 阶 | 81 | 162 |
| 用途 | QA 验收 | Agent 读的"我能下哪些指令" |

**为什么不一致且不矛盾**：

- **3 阶 45 vs 99**：`move_catalog` 把 `2R`、`2L`、`M` 这三个 token 都算作合法指令（同一个中间层有 3 种写法），而 AC-40 的轴口径只把它算作**一个**物理转动。差出来的 54 正是"同一物理转动的不同命名"。
- **4 阶 81 vs 162**：面口径（6 面 × 9 区间 × 3 转向 = 162）里每个轴区间都有正好 2 个面表示，轴口径去重后是 81。`move_catalog` 保留两种面命名，因为它要告诉 Agent"这两种写法都收"。
- **2 阶 18 = 18**：因为 2 阶只有 1 个可用区间，且 `2R` 这类前缀被 AC-07 拒绝，两个口径恰好重合。

**给 QA 的话**：验收 AC-40 时按 18 / 45 / 81 建用例；看到 `move_catalog` 的 18 / 99 / 162 不要当成错误。

#### 竞品怎么做键盘映射与打乱展示（回答重点问题 1）

- **键位组织**：csTimer 的做法是**把 6 个面 + 宽转 + 内层 + 整体旋转全部平铺到三行字母键上**（原文键位表 3 行 × 10 列），规律是"字母区中段放高频面键、`Shift` 系与边缘键放宽转与整体旋转"。代价是必须依赖文档记忆，csTimer 也是把键位表直接印在设置页里。
- **打乱展示**：全部竞品都用**纯文本 Singmaster 串**（如 `R U R' U' F2 D'`）作为主展示，辅以 2D 展开图（Twisty Timer）或 3D 预览（csTimer 的 scramble image）。文本串是刚需——因为它是可复制、可核验、可粘贴进求解器的唯一格式。
- **打乱质量**：Twisty Timer 与 csTimer 都强调"随机态"而非"随机步"，且明确引用 TNoodle 作为质量锚点；Twisty Timer 甚至主动声明"非官方工具，不用于正式比赛"。**这说明"随机态 vs 随机步"的区分是速拧圈的共识性质量声明**，不是可选礼貌。

**对我们的启示**：
1. 打乱必须同时给**可复制的文本串**和**可视化**，文本串放主位。
2. 键位平铺是竞品的共同失败点。我们改成"空间映射 + 前缀分层"，并配常驻键位图和鼠标层选择器兜底——这不是差异化，是**必要的体验修正**。
3. "随机态 / 随机步"必须显式区分并标注，这是行业礼仪。

| 平台 | 题目复现机制 | 多次运行与评分机制 | 可借鉴 / 需规避 |
|---|---|---|---|
| **ARC-AGI 1/2/3**（ARC Prize Foundation） | 公开集 / 半私有集 / 私有集三层隔离防污染；每次评测用固定的开源 benchmark 仓库 + 每个模型一份 model configuration（模型名、推理档位、token 上限）；ARC-AGI-3 每任务发布**完整 replay** | 每任务 pass@2（同一测试输入允许 2 次尝试，任一次精确匹配即得分）；**逐任务 0/1，无部分分**；分数 = 解出任务占比；另报 cost/task 与 time/task；官方明确指出"同一分数在不同算力预算下含义完全不同"，强调成本归一化 | 借鉴：**分层题面集 + 无部分分 + 每任务发布 replay + 必须标注测试条件**。规避：本产品不追求"防污染"，因为纯前端做不到，宁可承认而不是假装 |
| **SWE-bench**（含 Verified / Lite / Pro） | 每个实例一套 **per-instance Docker 镜像**，把仓库版本、依赖版本、测试环境全部冻结；镜像分层（base → env → instance）兼顾复用与隔离；gold patch 先跑一遍验证实例"确实可解" | pass@1；判定用 `FAIL_TO_PASS`（修前失败、修后必须通过）+ `PASS_TO_PASS`（修前通过、修后必须仍通过）双清单；**全部通过记 1，任何一步失败记 0**；社区实证：**仅 harness/scaffold 配置差异就能造成约 12 个百分点的分数波动**，因此跨 scaffold 的分数不具可比性 | 借鉴：**双清单思想**——我们的对应物是"必须还原" + "不得违规（不超时、不超步、不用非法指令）"；以及"必须先验证题目确实可解"（对应我们的题面合法性校验 §6.4）。规避：不承诺跨 harness 可比，明确"人机同引擎"是我们唯一能保证的可比性 |
| **AgentBench**（THUDM 学术版 + 工程版） | 用 POMDP（状态空间 / 动作空间 / 转移 / 奖励 / 指令 / 观察空间）形式化；任务跑在独立容器；**所有模型统一 greedy decoding（temperature = 0）+ 单次 CoT 示例**以保证可复现；工程版提供 `trace.jsonl` 逐工具调用毫秒级时间戳 | 逐任务得分 + 各域平均 + 加权总分；**稳定性置信度 `CI = 1 - σ/μ`**（同一任务多次运行的得分标准差 / 均值），CI 越接近 1 表示表现越稳定；工程版明确"因 Agent 非确定性，分数在多次运行间会波动 ±3~5 分，建议跑 3 次取均值，看 delta 而不是绝对值" | 借鉴：**稳定性置信度** + **建议 3 次取均值** 直接成为我们 F13"多轮实验对比表"的核心指标；**逐调用时间戳 trace** 直接对应我们的 `ObservationEvent` / `MoveEvent`。规避：学术版用 LLM-as-judge 引入主观性，我们全用规则判定 |

#### AI 评测平台怎么保证同一题目可复现、多轮可对比（回答重点问题 2）

三家给出的是同一套骨架，只是实现层不同：

1. **固定题面本体**：题面不许在运行间变化。ARC-AGI 靠固定数据集文件；SWE-bench 靠 per-instance 镜像冻结；AgentBench 靠固定任务 fixture。→ 我们的对应物是 `state_snapshot` + `state_fingerprint` + `gen_version`。
2. **固定环境**：库里/依赖/系统版本全部冻结，避免"在我机器上没问题"。→ 我们的对应物是 `engine_version` + 纯前端无外部依赖（这反而是纯前端的天然优势：环境就是那个浏览器）。
3. **固定执行策略**：temperature = 0、单次示例、固定 scaffold、固定步数上限。→ 我们的对应物是 `RunConfig` 全量落盘 + `agent_meta`（prompt 版本、tool 版本）。
4. **二元判定，不给部分分**：避免"差不多对"污染结论。→ 我们沿用：`solved` / `not solved`，其余指标只作参考不作分数。
5. **每次运行独立记录 + 发布 replay**：结论必须可被人逐帧核验。→ 我们的对应物是 §10 回放 + 导出 JSON。
6. **多次运行报均值与稳定性**：单次分数不可信。→ 我们的对应物是 F13 对比表，含 `mean` / `std` / `CI`。
7. **明确标注测试条件**：算力预算、数据集版本、公开/私有集。→ 我们的对应物是结果页那 5 条诚实标注（§9.2）。

### 15.3 竞争格局结论

| 维度 | 速拧计时器（csTimer / CubeDesk / Twisty Timer） | AI 评测平台（ARC-AGI / SWE-bench / AgentBench） | 本产品 |
|---|---|---|---|
| 3D 魔方交互 | 有（csTimer 虚拟魔方）或无（Twisty Timer） | 无 | 有，且驱动引擎与 Agent 完全同源 |
| 题面可复现 | 部分（打乱可复现，但无"同题面多轮运行"概念） | 强 | 强（seed + 快照 + 指纹 + 版本） |
| 观察权限受限 | 无（速拧不需要） | 无（任务全可见） | 有（三面/单面/受限） |
| 程序化接口 | **全部没有** | 有（但都是服务端/CLI） | 有，且**在页面内**、零部署 |
| 逐帧回放 | 无（只有成绩曲线） | 有（replay / trace） | 有，且含"观察者视角" |
| 部署成本 | 静态或 App | 重（Docker / 云 / 算力） | **零（静态站点）** |
| 防作弊 | 不关心 | 强（服务端持有状态） | **弱，已明确承认（§8）** |

### 15.4 我们的差异化（一句话）

> **"把速拧计时器的题面复现与键盘手感，和 AI 评测平台的同题多轮可比与逐帧 trace，压进同一个纯前端页面——人按下的是 `R` 键，Agent 调用的是 `applyMove('R')`，两者在引擎里是同一条指令、在回放里是同一条事件。"**

次级差异点（按重要性）：
1. **零部署的 Agent 评测**：不用 Docker、不用云、不用装东西，打开页面就能让 Agent 跑。
2. **观察者视角回放**：能回看"Agent 在单面观察下看到的是什么"，这是纯速拧工具和纯评测平台都给不出的。
3. **观察权限作为一等难度维度**：把"看得到多少"变成可配置的评测变量，而不只是"题有多难"。
