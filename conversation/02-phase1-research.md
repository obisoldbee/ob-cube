## 引擎算法验证（本项目唯一被机器证明的部分）

### 验证一：置换生成可行性 — `docs/research/permutation-proof.py`

用独立实现证明「程序化几何生成置换」这条路成立，不依赖架构文档：

- `R` / `R'` / `R2` 的置换非恒等、阶为 4、与逆互消、`R2` 与 `R` 两次结果一致
- 单面 90° 受影响贴纸张数符合理论值（含面心差异）：
  - N=2 → 12（4 + 4×2）
  - N=3 → 20（9 − 1 面心 + 12）
  - N=4 → 32（16 + 4×4，偶数阶中心块自身也互换）
- 退化 move 被拒绝：2 阶的 `Rw` / `3Rw` / `M`、任意覆盖全 N 层的转动
- 打乱序列 + 逆序逆操作 = 恒等（N=2 8 步 / N=3 11 步 / N=4 13 步）
- 人工抽样核对 3 阶 `F`：`U(2,0)→R(0,0)`、`U(2,2)→R(2,0)`、`R(0,0)→D(0,2)`

**退出码 0。**

### 验证二：架构文档算法 vs 已验证实现 — `docs/research/verify-spec-vs-proof.py`

把 `ARCHITECTURE.md §4.1/§4.3/§4.4` 的算法**逐字实现**（外法向量 + 列基 u + 行基 v + 位置公式 + slot 顺序 `[U,R,F,D,L,B]`），与验证一逐张贴纸比对：

- 六面基向量全部满足 `u × v = -n` 且与法向正交
- 位置公式与独立实现的六面坐标逐个等价
- N=2 的 18 个 move、N=3 的 27 个 move、N=4 的 25 个 move，置换逐个等价
- 语义抽检：`R` 把 `F(1,2)` 搬到 `U(1,2)`，与标准手转一致

**退出码 0。**

### 这一步消除了什么风险

架构师自己标注："几何基向量写错的代价是某一面的颜色矩阵镜像"——这类错误不会报错、不会崩溃，只会让某个面的贴纸显示颠倒，且极难通过肉眼发现（因为魔方本身就是对称的）。两套独立实现逐张贴纸对齐后，这条风险关闭。

## 设计侧关键结论

- 魔方六色按 L\* 严格阶梯排布（最小 ΔL\* = 7.87），**完全灰度化后六面仍可区分**；色盲方案为三级（亮度阶梯 / 贴纸字母 / 单色模式），明确否决「切换配色方案」——实测色相替换只把冲突挪位，不消除
