## 0. 结论先行

1. **产品的真正卖点不是"网页魔方"，而是"同一题面的可复现人机同台"**。速拧计时器已经解决了打乱与手感，AI 评测平台已经解决了复现与对比，但两者从未合并在一个页面里。本产品的差异化就压在这条缝合线上。
2. **MVP 必须闭环 12 项 P0 功能**（v2.0：v1.10 的 13 项中 F14 观察模式降回 P1，见 §3.3），其中 4 项是"没有它整个产品定义就不成立"的地基：统一引擎、seed 可复现题面、API 层蒙尘门控、操作记录与回放。
3. **两个必须先说清楚的诚实边界**：纯前端不能真正防作弊，蒙尘只能做到"不主动泄露 + 抬高作弊成本"；不接求解器时难度分级只能是启发式估计，必须标注为估计值。
4. **最大的产品风险是键盘记忆成本**，不是技术风险。4 阶的可操作层组合有 10 种以上，键位设计失败会让人类玩家在第一分钟流失。
5. **v2.0 新增的第三条诚实边界：文档不得声称代码没有的能力。** 12 项 P0 中 9 项已完整交付、3 项部分交付（F01 缺 2D 降级、F05 缺探针自动化、F07 缺对外 `INVALID_STATE` 码）；回放的独立页与全套控件、观察模式配置入口、埋点体系均为 P1 且未实现。逐项状态见 [`../PRD.md`](../PRD.md) §4，完整矩阵见 `docs/reports/2026-10-26-implementation-status-report.md`。

## 1. 产品定义

### 1.1 一句话描述

> 一个网页，人和 AI Agent 用**同一套魔方引擎、同一份计步规则、同一条回放记录**，在**同一个可复现题面**上比谁还原得更好。

### 1.2 核心问题

| 谁 | 什么场景 | 现在怎么解决 | 为什么不行 |
|---|---|---|---|
| 普通玩家 | 想在浏览器里不装 App 就转两把 2/3/4 阶，并且能复盘自己的操作 | 用速拧计时器（csTimer / CubeDesk / Twisty Timer） | 这些工具的核心是"计时 + 成绩统计"，虚拟魔方要么没有、要么是附属功能；键位是给熟练速拧者设计的，没有引导；没有"这一把我转了什么"的逐帧复盘 |
| AI Agent 开发者 | 想验证自己的 Agent 是否真能"看懂魔方状态并规划转动"，而不是靠模拟点击碰运气 | 自己写脚本 + 自己造魔方状态 | 没有标准化题面、没有统一计步、没有可对比的历史运行，每次实验结论都无法复现；自己造的题面别人无法重跑 |
| 模型评测人员 | 想用同一批题面横向比较多个模型/多个 prompt 版本 | 用通用 Agent benchmark（AgentBench / SWE-bench 类） | 这些平台没有"带观察权限限制的几何状态推理"场景；想加一个魔方维度就得自己搭全套环境 |

**一句话**：缺的不是魔方，缺的是**"同题面 + 同引擎 + 同计步 + 可回放"的横向可比性**。

### 1.3 目标用户画像

| 画像 | 特征 | 关键诉求 | 会因为什么放弃 |
|---|---|---|---|
| **A. 普通玩家**（主） | 18–35 岁，会还原 3 阶但非竞速选手，愿意在浏览器里消磨 5–15 分钟 | 打开就能转；不用背键位；能看回放知道自己哪一步走错了 | 前 60 秒内搞不清怎么转某一层；键位提示要看说明书 |
| **B. AI Agent 开发者**（主） | 熟悉 JS，能在控制台里调 `window.cubeAgent`，关心确定性与可调试性 | 题目 seed 固定；每步有明确返回值；能复制完整事件摘要；失败原因明确 | API 返回值模糊、错误码缺失、同 seed 出不同题面 |
| **C. 模型评测人员**（次） | 需要跑批量对比但这次不想搭后端 | 同一题面能跑 N 次；结果有表格对比；知道每次跑用的什么配置 | 记录里分不清"哪次是哪个 prompt 版本"；没有运行元信息 |

次要用户：教程作者（需要可分享的固定题面链接）。

### 1.4 产品设计原则（继承并修订原文）

| 原则 | 状态 | 说明 |
|---|---|---|
| 人类与 Agent 使用同一套引擎方法 | 保留 | Agent 调用的是引擎方法本身，不是模拟点击 |
| 视觉展示、真实状态、观察权限三者独立 | 保留 | 三者分层，互不耦合 |
| 每次转动可验证、可记录、可复现 | 保留 | 事件级记录 |
| 默认不向 Agent 暴露隐藏状态 | **修订** | 原文为"由服务端强制执行"。本产品无服务端，改为"由 API 层门控强制执行，并明确其不可强保证的边界"（见 §8） |
| 时间/步数/难度/观察限制由挑战配置决定 | 保留 | 配置即契约 |

## 3. 功能清单与 RICE 排序

### 3.1 RICE 说明

`Score = (Reach × Impact × Confidence) / Effort`

| 维度 | 取值 | 本产品口径 |
|---|---|---|
| Reach | 1–10 | 每季度会用到该功能的用户比例（10 = 几乎所有用户） |
| Impact | 0.25 / 0.5 / 1 / 2 / 3 | 对单个用户完成核心任务的影响 |
| Confidence | 50% / 80% / 100% | 100% = 有明确需求原文或竞品实证；80% = 有间接证据；50% = 判断 |
| Effort | 1–10 | 人月（1 ≈ 半天；10 ≈ 3 个月以上） |

> **重要**：RICE 只用于**排序**，不用于决定 P0。P0 由"MVP 闭环依赖门"决定——任何一项缺失都会让"人机同台可比"这个产品定义不成立，即使它的 RICE 分不高（例如 Agent API 的 Reach 只有 5）。这条规则写在这里，避免后续用分数砍地基。

### 3.3 MVP 范围

**MVP = F01–F11（其中 F09 只含 F09a）+ F18 = 12 项 P0。** F09b、F12–F17 进 Backlog。F19–F24 进 Out-of-Scope（§4）。

> **v2.0 相对 v1.10 的 MVP 变化**：v1.10 是 13 项（含 F14）。v2.0 把 F14 降回 P1，MVP 回到 12 项。逐项交付状态见 [`../PRD.md`](../PRD.md) §4.1。

> **F18 为何从 P1 升为 P0（v1.2 起，v2.0 维持）**：用户原始需求 §3.2 已把"暂停、继续"列入挑战主界面的必备按钮，且团队主理人裁决"保留按钮"。F18 的实现成本仅 0.5 人月（RICE 6.4），但它带出一条必须写死的语义——**暂停冻结计时（v1.9）**——这条语义与 §7.2.1、AC-57~AC-60、AC-73~AC-74 绑定，不能延后，否则后期补做会推翻已有的计时与判定实现。

> **F14 为何在 v2.0 从 P0 降回 P1**：v1.10 #54 曾把它升为 P0，理由是"§8.2 C6 的蒙尘门控与 AC-19/20/65 的直接被测能力"。这个理由本身成立，但升级**只改了 PRD 一处**：SPEC 的"锁定——不在此列表一律不做"清单里从来没有 F14，代码里也没有观察模式的配置入口（`settings.ts` 的 `ChallengeConfig` 无该字段，`wiring` 创建会话时不传，生产环境恒为 `full`），`after_move` 档更是连门控逻辑都没有。
>
> 结果是形成一个三角空洞：**验收依据说必须要、开发契约说不在锁定清单、代码里没有**。九条用户反馈裁决里配置面板的范围（时限/步数/蒙尘/参与者/题目）本来也不含观察模式。
>
> v2.0 的处理：**降回 P1，并把"配置面板增加观察模式入口 + 补齐 `after_move` 门控"列为 P1 的首要项**。AC-19 / AC-20 / AC-65 按附录 C 冻结规则保号并标注 `[已降级至 P1]`。引擎侧已支持的 `three_faces` / `single_face` / `restricted`（预算 24）保留，不删代码——它们已有测试覆盖，降级只是不再作为 MVP 验收门槛。
>
> **产品叙事的影响必须承认**：竞品分析的三大差异点之一是"观察权限作为一等难度维度"（见 `docs/research/2026-10-25-competitor-analysis-research.md` §15.4）。F14 降级意味着这个差异点在 MVP 里**不可被用户配置**，只能通过控制台直接调 API 触发。对外表述时不得声称"支持五档观察模式"，只能说"引擎支持五档，配置入口在 P1"。

> **F09 为何在 v2.0 拆成 F09a / F09b**：v1.10 把"操作记录 + 逐帧回放"作为一个 P0 单项，AC-47（回放第 k 步须等于第 k 条 `MoveEvent` 指纹）与 AC-48（拖拽进度条到第 k 步须 300ms 内定位）已冻结。但代码交付的是**结果页内 260ms 定时器驱动的重放**：没有独立回放页、没有进度条、没有调速、没有单步、没有三视角、没有 AC-50 的旧引擎版本提示。同时项目 memory 又把回放记为 P1，与 PRD 的 P0 双轨并行。
>
> v2.0 的处理：**按能力边界拆开**。F09a =「事件流完整记录 + 结果页原地重放」，这是已交付且构成产品定义地基的部分（"同一条回放记录"是人机同台的三根支柱之一），维持 P0，新增 AC-78 描述它。F09b =「独立回放页与全套控件」，降为 P1，AC-47 / AC-48 / AC-50 保号并标注 `[已降级至 P1]`。
>
> 这样做的代价是承认 MVP 的回放能力比 v1.10 声称的弱；收益是验收不再对着一个不存在的进度条打钩。

### 3.4 操作面板的 tab 组数（v2.0 锁定，追认实现）

| 阶数 | tab 组数 | 具体组（括号内为该 tab 的同屏控件数） |
|---|---|---|
| 2×2 | **2 组** | 单层(18)、自由层(6) |
| 3×3 | **3 组** | 单层(18)、中层(9)、宽转(18) |
| 4×4 | **5 组** | 单层(18)、宽转 2(18)、宽转 3(18)、内层(10)、自由层(8) |

**任一组不得折叠。** 峰值同屏控件数为 **19**（18 按钮 + 1 层选择器），三阶数一致，不突破既有布局容量；折叠会延长 AC-40 要求验证的可点击路径，属负优化。详见 [`03-notation-keyboard.md`](03-notation-keyboard.md) §5.6。

**「自由层」tab 的定义**：轴 + 层槽任意多选。`canSelectLayer` 只限制层数上限、不强制连续；**非连续组合（如 4 阶同时选第 1、3 层）由"将提交"预览串显示 `—` 来拦截**——因为记法无法序列化非连续区间（见 [`03-notation-keyboard.md`](03-notation-keyboard.md) §5.7），记不下来就回放不了、Agent 也读不懂。这个 tab 是 AC-40「存在一条可点击路径」的主要承载者，也是 AC-72「层选择器与将提交指令同源」的同源点。

> **v2.0 相对 v1.10 的三处修正（追认实现，非需求变更）**
>
> | 项 | v1.10 写法 | v2.0 修正 | 理由 |
> |---|---|---|---|
> | 2 阶第 2 组 | 「视角」 | **「自由层」** | 视角控件**从来不是 tab**，它在中栏舞台区（左上打乱·重置，右上视角 5 键 + 6 面直达按钮）。v1.10 把舞台区控件误记为一个 tab 组 |
> | 4 阶 G5 / G6 | 「单内层」「单内层第 2 层」两个独立 tab | **合并为一个「内层」tab（含近本侧/近对面位置切换）+ 一个「自由层」tab** | 实现用 `innerPosition: 2 \| 3` 参数让一个 tab 覆盖两个内层位置，比开两个 tab 更省同屏控件；组数仍是 5，AC-40 覆盖性不受影响 |
> | 「自由层」tab 的存在 | 未提及 | **正式纳入契约** | UIUX 附 C#6 曾裁定"删除自由层 tab，改「轴 + 起层 + 止层」选择器"，该裁定**从未执行**，代码里 2 阶（6 控件）与 4 阶（8 控件）各有一组。**v2.0 作废 UIUX 附 C#6**，理由：现形态已能表达全部连续区间（满足 AC-40），改选择器需重构 `turn-matrix-data.ts` / `turn-matrix-free.ts` 并重验 AC-40 / AC-72 的全部可点击路径，收益不足以覆盖回归成本 |
>
> 3 阶的三组（单层 / 中层 / 宽转）与 v1.10 一致，未变。

**MVP 一句话验收**：打开页面 → 选 3×3 + 指定 seed → 创建 → 看到题面（蒙尘=开为灰色遮蔽体；默认蒙尘=关为预观察彩色题面）→ 点开始 → 键盘转到底 → 看到"已还原 / 用时 / 步数" → 点回放看到每一步在 3D 上重演；同时控制台能 `window.cubeAgent.observe()` 拿到同样的题面。

> 上述验收在 v2.0 定稿时**已可走通**（见 [`../PRD.md`](../PRD.md) §4 交付基线），唯一例外是"点回放"目前只是结果页内的原地重放（F09a），不是独立回放页（F09b，P1）。

## 4. 明确不做（Out-of-Scope）

| 不做的事 | 原因 | 何时考虑 |
|---|---|---|
| **后端账号体系**（注册/登录/用户档案） | 产品定位是"打开即用、可离线、可静态部署"。账号体系会引入服务端、隐私合规、密码安全三项非核心负担，且与"无后端"的交付约束直接冲突。历史数据用 localStorage 已能满足单人纵向对比。 | 当出现"跨设备同步成绩"或"多人榜单"的真实需求，且已确认愿意承担服务端成本时。触发信号：≥30% 用户在反馈里提到换设备丢记录。 |
| **云端题库共享**（公开题库市场、他人题面订阅） | 题库共享需要内容审核、版本兼容、题面合法性服务端校验。MVP 阶段用"粘贴 seed / 复制题面指纹"已能完成题面流转，成本几乎为零；本地导入导出仍按 v1.9 #44 不在范围。 | 当固定题库的本地运营量超过约 200 条、或出现"希望别人跑我的题面"的重复请求时。 |
| **自动难度分级**（按最优解长度自动标级） | 真难度需要求解器（2 阶可做，3 阶需两阶段算法，4 阶需降阶 + parity 处理），是数人月量级的独立工程；且 4 阶求解在浏览器里耗时不可控。MVP 用启发式估计（§6）覆盖 90% 的运营标注需求。 | 当难度标签引发争议（同一题被判为不同等级）、或需要对外发布"标准化能力测试集"时。 |
| **批量多步提交**（Agent 一次提交整段算法） | 会绕过"逐步观察"这一核心评测维度：如果允许一次交 60 步，模型就可以不做状态推理只做模式匹配，评测结论失真。且会让计步与人机对比失去可比性。 | 作为**独立模式**（`batch` 标记）与逐步模式并存时考虑；必须单独标注、单独排行榜，不得与逐步模式混算。触发信号：开发者明确反馈逐步调用的网络/调用开销成为主要成本。 |
| **移动端深度适配**（触屏手势转层、竖屏三栏改版、性能调优） | 4 阶有 96 个贴纸 + 层选择器 + 三栏信息，竖屏下触控目标密度不足；手势转层需要独立设计一套交互（本项目 UX 预算只够桌面键盘一套）。第一版优先保证桌面效率（沿用原文"第一版优先保证桌面端操作效率"）。 | 当移动端访问占比 > 25%，或明确出现"想在手机上做 Agent 评测"的需求时。最小让步方案：移动端只读回放 + 只做 2×2。 |
| **求解器提示 / 分步教学** | 与评测平台的核心价值**直接冲突**：任何内置提示都可能被 Agent 通过 API 触达，一旦存在就等于提供答案通道，会污染全部评测结论。另需承担求解器体积与耗时。 | 上线后作为**独立"学习模式"**，与挑战模式硬隔离（不同构建产物或不同页面，学习模式的任何模块在挑战页不加载）。不得出现在挑战页。 |
| **多人比赛房间**（实时对战、观战） | 需要服务端房间、实时同步、断线重连、裁判逻辑；与"纯前端静态部署"约束冲突。竞品 CubeDesk 的 1v1 之所以存在，是因为它本来就有云端基础设施。 | 当产品已有后端（例如因账号体系引入），且"人机同台"已被验证有留存时。 |
| **纯前端防作弊强制** | 详见 §8。做不到就是做不到，不列功能，只列边界。 | 当评测结论需要对外背书（论文、榜单、采购决策）时，必须引入服务端持有状态。 |
| **成绩排行榜 / 反作弊评分** | 没有服务端就无法验证成绩真实性，公开榜单会立刻被污染，反而伤害可信度。 | 与服务端方案同期。 |
| **魔方类型扩展**（金字塔、五魔方、SQ1） | 状态模型与记法体系完全不同，是独立产品线。 | 当 2/3/4 阶的留存与评测使用率已稳定。 |
