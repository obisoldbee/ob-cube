## 6. 难度分级定义

### 6.1 设计前提：为什么不能只用打乱步数

打乱步数（scramble length）衡量的是**题面被扰动了几次**，不是**求解难度**：
- 20 步打乱可能因操作抵消而等效于 6 步（`R R'` 白打）；
- 4 阶的 60 步打乱可能全部是外层转动，实际等价于一个 3 阶题面加未配对中心（反而更容易）；
- 反过来，一个 8 步打乱的 3 阶若含大量 D 面/双层结构，人类还原难度显著高于 20 步全 R/U 打乱。

因此难度由**四个正交维度**共同判定，打乱相关因子只占其中一个子权重。

### 6.2 四个判定维度

| 维度 | 代号 | 量化方式 |
|---|---|---|
| **规模** | `S` | 2 阶 = 1.0；3 阶 = 2.5；4 阶 = 4.0 |
| **题面结构复杂度** | `K` | `K = 0.8·dF + 1.2·pW + 0.5·(nE/10)`，其中 `dF` = 打乱序列覆盖的不同面数（1–6）、`pW` = 宽转/内层步在序列中的占比（0–1）、`nE` = 抵消化简后的净有效步数（上限 40）。**打乱步数只通过 `nE` 这一项间接进入，且权重最低** |
| **观察约束** | `O` | 五档互斥查表（不再叠加）：完整观察 = 0；三面观察 = 1.0；单面观察 = 2.0；操作后观察 = 1.5；受限观察 = 2.5 |
| **时间/蒙尘约束** | `C` | 蒙尘开 +1.5；限时压力 `T = clamp( (估算最低步数 × 2.0 秒) / 时间限制秒数 , 0 , 2.0 )`（2 秒/步是新手节奏假设，用于把"时间够不够"折算为压力值） |

`difficulty_score = S + K + O + C`

> **v1.10 修正**：`observation_mode` 是单值枚举（§13.2），五档互斥，因此 `O` 取对应档位的值，不存在“在某个基数上叠加”的写法。`after_move` 与 `restricted` 的基数由本表直接给出。

### 6.3 等级判定表

| 等级 | 判定条件（按顺序判定，命中即停） | 附加说明 |
|---|---|---|
| **入门** | `difficulty_score < 3.0` **且** `O = 0` **且** `C < 0.5` | 典型：2 阶 4–6 步打乱；3 阶净有效步数 ≤ 6 且只涉及 2–3 个面 |
| **常规** | 不满足入门，且 `difficulty_score < 5.5` | 典型：3 阶标准 20 步随机打乱、完整观察、不限时；也覆盖 2 阶 + 单面观察等“分数不高但观察受限”的组合 |
| **高难度** | `difficulty_score ≥ 5.5` | 典型：4 阶题面；3 阶高净有效步数 + 宽转密集 + 受限观察 |
| **指定结构** | 题面带 `structure_tag`（正交标签，不参与 `difficulty_score`） | 预置标签：`仅对面双转`、`十字已完成`、`F2L 缺一组`、`仅 R/L 面`、`中心已聚`（4 阶）、`棱已配对`（4 阶）。标签由运营者手动指定 |
| **长序列** | 打乱序列原始长度 ≥ 阈值（2 阶 ≥ 30 / 3 阶 ≥ 25 / 4 阶 ≥ 45）**且** `nE ≥ 0.6 × 原始长度`（即未被大量抵消） | 这一条单独存在，专门用于测"长上下文跟随能力"。**若净有效步数不达标，不允许打"长序列"标签** |
| **专项观察** | `O ≥ 1.0` | 与主等级并集存在（一个题可同时是"常规 + 专项观察"） |
| **限时** | `T ≥ 1.0` | 同上 |
| **蒙尘** | 蒙尘模式开启 | 同上 |

**主等级算法（唯一口径）**：先判 `入门`；不命中则 `difficulty_score < 5.5` 一律 `常规`，否则 `高难度`。`O` 与 `C` 已经进入 `difficulty_score`，**不再对主等级额外设 `O`/`C` 上限**——v1.10 前的 `O ≤ 1.0 / O ≤ 2.0` 条件会让“2 阶 + 单面观察（约 4.0 分）”落进无等级空档。

主等级（入门/常规/高难度）互斥取一；**五个**专项标签（指定结构 / 长序列 / 专项观察 / 限时 / 蒙尘）为正交并集。

### 6.4 题面合法性下限（与难度无关的硬门槛）

| 阶数 | 门槛 | 依据 |
|---|---|---|
| 2×2 | 最短解 ≥ 4 步 | 对齐 WCA 规则 4b3b 的下限精神，防止出现 1–3 步白给题 |
| 3×3 | 最短解 ≥ 2 步 | WCA 4b3 默认下限 |
| 4×4 | 最短解 ≥ 2 步 | 继承立方体类下限 |

> 无求解器时，`最短解` 用"净有效步数 ≥ 下限"作为代理判定，并在题目元信息中标记 `distance_is_estimated: true`。**这是已知的近似，必须对用户可见**，不得宣称这是真最短解距离（对应 Out-of-Scope 中的"自动难度分级"）。

### 6.5 打乱生成方式必须区分（继承原文，强化）

| 方式 | 定义 | 用途 | 元信息标记 | MVP 是否实现 |
|---|---|---|---|---|
| **随机操作** | 从已还原态施加 N 次随机合法操作 | 娱乐、操作手感测试 | `gen_mode: "random_moves"` | **是（v1 实现）** |
| **预设题** | 内置题库中的固定 seed + `scramble`，可复现 | 教学、回归对比 | `gen_mode: "preset"` | **v1.1 实现（不在 MVP）** |
| **随机状态** | 从合法状态空间等概率采样 | 标准化能力测试 | `gen_mode: "random_state"` | **否（v2 候选）** |
| **导入** | 外部粘贴的打乱序列或状态 | 题面流转 | `gen_mode: "imported"` | **否（v2 预留，范围外）** |

**硬性约束**：随机操作生成的状态**不得**标记为随机状态。UI 上必须用不同措辞区分（"随机题面"vs"随机打乱"），并在结果页脚注标明本次运行用的是哪种。混用会让跨运行的评测结论不可比。

#### v1 范围收窄（已由架构师裁决，本 PRD 据此降级）

> **v1 只实现「随机操作打乱」，不做均匀随机状态生成；v1.1 增加 `preset` 预设题，导入仍不做。**

原因与影响：

| 项 | 说明 |
|---|---|
| 为什么不做的技术原因 | 均匀随机状态生成需要对每个阶数实现"随机状态采样 + 求解器校验距离下限"。2 阶可做（状态空间小），**3 阶需两阶段算法、4 阶需降阶 + parity 处理**，属于独立工程且浏览器内耗时不控。这与 §4 Out-of-Scope 中"自动难度分级（需求解器）"是同一块能力的依赖 |
| PRD 相应降级 | `gen_mode: "random_state"` 保留在数据模型枚举中作为**预留值**，但 v1 的任何代码路径都不得产出该值 |
| 对评测结论的影响（必须写进结果页） | v1 的题面分布**不是**状态空间上的均匀分布，因此**不能**宣称"标准化能力测试"或用于跨平台能力对比。结果页在 `random_moves` 时必须显示："本次题面由随机操作生成，非均匀随机状态，不构成标准化难度基准。" |
| 何时升级到 v2 | 当出现"需要对外发布标准化题集"或"同一题面难度争议"时，且求解器已可用（F19） |

**因此**：§4 Out-of-Scope 里"自动难度分级"的"何时考虑"与本节绑定——两者应同期或在求解器落地后一并评估。v1 的难度标签一律是启发式估计，`distance_is_estimated` 恒为 `true`。

## 7. 计分与判定规则

### 7.1 HTM 计步细则

**定义（本平台口径，记作"本平台 HTM"）**：

> **一次提交的、绕单一轴线的、刚性层组的转动 = 1 步**，不论该次转动包含几层、转角是 90° 还是 180°。

| 情况 | 步数 | 说明 |
|---|---|---|
| `R` | 1 | |
| `R'` | 1 | |
| `R2` | 1 | 半转 1 步，这是 HTM 与 QTM（单转计步）的核心区别 |
| `Rw`（宽转 2 层） | **1** | 见下方结论 |
| `3Rw`（宽转 3 层） | **1** | 同上 |
| `2R`（单内层） | **1** | 原文明确要求"内层也各计 1 步" |
| `M` / `E` / `S` | **1** | |
| 视角旋转 | **0** | 不改变魔方状态 |
| `observe()` 调用 | **0** | 观察不是转动 |
| `submitSolution()` | **0** | |
| 被拒绝的非法操作 | **0** | 未改变状态，不计步也不计尝试 |

#### 结论：一次操作转动多层，仍计 1 步

**理由**：

1. **人体工学事实**：`Rw` 在物理魔方上是一次手指动作，和 `R` 的肌肉成本同阶。按层计步会让 4 阶的同一套解法在数字上被系统性放大 2–3 倍，制造"4 阶比 3 阶难 3 倍"的假象。
2. **跨阶可比性**：本平台的核心场景是**跨阶数、跨模型对比**。若计步口径随层数变化，4 阶的 60 步和 3 阶的 60 步就不是同一个量，对比表失去意义。
3. **与主流速拧直觉一致**：速拧社区说"这把 55 步"时，`Rw` 算一步。
4. **不损失信息**：见下方辅助字段。

**辅助字段（必须同时记录，保证可后验重算）**：

| 字段 | 含义 |
|---|---|
| `layer_count` | 本次转动涉及的层数（1 / 2 / 3） |
| `turn_amount` | 90 / 180 |
| `axis` | `x` / `y` / `z`（转轴） |
| `layer_set` | 具体层索引集合，如 `[1,2]` |

由此可派生 `HTM-layer` 口径（每层各计 1 步）与 `QTM` 口径（180° 计 2 步），在结果页作为"其他计步口径"折叠展示。默认展示与对比排序一律用本平台 HTM。

#### 口径与"限步 / 判定"的关系（必须写清，UI 需要据此设计标签）

| 场景 | 采用口径 | 是否可切换 |
|---|---|---|
| 挑战进行中的实时步数计数 | 本平台 HTM | **不可切换**。中途换口径会让"还剩多少步"这件事失去意义 |
| `move_limit` 限步判定 | 本平台 HTM | **不可切换**。判定标准必须在开始前锁定，否则同一 run 内可被口头重解释 |
| 结果页主指标 | 本平台 HTM | 不可切换 |
| 结果页"其他计步口径"折叠区 | `HTM-layer` / `QTM` | 可切换，**只影响该折叠区的展示与跨 run 对比表的排序**，不回写记录、不影响判定与胜负 |

**结论给 UI**：挑战中的步数标签是**固定口径**，不需要做成可选控件；但标签旁**必须**标注口径名（因为有 `R2` 算 1 步这种反直觉点）。结果页需要一处可切换的三口径展示区，用分段控件（Segmented）而非下拉，因为只有 3 个选项且需要并排对比。

#### 7.1.1 计步的三条公理（AC-21 / AC-61 / AC-70 的相容性说明）

这三条曾被误认为互斥，实际不互斥。先把公理写死：

| 公理 | 内容 |
|---|---|
| **G1** | `move_count` **等于事件数**。既不按层数累加，也不按角度除以 90 |
| **G2** | **一条已定稿的转动事件恒计 1 步**，无论它是 `R`、`R2`、`Rw`、`3Rw`、`2R`、`M`、还是归并产生的 `R2` |
| **G3** | **归并是输入整形，不是计步规则**。归并发生在事件定稿之前（§5.4.1），定稿之后一切照 `R2` 处理 |

**表面矛盾与解答**：

| 场景 | 表达出来的 move 序列 | 事件数 | `move_count` |
|---|---|---|---|
| 人类 300ms 内双击 `D` 键两次 | `['R2']`（整形后） | 1 | **1** |
| 人类点 `R2` 按钮 | `['R2']` | 1 | **1** |
| Agent 调 `applyMove('R2')` | `['R2']` | 1 | **1** |
| Agent 连调两次 `applyMove('R')` | `['R','R']` | 2 | **2** |
| 人类按 `D` 键两次但间隔 > 300ms | `['R','R']` | 2 | **2** |

**关键**：比较基准是**经 §5.4.1 输入整形后的规范化 move 序列**，不是“按了几个键”或“调了几次接口”。键盘 300ms 双击是**输入整形规则**的一部分（把两次 90° 表达为一次 `X2` 意图）；API 没有这个时间窗，两次 `applyMove('R')` 就是两次独立意图。**禁止的是在归并判定之后按 `input_channel` 再做差异化处理**，不是禁止键盘双击归并本身。

**禁止的做法**（会破坏上述一致性）：
- 在归并判定之后按 `input_channel` 差异化处理（例如“键盘已归并、API 再合并一次”或反之）——见 AC-70；
- 在 `keydown` 时就 `move_count + 1`，之后再"抹掉"——见 §5.4.1 约束 2；
- 把 `move_count` 定义为 `Σ layer_count` 或 `Σ (turn_amount/90)`——见公理 G1。

**为什么这条重要**：`move_count` 会进 `Run.metrics`、进结果页排序、进跨阶对比表。口径一旦漂移，所有历史记录就不可比，且**不可逆**。这是全篇最不能"随手实现"的一条。

### 7.2 计时口径

> **v2.0 新增「交付状态」列。** v1.10 列了 7 项计时指标，实现只落了 1 项（`elapsed_ms`），另有两个实现里有、v1.10 没写的指标（`tps`、`paused_total_ms`）。字面真源是 `src/ob-cube/src/contracts.ts` 的 `ChallengeResult`。未交付项一律降为 P1，不再伪装成 MVP 能力。

| 指标 | 定义 | 交付状态 | 备注 |
|---|---|---|---|
| `elapsed_ms` | **活跃时长**：`running` 开始到结束的单调时钟差，**扣除全部 `paused` 段**（v1.9 真暂停） | **已交付** | 用单调时钟，避免系统时间调整干扰。全项目只允许 `challenge/clock.ts` 一处取时间 |
| `paused_total_ms` | 全部暂停段的累计时长 | **已交付** | v1.10 只在 §13.3 的 `metrics` 里提到，未进本表；v2.0 补入。AC-59 要求它进结果页 |
| `pause_count` | 暂停次数 | **已交付** | 同上。AC-59 |
| `tps` | 每秒步数（`move_count / elapsed_ms` 秒） | **已交付** | v1.10 未列入本表，但 §9.1 结果面板"核心指标区"要求"每秒步数"卡；v2.0 补入并统一命名 |
| `wall_elapsed_ms` | 总墙钟时长：开始到结束，不扣除暂停段 | **未实现（P1）** | 仅用于结果页旁证；不参与判定与排序。可由 `elapsed_ms + paused_total_ms` 派生，无需单独存 |
| `agent_think_ms` | 相邻两次交互之间的间隔（观察返回 → 下次操作提交） | **未实现（P1）** | 外部 Agent 的模型推理时间无法直接测量，此项即"端到端等待时间"。可由事件流的 `at_ms` 差派生 |
| `api_call_ms` | 每次 API 调用的本地处理耗时 | **未实现（P2）** | 纯前端下通常 < 1ms，主要价值是排查卡顿，不是评测指标 |
| `first_move_ms` | 开始 → 第一步操作 | **未实现（P1）** | 用于分析"读题"成本。可由首条 `MoveEvent.at_ms` 派生 |
| `solved_at_ms` | 开始 → 首次满足还原条件（进入 `solved_pending`） | **未实现（P1）** | 无还原为 `null`。可由 `solved:true` 的那条事件 `at_ms` 派生 |
| `submit_ms` | 开始 → 成功 `submitSolution()` | **未实现（P1）** | v2.0 删除"自动提交记自动提交时刻"（`auto_submit_on_solved` 默认已改 `false`）。可由 `type:'submit'` 事件的 `at_ms` 派生 |

> **五项未交付指标全部可由已落盘的事件流派生**（`RunEvent.at_ms` + `type`），因此它们不是"数据丢了"，而是"结果对象上没有现成字段"。P1 的实现路径是在 `ChallengeResult` 上补派生 getter，不需要改记录格式、不需要数据迁移。

**诚实边界**：纯前端计时无法防篡改（用户可暂停调试器、改内存）。所有计时结果必须在结果页标注"本机测量，未经服务端校验"。**不得用于对外成绩背书**。

#### 7.2.1 暂停（`paused`）的计时细则 —— "真暂停"（v1.9 推翻 v1.2 裁决）

> **2026-10-26 主理人裁决：暂停 = 冻结计时 + 屏蔽输入 + 冻结画面。**
> v1.2 的"计时不暂停"设计（保留时间压力、保证人机可比）在实测中与用户预期严重冲突
> （"我按暂停也没有实现暂停"）。新语义以用户直觉为准；公平性改由 P6'/结果口径补偿。

| 规则 | 内容 |
|---|---|
| P1' | 暂停冻结计时。`elapsed_ms` = 活跃时长（总墙钟时间扣除全部暂停段）。暂停期间 `remaining_ms` 不变 |
| P2' | 超时判定基于冻结后的 `elapsed_ms`，**暂停中不可能超时**。主循环 tick 与 `applyMove`/`observe` 入口检查保留（防绕过），但暂停中 `elapsed_ms` 不增长 |
| P3' | `paused` 期间 `observe()`、`applyMove()`、`submitSolution()`、`rotateView()` 一律**抛 `E_CHALLENGE_PAUSED`**（PRD 短名 `PAUSED`），不改变状态、不计步（AC-57） |
| P4' | 暂停**仅人类模式可用**。`window.cubeAgent` **不提供** pause/resume 方法；Agent 模式下界面上不渲染暂停按钮 |
| P5' | 暂停次数不设上限，但每次暂停/恢复都记入事件流（`pause` / `resume` 事件，含时间戳），供回放与审计 |
| P6' | 结果必须记录 `pause_count` 与 `paused_total_ms`；发生过暂停的运行，结果页**必须**显示一行："本次运行包含 `N` 次暂停（共 `M` 秒），计时已扣除。"——这是新口径下的诚实标注：暂停给了人类额外思考时间，跨运行对比时必须可见 |
| P7' | 暂停期间 3D 场景冻结在暂停前最后一帧，并叠加半透明遮罩（沿用 UIUX §7.7.2 的遮罩规范），**防止把暂停当无限观察用**；倒计时数字冻结，恢复后从冻结点继续 |

**为什么可以真暂停了（与 v1.2 三条理由的对照）**

1. 人机可比性：Agent 确实没有暂停等价物——所以 P6' 把暂停时长显式写进结果，
   对比口径（`elapsed_ms` 活跃时长 + `paused_total_ms` 旁证）完整保留，谁停了表一眼可见。
2. 限时意义：暂停期间画面被遮罩盖住（P7'），"暂停慢慢看题面"这条路被堵死。
3. 跨运行对比：`elapsed_ms` 语义改为"活跃时长"后，历史对比反而更干净——
   暂停接电话不再污染计时数据。

### 7.3 终止判定

判定顺序固定为：**先判还原 → 再判步数耗尽 → 再判超时 → 再判放弃**。

> **v2.0 裁定：顺序从 v1.10 的「还原 → 超时 → 步数 → 放弃」改为「还原 → 步数 → 超时 → 放弃」**（取 ARCHITECTURE v1.4 §7.4 的口径）。
>
> 理由：这个顺序唯一影响的场景是"第 `move_limit` 步刚好也是超时的那一刻"。步数耗尽是**确定性事件**——第 N 步执行完即可判定，不依赖轮询时机；超时是**轮询事件**——它取决于 tick 何时跑、`observe`/`applyMove` 何时被调。让确定性事件优先，判定结果就不依赖"哪次 tick 先跑到"，同一个 run 重放必然得到同一个结局。若反过来让超时优先，同一个操作序列在不同帧率下可能得到不同结局，这对一个评测平台是不可接受的。
>
> "还原优先于一切"这条不变（AC-27 / AC-75）：只要该步执行后已还原，就进 `solved_pending` 并锁定 `solved`，此后既不判步数耗尽也不判超时。

> **v2.0 关键口径**：`applyMove` 后检测到还原**不是终止**，而是进入 `solved_pending`；**人类与 Agent 一律须显式 `submitSolution()`** 才产生 `ended_solved`（`auto_submit_on_solved` 默认已改为 `false`，见 [`02-user-flow.md`](02-user-flow.md) §2.2 步骤 1 的裁定说明）。因此 `solved_pending` 下"还原优先于超时"：即使此后计时超过 `time_limit_ms`，结果仍锁定为 `solved`。
>
> **交付状态（2026-10-26 更正）**：这条豁免已实现——`session.tick()` 在 `paused` 与 `ended_*` 之外也排除 `solved_pending`，回归用例见 `tests/challenge/session.test.ts` 的「D1：solved_pending 不被超时覆盖」。原登记的 D1 缺陷与「无测试覆盖」结论均已过时。

| 判定 | 触发条件 | 结果状态 | 后续行为 |
|---|---|---|---|
| **还原成功** | `submitSolution()` 时 §7.4 的还原条件成立（`solved_pending` 下提交） | `ended_solved` | 终止，记录 `solved_at_move`；`submit_ms`（P1）取实际提交时刻 |
| **步数耗尽** | 第 `move_limit` 步执行后仍未还原（若该步已还原，按"还原成功"路径进 `solved_pending`） | `ended_move_limit` | **立即终止**；此后任何 `applyMove` 抛 `E_MOVE_LIMIT_REACHED`。不存在"第 `move_limit+1` 步"的真实提交 |
| **超时** | `elapsed_ms > time_limit_ms`。检查点：每次 `applyMove` 入口、`observe` 入口、`getProgress` 入口、主循环每帧 tick（v1.9：暂停中 `elapsed_ms` 冻结、不可能触发）；**若当前是 `solved_pending`，不判超时**，结果保持 `solved`（AC-75，当前未实现，见 D1） | `ended_timeout` | 终止；进行中的动画播放完毕后定格；`applyMove` 此后抛 `E_DEADLINE_EXCEEDED`；**UI 在状态迁移的同一渲染帧内禁用置灰，最迟 200ms**（AC-28）。只读 API 也可能触发这次翻转，因此翻转必须即调 `onMutate()` 同帧同步 UI |
| **主动放弃** | 人类点"放弃"并确认；或 Agent 调 `abandonChallenge(note)` | `ended_abandoned` | 终止，保留已有记录 |
| **提交校验累计失败** | `submitSolution()` 且未还原；同一 run 内累计 3 次（`applyMove` 或观察不重置计数；成功提交会直接结束） | `ended_invalid` | 第 1、2 次失败**不终止**（防止误判终止一次有效尝试），返回 `{accepted:false, reason, mismatch}` 让用户继续；第 3 次终止 |
| **页面关闭/刷新** | `beforeunload` 且状态为 `running` **或 `paused`** | `ended_interrupted` | 尽力写入 localStorage（含已知事件）；重进时提示"有一次未完成的运行" |
| **页面关闭/刷新（已还原未提交）** | `beforeunload` 且状态为 `solved_pending` | `ended_solved`（`submit_ms = null`） | 还原优先于"未提交"；重进时提示"有一次已还原但未提交的运行" |
| **内部错误** | 引擎抛出未捕获异常且无法继续 | 现有 `ended_*` + `ended_reason` 记错误栈摘要 | 终止；结果页允许"复制诊断摘要"（纯文本，不新增导入导出能力）。**v2.0 裁定：不新增第 7 个终态**——`internal_error` 是"为什么结束"，不是"结束成什么样"，用 `ended_reason` 表达即可，避免终态枚举膨胀 |

**结束后写操作的错误码优先级（唯一口径）**：`ended_timeout` → `E_DEADLINE_EXCEEDED`；`ended_move_limit` → `E_MOVE_LIMIT_REACHED`；其余已结束状态 → `E_CHALLENGE_ENDED`。不使用 HTTP 状态码语义。完整映射表见 [`../execution/agent-api.md`](../execution/agent-api.md)。

### 7.4 还原判定标准（2/3/4 阶差异）

#### 总原则

> **已还原 ⟺ 存在某个整体朝向 `o`，使 6 个面各自单色，且该朝向下"颜色 → 面"的映射属于标准配色方案的 24 个合法旋转之一。**

为什么需要朝向归一化：玩家/Agent 完全可能在还原后改变观察方向（通过视角操作，不是通过 `applyMove`，见 §5.3.4），4 阶还可能在还原过程中自然地换过握持方向。物理上已还原，但"哪一面朝上"不唯一。若判定绑定固定朝向，会把合法还原判为失败。

#### 各阶差异

| 阶数 | 判定实现 | 关键差异 | 为什么 |
|---|---|---|---|
| **2×2** | 24 种朝向归一化后检查 6 面各单色 | **无中心块、无棱块**，仅 8 个角块。单色 6 面 ⟺ 还原 | 2 阶没有任何"锚点"能固定朝向，只能靠归一化 |
| **3×3** | 同样 24 朝向归一化后检查 6 面各单色（实践中可简化为直接检查 6 面单色，见右） | **中心块相对彼此固定**，因此"6 面单色"本身已蕴含"配色正确"——中心块无法被单独移动，若 6 面单色则必然是合法配色 | 3 阶的 24 种整体旋转只是把"白上绿前"转成别的朝向，不改变"每面单色"这一事实。所以 3 阶可以跳过枚举，直接判 6 面单色 |
| **4×4** | **必须做 24 朝向枚举 + 配色合法性校验** | **中心块可动、无固定朝向**：① 4 个中心块同色时互相不可区分，不能用"中心块朝向"定义还原；② 6 面单色是**必要但不充分**条件——理论上可能存在"6 面单色但中心块排列为镜像配色"的非法陈列（由物理拆装造成，合法转动无法达成）；③ 存在 OLL/PLL parity，但若 6 面单色则 parity 必然已消解，无需单独检测 | 这是三阶中唯一需要显式枚举 24 种朝向 + 校验配色映射的阶数 |

#### 4 阶的产品级硬要求

> **算法实现（24 朝向枚举、手性 `det = +1` 校验、中心 2×2 取映射）已移交 [`../execution/engine.md`](../execution/engine.md) §3.4，本节只保留产品口径。**

1. **必须做全脸单色检查**（v1.10 #52）：对每一面，检查该面全部 `N×N` 个贴纸是否同色。4 阶为 4×4 = 16 块，**不得只检查中心 2×2 的 4 块**；中心 2×2 只用于确定"该面是什么颜色"。
2. **6 面单色是必要不充分条件**：还必须校验"面 → 颜色"映射属于标准配色的 24 个合法旋转之一（AC-25）。镜像配色（合法转动无法达成，只能由物理拆装产生）必须判**未还原**（AC-26）。
3. **镜像配色的对外错误码是 P1 缺口**：AC-26 原文要求返回 `INVALID_STATE`，但代码的 `ERROR_CODES` 里没有 `E_INVALID_STATE`，镜像配色目前只在内部以 `mismatch.reason = 'invalid-scheme'` 区分。v2.0 裁定：**AC-26 的判据改为"必须判未还原，且未还原原因可区分"（已满足）**，补对外 `E_INVALID_STATE` 码列为 P1。理由：真实流程中不可能出现镜像配色（只有未来的非法导入路径会触发），为它现在扩错误码表不划算。

#### 判定时机

| 时机 | 是否判定 | 说明 |
|---|---|---|
| 每次 `applyMove` 成功后 | 是 | 若已还原，进入 `solved_pending`，3D 场景播一次“已还原”高亮；**不直接进入任何 `ended_*` 终态** |
| `submitSolution()` | 是 | 唯一正式结算点；`solved_pending` 下提交成功 → `finished/solved`；`running` 下未还原 → `NOT_SOLVED` |
| 达到步数上限时 | 是 | 先判还原；若已还原按 `solved`，否则 `move_limit` |

**关于"自动结束"（v2.0 定稿）**：`applyMove` 后检测到已还原**不直接终止挑战**，而是进入 `solved_pending`。**人类与 Agent 一律须显式 `submitSolution()`** 才进入 `ended_solved`——`auto_submit_on_solved` 默认已改为 `false`（v1.10 的"人类默认自动提交"从未实现，v2.0 改文档对齐代码，裁定理由见 [`02-user-flow.md`](02-user-flow.md) §2.2 步骤 1）。

理由：人类玩家可能在还原后继续做整体旋转演示；Agent 可能想再确认一次观察。给人类一条自动结算捷径本身就是对 Agent 的差异化对待，与"同一套引擎、同一份计步规则"的产品定义相冲突。

`solved_pending` 下 `applyMove` 抛 `E_CUBE_ALREADY_SOLVED`，`observe` / `rotateView` / `submitSolution` 仍可用；**不可暂停**；**不可被判超时**（AC-75，当前未实现，见缺陷 D1）。
