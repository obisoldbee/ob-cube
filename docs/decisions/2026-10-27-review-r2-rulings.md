## R-7：哪些事件会关闭归并窗口

### 问题

R2-03 指出：`D → 方向键 → D` 仍会归并。归并时 `commitMerged` 撤掉第一次转动的
事件，后面的 view 事件保留原序号，新事件用 `events.length + 1` 编号，于是出现
**重复序号**（`[1,3,3]`）与**数组内时间倒序**（`[0,80,10]`）。

### 裁定

**换视角、显式观察、暂停/继续、提交、放弃都会关闭归并窗口；事件序号改为独立递增计数。**

- 会话层 `closeMergeWindow()`：清 `lastTurn`，并把仍在推迟中的「步数耗尽」立即结算。
- 键盘层：任何非面键的按键都会清掉 `last`，不再对上层宣称 `merged: true`。
- `pushEvent` 用 `++eventSeq`，与数组长度解耦。

### 理由

1. 归并是**同一组双击**的整形，插入任何可见动作后就不该再算同一次输入。
2. 撤事件必然留下序号空洞。空洞是可解释的（少一条），重号是不可恢复的（两条事件自称同一位）。
3. 只在键盘层清 `last` 不够：API 的 `rotateView` 也能插进来，所以窗口的权威在会话层。

### 影响

- `D → observe → D`、`D → pause → D` 都变成两次独立转动（各 1 步）。
- 步数耗尽若正卡在推迟判定上，换视角/观察会立刻按上限结算，不会借视角操作绕过。
- 归并事件仍是 `merged_from: ['R','R']`、`turn_amount: 180`，只是序号可能有空洞。

## R-8：「一次观察」在界面侧含义

### 问题

R-4 定义了「交付一份新颜色布局 = 一次观察」，但 `peekObservation()` 只对
`restricted` 生效。`after_move` 的面板仍直接读实时状态，用旧编号展示新布局（探针 P02）。
另外，成功 `observe()` 不通知界面，restricted 档 Agent 拿到 `o1` 时面板还停在
「尚未获得观察」（探针 P01）。人类三个输入通道的预算消耗也不一致。

### 裁定

**门控档（`restricted` / `after_move`）的面板只显示最后一次已交付快照，并提供显式获取入口。**

| 入口 | 是否交付 | 是否消耗预算 |
|---|---|---|
| `observe()`（API 或界面按钮） | 是 | 是（仅 restricted） |
| `applyMove().next_observation`（Agent） | 是（`after_move` 除外） | 是（仅 restricted） |
| 按钮 / 键盘 / 记法框 | 否 | 否 |
| 观察面板（`peekObservation`） | 否，只显示已交付那份 | 否 |

- 面板新增「获取观察」按钮，只在门控档可见；`after_move` 与 `restricted` 都靠它取用。
- 成功 `observe()` 无条件触发宿主回调（交付是可见状态变化）。
- 人类三个通道统一不自动交付：同一次物理动作不因入口不同而少看一次或多烧一次预算。

### 理由

1. 只要有一个入口能「不交付也看到最新颜色」，交付规则就只是装饰。
2. `after_move` 的语义是「转动后开放**一次**观察」，自动塞回去等于取消门控。
3. 人类与 Agent 的差别应当只在「走哪个接口」，不在「同一次动作算不算一次观察」。

### 影响

- `ObservationView` 增加 `canObserve` / `budgetLeft`；`UiPorts` 增加 `observe()`。
- 人类在 restricted 档若从不点「获取观察」，面板会一直是空的（这是正确行为，不是故障）。

## R-9：结果卡片与历史中位数的口径

### 问题

R2-05：卡片显示 `elapsed_ms`（含还原后等待提交），中位数却取 `solved_at_ms`。
一局「10 秒还原、30 秒提交」会同时显示「总耗时 30 秒」与「同题中位 10 秒」。

### 裁定

**OD-06 裁定前，当前值与历史值统一用 `elapsed_ms`（总耗时），标签写明「中位总耗时」。**

`services/history.ts` 里保留单点开关 `SCORE_METRIC`：改成 `'solved'` 即切到还原用时，
但**必须同时**改结果卡片主指标、标签与 TPS 分母——否则又回到两个终点混用。

### 理由

1. 混用比选错更糟：它让人无法判断"我比历史快"到底是真快还是口径不同。
2. 主指标口径是产品决策（OD-06），不该由一次缺陷修复顺手改掉。
3. 单点开关让裁定后只改一处，且改不完整会被类型与测试拦住。

### 影响

- 历史样本不再优先 `solved_at_ms`；缺失该字段的旧记录不再被特殊对待。
- R12 回归用例的期望值随之改为按总耗时计算。

## Q01：受限观察的预算是否覆盖画面通道（**未决，需产品裁定**）

R-4 原文两处表述不一致：开头说「所有入口同规则」，理由第 3 条又说 3D 画面可以持续
显示实时颜色（预算只约束结构化快照）。当前实现属于后者。

| 规则 | 行为 | 评测含义 |
|---|---|---|
| A. 结构化观察配额（**当前实现**） | 预算只约束 `observe` 与自动快照；3D/2D 画面照常显示当前授权面 | 只比较「相同结构化接口规则」下的 Agent；不能与可持续看图的 GUI 运行混组 |
| B. 全渠道信息受限 | 预算耗尽后画面冻结在最后交付内容或全部遮蔽 | 可以比较「相同信息预算」下的 GUI/API Agent，但要同时固定操作与计时规则 |

未选之前，本轮只做了两件两种规则下都需要的事：

1. 面板与 API 用同一套交付规则（不再有免费旁路）。
2. 结果页与结果记录保留 `observation_mode`，便于将来按规则分组统计。

若选 B，需要新增「预算耗尽后冻结画面」的渲染分支，并为 GUI Agent 重新定义操作录入口径；
这不是一次缺陷修复能顺手带上的改动。裁定见 `docs/decisions/OPEN-DECISIONS.md` 的 OD-09。
