# ADR-004：纯前端交付，不引入任何后端

## Status

Accepted（2026-10-25），由 Phase 0 需求澄清会确立，本文档补全技术论证与代价记录。

## Background

用户原始需求是「实现完整的前端界面与交互逻辑」。但附件里的 PRD 草稿（`writing-block.md`）在描述 AI Agent 接入时，写了一整套服务端语义：

- 「隐藏状态必须由数据访问层执行，而不只是用 CSS 遮住」（2.2）
- 「所有观察限制均由服务端强制执行」（7.2）
- 「模型凭证保存在服务端，不进入浏览器」（6.4）
- 「API 应提供认证、挑战会话隔离、请求限流、超时处理、错误码及操作幂等性支持」（6.4）
- 「计时使用服务端单调时钟」（8.1）

这些要求如果逐条实现，产品就从「一个网页工具」变成「一个有账号与评测队列的 SaaS」。两者在交付形态、成本、以及用户实际使用方式上差距巨大，必须先裁决。

## Decision

**纯前端，不做后端。** 具体边界：

- 无服务端代码、无数据库、无账号体系、无云端题库、无鉴权、无限流。
- 状态、题库、运行记录全部在浏览器内存与 `localStorage`。
- 交付形态为 `npm run build` 产出静态站点，可放到任意静态托管。
- Agent 通过页面内 `window.cubeAgent` JS API 接入，与人类按钮走同一条调用路径。

理由：

1. 用户要求交付的是前端界面与交互逻辑，未提出账号、云端题库、多人协作需求。
2. 本产品是单机评测工具：题目在本地生成、成绩在本地存储，不存在多租户数据隔离需求。
3. 引入后端会让「下载即用、静态托管」的交付形态丢失。而这一形态对本产品是核心价值：Agent 开发者可以直接在本地跑评测，不需要申请账号或部署服务。
4. PRD 草稿里的服务端语义，绝大部分是「为了让观察权限不可绕过」。但本产品的目标用户是配合评测的 Agent 开发者，不是对抗性攻击者。为一个不存在的威胁模型付出一整套后端的成本，收益与成本不匹配。

**代价必须如实记录，且必须写进 PRD 与 UI 文案：**

> 观察权限门控只能在应用层实现，无法构成安全沙箱。用户仍可通过 DevTools 读内存、修改源码或打补丁绕过。蒙尘模式约束的是「诚实 Agent 的信息获取路径」，用于评测「在信息受限下求解」的能力，**不是防作弊**。产品不得以「防作弊」作为卖点宣传。

技术上如何把这个代价压到最小：

1. **单一颜色出口。** `challenge/projection.ts` 是唯一能产出颜色的函数；`ready` 阶段该出口整体关闭，渲染层拿到的是「遮蔽指令」而不是颜色数据。这与 PRD「不得只用 CSS 遮住」的要求在意图上一致，只是执行位置从服务端移到应用层。
2. **观察策略单点实现。** `observation-policy.ts` 暴露 `visibleFaces(policy, view)`，被投影层与渲染层共同调用。这保证「屏幕上能看到的」与「API 能读到的」不会打架——单机产品里最容易出的漏洞不是恶意绕过，而是这两者不一致。
3. **不泄露摘要。** 进行中的观察响应不包含 `scramble`、`seed`、状态指纹。指纹虽然只有 16 字符，但是一个强预言机：受限观察下的 Agent 可以本地枚举状态、算指纹、比对，从而在完全看不到颜色的情况下反推出局面。这条由 T-20 的递归键名扫描锁住。
4. **时间用单调时钟。** `performance.now()` 是单调的，满足 PRD「不能只依赖浏览器显示的倒计时」的实质要求（记录的是真实经过时间，而不是浮点累加的倒计时值）。`Date.now()` 只在创建记录时用于时间戳。

被明确放弃的能力（不是「以后再说」，是 v1 不做）：

- 平台托管 Agent（服务端持有模型凭证并代调模型）
- 外部 Agent 的远程接入（需要认证、会话隔离、限流）
- 跨设备同步与排行榜
- 服务端强制的观察限制

## Consequences

正面：

- 交付物是一个静态目录，`npm run build` 后即可分发；Agent 开发者的接入成本是一行 `window.cubeAgent`。
- 没有部署、没有运维、没有密钥管理、没有账单。MVP 总成本接近零。
- 引擎与规则层是纯计算，可以在 Node 环境 100% 单测，不需要起服务、不需要 mock 网络。
- 计时、状态、日志全在同一进程内，事件顺序天然一致，回放一致性容易保证。

负面：

- **无法防作弊**，如上。这是永久性限制，不会因为迭代而消失。
- **localStorage 是唯一的持久层**，受配额（通常 5MB）与同步阻塞写的影响。这带来两条硬约束：写入必须 debounce + 在关键时点强制 flush（否则 `setItem` 会吃掉帧预算，甚至造成「因为写盘所以超时」的荒谬结论）；必须有淘汰策略与 `QuotaExceededError` 处理，且不得静默吞掉。
- **数据只在单浏览器单 profile 内**。换设备、清缓存即丢失。必须提供「导出 JSON」能力，且导出的格式就是 `ChallengeResult`，不需要额外设计。
- **多轮实验（PRD 3.1 的「题目重复次数」）只能在本地串行**。并发跑多个 Agent 需要多开标签页，且各自独立存储。
- 若未来要接远程 Agent，`window.cubeAgent` 的返回包已经带 `httpLike` 语义的错误码，但认证、会话隔离、限流需要从零设计与实现，不是「包一层」就能完成。
