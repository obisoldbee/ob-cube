# ADR-003：整体旋转（x/y/z）只转相机，不进入魔方状态

## Status

Accepted（2026-10-25）

## Background

魔方记法里的 `x / y / z` 表示「拿着整个魔方转一下」。它在真实速拧里是必要的：选手需要把不便操作的面转到手边。因此一个完整的记法系统必须能表达它。

问题在于：它算不算一步？改不改变状态？

PRD 对此已有明确回答（4.2）：「视角旋转只改变观察方向，不改变魔方内部状态，不计入魔方转动步数」；4.4 又强调「每次实际执行的魔方层转动计为一步，整体视角旋转不计步」。同时 PRD 4.2 要求「允许用户通过视角旋转依次观察全部六个面」。

但 PRD 没有回答一个实现层面的追问：**Agent 需要 reorientation 时怎么办？** 如果一个 Agent 的求解算法是在某个特定朝向下推导的，它需要把「我看到的世界」对齐到自己的参考系。如果 `x/y/z` 完全不可用，它可能被迫在错误朝向下推理。

## Decision

**`x / y / z` 不进入魔方状态，不计步，不走 `applyMove`。它们属于观察通道，由 `rotateView` 承担。**

三条理由：

1. **与 PRD 4.2 一致。** 若把整体旋转写进 state，就必须回答「计不计步」这个 PRD 已经回答过的问题，并引入第二种「合法但不计步的状态变更路径」。一条规则有一个出口，比两个出口容易守住。
2. **保护还原判定。** 状态里不含朝向，还原判定就是「六面各自单色」，天然朝向无关，4 阶「整体朝向不唯一」的争议自动消解。一旦允许整体旋转入 state，就必须额外维护「当前朝向」并让 `solved` 考虑它，那个争议会立刻回来，且会引入「转了多少次算回到标准朝向」的判断。
3. **保护计步规则。** HTM 的语义是「层转动次数」。整体旋转若入 state 但不计步，就会出现「状态变了但步数没变」的记录，回放与日志的一致性校验（指纹链）会变得难以解释。

具体落地：

- 记法解析层**仍然支持**解析 `x / y / z`（产出 `kind: 'rotation'`），因为题目导入导出、UI 键盘映射、以及未来可能的外部算法文本都会用到它。但调用链上它被路由到 `rotateView`。
- `applyMove` 见到 `x / y / z` 报 `E_NOTATION_ORIENTATION_NOT_MOVABLE`，`hint` 里明确提示改用 `rotateView`。
- `rotateView` 提供两种请求形态：
  - 相对：`{ kind: 'relative', axis, quarter_turns }`
  - 绝对：`{ kind: 'absolute', up, front }`（两参数必须不共线）
- `observe()` 返回 `view.matrix`：一个 3×3 整数矩阵，把魔方坐标系三轴映射到观察者坐标系。Agent 拿到矩阵后可以自行把看到的颜色矩阵换算到自己的参考系里做推理，**这个换算不需要也不应该污染 state**。

同时裁决了一个相关形态：**覆盖全部 N 层的层转动被拒绝**（`E_MOVE_COVERS_ALL_LAYERS`）。理由：在 facelet 语义下，绕某轴转全部 N 层在几何上等价于一次整体旋转，结果是「六面仍各自单色」。允许它会让 Agent 可以用「不计分但不改变相对结构」的方式刷步数，也会让「能执行的动作」与「会改变状态的动作」不再重合。若调用方的真实意图是改观察方向，`hint` 会引导它用 `rotateView`。

## Consequences

正面：

- 状态机少一个维度，还原判定、指纹、回放三条链路都因此变简单。
- 「界面上看到的朝向」与「引擎里的状态」彻底解耦，视觉层可以自由拖动而无需通知引擎。
- Agent 的 reorientation 需求被完整满足：24 个离散朝向全部可达（绝对形态），并且拿得到坐标变换矩阵（`view.matrix`）。

负面与需要说清楚的地方：

- **`x/y/z` 不能用来「在解题过程中改变朝向再继续」**。一个依赖整体旋转的算法文本（例如某些速拧教程的逐步演示）不能直接作为 move 序列喂给引擎，必须先做一次「把整体旋转折算进后续层转动」的转换。这个转换器不在 v1 范围，属于 out-of-scope，但必须在文档里写明，避免后续有人以为「解析成功了就应该能执行」。
- **受限观察模式下存在一个语义张力**：用户可以用鼠标把相机拖到看见 D 面，但 `view` 没变，因此 D 面仍是遮蔽材质。这是刻意设计（「能拖到」不等于「能看到」），但需要在 UI 上给用户明确反馈（例如遮蔽面显示禁止图标与「未授权」提示），否则会被当成 bug。
- **`view` 与相机是两个状态**。必须在实现上保持「拖动只改相机」这条纪律，否则受限模式下会出现「拖一下就绕过观察限制」的漏洞。`camera-rig.ts` 的公共接口不暴露「从相机反推 view」的方法，就是为了让这条纪律无法被误用。
