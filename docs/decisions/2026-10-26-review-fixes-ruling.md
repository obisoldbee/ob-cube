## R-1：AC-42（13 字段）与 AC-43（`applyMove` 必须回填 `observation_id`）互斥

### 问题

- AC-42（v2.0 修订）冻结 `applyMove` 恰好 13 个字段，**不含根级 `observation_id`**。
- AC-43 要求「后续 `applyMove` 的返回值中 `observation_id` 必须与该 `observation_id` 一致」。
- 代码现实是第 16 个字段：外层 API 额外塞了 `ok`、根级 `observation_id`、`based_on_observation_id`。

两条 AC 无法同时成立：要么 AC-42 破，要么 AC-43 破。

### 裁定

**AC-43 的意图由事件字段承载，`applyMove` 返回值收敛回 13 字段。**

- 新增 `RunEvent.based_on_observation_id`：调用方声明「本次决策依据哪次观察」时原样落库；未声明时取事件生成时刻的当前观察 id。
- `RunEvent.observation_id` 保持原语义（该操作发生时手上的那份观察）。
- 删除 `ok`（失败本来就走异常，这个键恒为 `true`，纯冗余）与根级 `observation_id`（在 `next_observation` 里已有）。

### 理由

1. AC-42 已标注「以实现为准、改回 8 字段需重写全部调用方」，v2.0 明确选了 13 字段这条路。
2. AC-43 要的是**可追溯性**，不是「必须出现在返回值里」。写进事件比写在返回值更强：返回值会丢，事件会随记录落盘。
3. 保留 `ok: true` 会诱导调用方写 `if (res.ok)`——而失败根本不会返回，这个分支永远不可达，是误导性 API。

### 影响

- `agent.applyMove()` 返回值字段数从 16 → 13；R07 与 `tests/agent/read-flip-sync.test.ts` 直接断言字段集合。
- `observation_lag` 可由此派生，不新增字段。

## R-2：`next_observation` 在预算用尽时是「空对象」还是 `null`

### 问题

受限观察只有 24 次预算，但 `applyMove` 每次都返回一份新观察。若继续返回，预算形同虚设；若返回空对象，调用方无法区分「没有观察」与「魔方是空的」。

### 裁定

**`next_observation: Observation | null`。** `null` = 当前不可交付。

### 理由

1. PRD §8.2 C6（观察模式执行）与 §8.6（受限观察）都以「限制信息」为目的。返回空对象会让 `face_colors: {}` 同时表示「没授权」和「读失败」。
2. `null` 是唯一能让 Agent 明确「别再指望这一步拿到颜色」的表达，键仍存在，不破坏「键必须存在」的规则。
3. 同一条规则适用于 `after_move`：那一档的语义是「转动后开放**一次**观察」，若 `applyMove` 顺手塞回去，门控就没有存在意义——因此该档不做自动交付，由调用方显式 `observe()` 取。

### 影响

- 5 档观察模式中，`restricted`（预算耗尽）与 `after_move`（从不自动交付）会返回 `null`；其余三档不受影响。
- 会话层新增**唯一交付口** `deliverObservation()`：显式 `observe()` 与自动交付共用，预算、编号、after_move 步数三者同源。

## R-3：双击归并与「步数耗尽」判定谁先

### 问题

PRD §5.4 要求「输入整形早于定稿，再做计步与终止判定」。旧实现是**先提交再改日志**：

- 第一次 90° 提交时就做了计步与终止判定；
- 步数上限只剩 1 步时，第一次按键先判负，第二次按键直接被终态守卫拒绝；
- 结果：`R2` 能在 1 步内还原，双击同一动作却判 `ended_move_limit`。

### 裁定

**归并前移到提交点之前；键盘 90° 的步数耗尽判定推迟一个归并窗口（300ms）。**

- 会话层保存「上一次 90°」的**转前状态快照**；第二次同向按键到达时回滚到转前、撤掉半成品事件、一次性执行 180°，终止判定只做一次。
- 键盘通道的 90° 若恰好撞上步数上限，先不判负，把 deadline 交给 `tick()`；窗口内没有第二次按键就在窗口关闭时判负。

### 理由

1. 只有「回到转前状态重算」才能保证与显式 `R2` **完全同构**（同一份 from/to 指纹、同一条事件、同一次判定）。在提交后修补日志必然留下「已经判过负」的痕迹。
2. 推迟窗口只作用于键盘 90°：按钮与记法输入不参与双击，不该被延迟判负。
3. 推迟不等于取消——窗口关闭后仍按步数耗尽结算，R03 的三个用例分别覆盖「显式 R2」「合法双击」「窗口关闭后判负」。

### 影响

- 人机同源（AC-45 / AC-70）的比较基准仍是「整形后的规范化 move 序列」，实现现在与之一致。
- 键盘 `2 D D` 必须保留层集合：第一次面键会清前缀，第二次按键沿用上一次的层规格，否则得到 `Rw` + `R` 而不是 `Rw2`（R04）。

## R-4：「一次观察」的定义

### 问题

`observe()` 消耗预算，`applyMove` 自动返回的观察不消耗；观察面板还能直接读实时状态。同一档观察模式有三个入口、两套规则。

### 裁定

**「一次观察」= 向参与者交付一份新的颜色布局。所有入口同规则。**

| 入口 | 是否交付 | 是否消耗预算 | 是否换编号 |
|---|---|---|---|
| `observe()` | 是（受 after_move 门控） | 是 | 是 |
| `applyMove().next_observation` | 是（`after_move` 档除外） | 是 | 是 |
| 观察面板（`peekObservation`） | 否 | 否 | 否，返回**已交付的那份** |
| 3D 画面 | 只显示授权面（`setReveal` 遮罩） | 否 | — |

### 理由

1. 只要存在一个「不消耗预算也能拿到最新颜色」的入口，24 次预算就只是装饰。
2. 面板读实时状态、相机可拖到背面，是同一个漏洞的两个入口：一个在 DOM，一个在渲染。两个都要堵。
3. 3D 画面仍然显示三面是**物理模型**（看着一个真魔方转动，你自然看得到当前三面），预算约束的是「结构化快照的交付次数」，不是「能不能看」。

### 影响

- `peekObservation()` 在 `restricted` 档返回 `lastDelivered`，无交付时返回空授权投影（面板显示 `no-observation` 文案）。
- 相机拖到未授权面看到的是遮蔽材质，不是颜色。

## R-5：`solved_pending` 刷新后的结算

### 问题

PRD §7.3 要求「`solved_pending` 关闭或刷新页面时保存为 `ended_solved`，`submit_ms` 保持 `null`」。实现里 `interrupt()` 与 `beforeunload` 都只接受 `running` / `paused`，`solved_pending` 被直接跳过——已还原的成功记录会凭空消失。

### 裁定

**`interrupt()` 接受 `solved_pending`，结算为 `ended_solved`；`submit_ms` 保持 `null`（没有提交事件）。**

### 理由

「已还原」是既成事实，不因没点提交而作废；`submit_ms` 为 `null` 准确表达「没有提交动作」，两者并不矛盾。不引入「保存成功检查点」的第二条写盘路径——那会与结束落盘重复。

### 影响

- `SubmitResult.accepted = true`，`reason` 明确写成「页面在已还原待提交时关闭（未提交，`submit_ms` 为 null）」。
- R08 覆盖状态、`solved`、`submit_ms` 与 `end` 事件四项。

## R-6：事件超限时丢头还是丢尾

### 问题

旧实现超过 2000 条时丢 view 事件、再截取**前** 2000 条非 view 事件。若 move 事件本身超限，最后几步与 `end` 事件一起被丢掉——结果页与回放都缺结局。

### 裁定

**先丢 view 事件；非 view 事件仍超限时保留尾部，并落 `events_dropped`。**

### 理由

复盘要看的是「最后怎么结束的」。丢头至少保住结局与最近几步；丢尾则把胜负证据一起丢掉。同时只标 `events_truncated: true` 无法判断缺口大小，因此补 `events_dropped`。

### 影响

- 分块持久化（报告第二部分第 7 条）不在本轮范围，属于 PRD 级设计变更，已登记进 `OPEN-DECISIONS.md`。
