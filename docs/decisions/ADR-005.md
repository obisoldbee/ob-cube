# ADR-005：渲染采用 cubie mesh，且贴纸颜色由 facelet 状态派生

## Status

Accepted（2026-10-25）

## Background

ADR-001 已经决定状态模型是 facelet。渲染层现在必须解决一个矛盾：**状态以贴纸为粒度，但视觉上人们看到的是「块」**——块与块之间有缝隙、有倒角、有塑料质感。如果渲染只是「六个面上贴彩色方块」，会得到一张平铺的色块图，失去魔方的可读性与操作反馈。

两个候选：

- **贴纸 plane 方案**：每个外表面贴纸一个平面，直接贴在六个面上。
- **cubie mesh 方案**：每个小块一个盒体，贴纸是盒体朝外面的子节点。

难点不在「画出来」，而在**状态与视觉如何保持同步**。这是本项目最容易出隐藏 bug 的地方：如果渲染层自己维护一套「哪块在哪」，就会出现两份真相，而两份真相一定会漂移。

另一个必须同时解决的问题是**转动动画的浮点漂移**。本类项目的经典坑是：动画结束时用 `quaternion.multiply(delta)` 或 `position.add(offset)` 累积，误差随步数线性增长，几百步后魔方肉眼可见地歪掉、缝隙不均。

## Decision

**采用 cubie mesh 方案，并加上一条关键设计：每个 cubie 只回答「我这一格朝外的面该显示什么颜色」，颜色由 facelet 状态逐面派生。渲染层不持有任何独立的魔方语义。**

也就是说：不维护块身份、不维护块朝向、不做「块到 mesh」的映射表。一个位于格 `(i,j,k)` 的 cubie，它朝外的三个方向分别对应三个 slot；每步之后读这三个 slot 的颜色，写进三个贴纸材质。仅此而已。

组成与规模：

- cubie body：`RoundedBoxGeometry(0.95, 0.95, 0.95, 2, 0.08)`，单材质（体色 Token），提供缝隙与倒角。
- 贴纸：每个朝外方向一个圆角薄平面，尺寸 `0.82`，法向偏移 `0.476`，作为 body 的子节点，局部变换在构造时固定、永不修改。
- 数量：4 阶 56 个 body + 96 个贴纸 = 152 个 draw call（2 阶 32、3 阶 80）。
- 默认关闭 shadowMap（4 阶 96 贴纸开阴影在集显上是已知掉帧源）。

对比矩阵：

| 维度 | 贴纸 plane | cubie mesh |
|---|---|---|
| 与 facelet 的映射 | 需要「贴纸身份随块移动」的二次绑定，颜色与位置双通道 | 颜色由状态派生（纯函数），无身份绑定 |
| 动画 | 需要结束瞬间换色，易出现跳变边界帧 | 物理旋转，结束瞬间重算与物理结果必然一致 |
| 4 阶规模 | 96 平面 | 56 body + 96 贴纸 |
| 视觉质感 | 平面色块，缺缝隙与倒角 | 体块、缝隙、倒角、内黑体 |
| 倒角 | 需自绘圆角路径 | `RoundedBoxGeometry` 现成 |
| 实现风险 | 状态同步风险高 | 建模略多，但同步逻辑是纯函数 |

动画与漂移的处理（这是本 ADR 的第二个决策）：

**规则：任何 `Object3D` 的变换都不得做累积乘法或加法。变换的唯一来源是「整数格坐标 → 精确变换」的纯函数。**

提交时序：记下受影响的 cubie 集合（用 engine 的同一份层判定，不重复实现）→ 建临时 pivot Group → reparent 进去 → 每帧设 `pivot.quaternion` 为 `axisAngle(axis, angle·easedT)`，其中 `angle` 来自 `{90°, 180°, 270°}` 整数表 → 到 `t=1` 时**先**向 engine 提交 move，**再**把每个 cubie 的 position/quaternion 直接 set 为由整数格坐标与整数朝向矩阵重算的精确值，然后 reparent 回静态父节点、pivot 归零 → 最后按新状态重算 96 个贴纸颜色。

关键点：所有角度都是 `π/2` 的整数倍，二进制可精确表示；每步是**重新计算**而不是叠加，因此不存在累积误差这件事。

## Consequences

正面：

- **状态与视觉之间没有第二份真相**，消灭了「渲染状态与引擎状态不一致」这个 bug 类别。
- 动画与颜色在两个时刻都必然一致：动画期间 cubie 携带转前的颜色（正确）；提交后按新状态重算（正确）。两者在拓扑上必然吻合，因为置换正是把那些面片搬到了那一格。**不需要「换色补偿」逻辑**。
- 浮点漂移被结构性消除，而不是靠「定期重置」这种补丁。
- `turn-animator` 只操作 `Object3D` 图，不接触 `WebGLRenderer`，而 three 的数学类在 Node 里可用，因此**动画变换逻辑可以在 vitest 的 node 环境里直接单测**（T-13：500 步后 `maxAbsDiff === 0`）。
- 若未来换状态模型（例如为了接求解器而引入 cubie 状态），渲染层只需要换一个派生函数，动画与场景代码不动。

负面与代价：

- **每步要重算贴纸颜色**（4 阶 96 次材质写）。这是 `O(N²)` 的常量工作，量级远小于一帧预算，但必须在提交时点做一次，不能每帧做。
- **152 个 draw call 是明确的性能预算**。桌面端不是瓶颈，但在低端集显上需要 §8.5 的降级链。优化路径（body 合并为 `InstancedMesh`）已留好，v1 故意不做——提前实例化会把动画代码复杂度抬一个台阶，而收益在桌面端不可观测。
- **`RoundedBoxGeometry` 是 addons**，必须从 `three/addons/geometries/RoundedBoxGeometry.js` 导入（带 `.js` 扩展名），类型来自 `@types/three`。这是版本锚定层面必须记住的一条。
- **体块方案让「内侧面」成为可见的一部分**（缝隙里能看到黑体）。这意味着体色 Token 必须与面板背景有足够对比，否则缝隙会糊成一片。这一条要交给设计师在视觉验收时确认。
