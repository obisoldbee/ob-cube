## 15. 竞品分析

### 15.1 直接竞品：速拧计时器

| 竞品 | 核心功能 | 优势 | 劣势（来自用户差评与官方限制） | 定价 |
|---|---|---|---|---|
| **csTimer**（cstimer.net） | 打乱生成（对齐 TNoodle 系算法）、虚拟魔方、成绩统计（ao5/ao12/ao50/ao100）、8 秒/15 秒观察提醒、音拍器、批量打乱、备份到本地/自有服务器/Google 存储、多种求解器（Cross/Xcross/2×2 面） | 功能覆盖最全；离线可用的浏览器缓存机制；GPLv3 开源；阶数切换用 `Alt+2~7` 一个动作完成；虚拟魔方有一套完整的 3 行键位表，宽转/内层/整体旋转全部有键 | 移动端网页体验被社区直接吐槽（"跟用铁勺子计时差不多"）；虚拟魔方键位表是 3 行 × 10 列的密集布局，新用户几乎无法靠规律记忆，必须贴着一张表操作；无任何程序化接口，第三方无法驱动它做自动化评测；UI 信息密度极高 | 免费，GPLv3 |
| **CubeDesk**（cubedesk.io） | 计时器、Ao5/12/50/100/1000 图表、750+ 算法训练器（OLL/PLL 等）、自定义训练器、1v1 对战、社区、焦点模式、StackMat 支持、手动录入、主题定制、从 csTimer 一键迁移 | 设计现代（社区评价"远超 csTimer"）；训练器生态最强；热键 + 专注模式做得好；数据分析维度细（时间分布、生涯统计、分事件统计） | GPL-3.0 且**依赖云端**：官方明说"CubeDesk 完全免费，但云不是免费的"，因此有 Pro 会员；社区反馈开放 issue 多、活跃贡献者少，新功能与修 bug 慢；自托管需 Node 环境 + 云服务配置，不是"一个静态站点"；无程序化接口 | 免费 + Pro 会员（价格按云成本） |
| **Twisty Timer**（Android/iOS 原生） | TNoodle 同源随机态打乱（覆盖全部官方项目）、每个打乱的可视化表示、OLL/PLL 算法参考、20+ 主题、自定义配色、观察开关、手动录入、CSV 导出、分段统计 | 真原生 App（社区公认"唯一能用的手机端计时器"）；100% 免费无广告；随机态打乱质量高；配色方案可自定义到贴纸级 | 仅移动端，无桌面/网页版；最后更新停留在 2023 年；官方明示"本 App 生成的打乱不得用于正式比赛"（非 WCA 官方工具）；无虚拟魔方操作，不能"在应用内还原"；无程序化接口 | 免费 |

#### 竞品怎么做键盘映射与打乱展示（回答重点问题 1）

- **键位组织**：csTimer 的做法是**把 6 个面 + 宽转 + 内层 + 整体旋转全部平铺到三行字母键上**（原文键位表 3 行 × 10 列），规律是"字母区中段放高频面键、`Shift` 系与边缘键放宽转与整体旋转"。代价是必须依赖文档记忆，csTimer 也是把键位表直接印在设置页里。
- **打乱展示**：全部竞品都用**纯文本 Singmaster 串**（如 `R U R' U' F2 D'`）作为主展示，辅以 2D 展开图（Twisty Timer）或 3D 预览（csTimer 的 scramble image）。文本串是刚需——因为它是可复制、可核验、可粘贴进求解器的唯一格式。
- **打乱质量**：Twisty Timer 与 csTimer 都强调"随机态"而非"随机步"，且明确引用 TNoodle 作为质量锚点；Twisty Timer 甚至主动声明"非官方工具，不用于正式比赛"。**这说明"随机态 vs 随机步"的区分是速拧圈的共识性质量声明**，不是可选礼貌。

**对我们的启示**：
1. 打乱必须同时给**可复制的文本串**和**可视化**，文本串放主位。
2. 键位平铺是竞品的共同失败点。我们改成"空间映射 + 前缀分层"，并配常驻键位图和鼠标层选择器兜底——这不是差异化，是**必要的体验修正**。
3. "随机态 / 随机步"必须显式区分并标注，这是行业礼仪。

### 15.2 AI 评测平台

| 平台 | 题目复现机制 | 多次运行与评分机制 | 可借鉴 / 需规避 |
|---|---|---|---|
| **ARC-AGI 1/2/3**（ARC Prize Foundation） | 公开集 / 半私有集 / 私有集三层隔离防污染；每次评测用固定的开源 benchmark 仓库 + 每个模型一份 model configuration（模型名、推理档位、token 上限）；ARC-AGI-3 每任务发布**完整 replay** | 每任务 pass@2（同一测试输入允许 2 次尝试，任一次精确匹配即得分）；**逐任务 0/1，无部分分**；分数 = 解出任务占比；另报 cost/task 与 time/task；官方明确指出"同一分数在不同算力预算下含义完全不同"，强调成本归一化 | 借鉴：**分层题面集 + 无部分分 + 每任务发布 replay + 必须标注测试条件**。规避：本产品不追求"防污染"，因为纯前端做不到，宁可承认而不是假装 |
| **SWE-bench**（含 Verified / Lite / Pro） | 每个实例一套 **per-instance Docker 镜像**，把仓库版本、依赖版本、测试环境全部冻结；镜像分层（base → env → instance）兼顾复用与隔离；gold patch 先跑一遍验证实例"确实可解" | pass@1；判定用 `FAIL_TO_PASS`（修前失败、修后必须通过）+ `PASS_TO_PASS`（修前通过、修后必须仍通过）双清单；**全部通过记 1，任何一步失败记 0**；社区实证：**仅 harness/scaffold 配置差异就能造成约 12 个百分点的分数波动**，因此跨 scaffold 的分数不具可比性 | 借鉴：**双清单思想**——我们的对应物是"必须还原" + "不得违规（不超时、不超步、不用非法指令）"；以及"必须先验证题目确实可解"（对应我们的题面合法性校验 §6.4）。规避：不承诺跨 harness 可比，明确"人机同引擎"是我们唯一能保证的可比性 |
| **AgentBench**（THUDM 学术版 + 工程版） | 用 POMDP（状态空间 / 动作空间 / 转移 / 奖励 / 指令 / 观察空间）形式化；任务跑在独立容器；**所有模型统一 greedy decoding（temperature = 0）+ 单次 CoT 示例**以保证可复现；工程版提供 `trace.jsonl` 逐工具调用毫秒级时间戳 | 逐任务得分 + 各域平均 + 加权总分；**稳定性置信度 `CI = 1 - σ/μ`**（同一任务多次运行的得分标准差 / 均值），CI 越接近 1 表示表现越稳定；工程版明确"因 Agent 非确定性，分数在多次运行间会波动 ±3~5 分，建议跑 3 次取均值，看 delta 而不是绝对值" | 借鉴：**稳定性置信度** + **建议 3 次取均值** 直接成为我们 F13"多轮实验对比表"的核心指标；**逐调用时间戳 trace** 直接对应我们的 `ObservationEvent` / `MoveEvent`。规避：学术版用 LLM-as-judge 引入主观性，我们全用规则判定 |

#### AI 评测平台怎么保证同一题目可复现、多轮可对比（回答重点问题 2）

三家给出的是同一套骨架，只是实现层不同：

1. **固定题面本体**：题面不许在运行间变化。ARC-AGI 靠固定数据集文件；SWE-bench 靠 per-instance 镜像冻结；AgentBench 靠固定任务 fixture。→ 我们的对应物是 `seed` + `scramble` + `state_fingerprint` + `gen_version` + `notation_version`（不存状态快照，靠重放校验）。
2. **固定环境**：库里/依赖/系统版本全部冻结，避免"在我机器上没问题"。→ 我们的对应物是 `engine_version` + 纯前端无外部依赖（这反而是纯前端的天然优势：环境就是那个浏览器）。
3. **固定执行策略**：temperature = 0、单次示例、固定 scaffold、固定步数上限。→ 我们的对应物是 `RunConfig` 全量落盘 + `agent_meta`（prompt 版本、tool 版本）。
4. **二元判定，不给部分分**：避免"差不多对"污染结论。→ 我们沿用：`solved` / `not solved`，其余指标只作参考不作分数。
5. **每次运行独立记录 + 发布 replay**：结论必须可被人逐帧核验。→ 我们的对应物是 §10 回放 + 复制结果摘要（MVP 不导出 JSON）。
6. **多次运行报均值与稳定性**：单次分数不可信。→ 我们的对应物是 F13 对比表，含 `mean` / `std` / `CI`。
7. **明确标注测试条件**：算力预算、数据集版本、公开/私有集。→ 我们的对应物是结果页的 6 条诚实标注（§9.2：两条恒显 + 两条蒙尘 + 一条随机打乱 + 一条暂停）。

### 15.3 竞争格局结论

| 维度 | 速拧计时器（csTimer / CubeDesk / Twisty Timer） | AI 评测平台（ARC-AGI / SWE-bench / AgentBench） | 本产品 |
|---|---|---|---|
| 3D 魔方交互 | 有（csTimer 虚拟魔方）或无（Twisty Timer） | 无 | 有，且驱动引擎与 Agent 完全同源 |
| 题面可复现 | 部分（打乱可复现，但无"同题面多轮运行"概念） | 强 | 强（`seed` + `scramble` + 指纹 + 版本） |
| 观察权限受限 | 无（速拧不需要） | 无（任务全可见） | 有（三面/单面/受限） |
| 程序化接口 | **全部没有** | 有（但都是服务端/CLI） | 有，且**在页面内**、零部署 |
| 逐帧回放 | 无（只有成绩曲线） | 有（replay / trace） | 有，且含"观察者视角" |
| 部署成本 | 静态或 App | 重（Docker / 云 / 算力） | **零（静态站点）** |
| 防作弊 | 不关心 | 强（服务端持有状态） | **弱，已明确承认（§8）** |

### 15.4 我们的差异化（一句话）

> **"把速拧计时器的题面复现与键盘手感，和 AI 评测平台的同题多轮可比与逐帧 trace，压进同一个纯前端页面——人按下的是 `D` 键（R 面），Agent 调用的是 `applyMove('R')`，两者在引擎里是同一条指令、在回放里是同一条事件。"**

次级差异点（按重要性）：
1. **零部署的 Agent 评测**：不用 Docker、不用云、不用装东西，打开页面就能让 Agent 跑。
2. **观察者视角回放**：能回看"Agent 在单面观察下看到的是什么"，这是纯速拧工具和纯评测平台都给不出的。
3. **观察权限作为一等难度维度**：把"看得到多少"变成可配置的评测变量，而不只是"题有多难"。
